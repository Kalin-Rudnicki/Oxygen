## Expanded Description

**What it likely means:** Make the error output that the CLI prints when argument parsing fails more actionable. Today the system already reports *all* parse failures at once (not one-at-a-time — `docs/docs/executable/index.md:260`), but the *messages themselves* are generic, terse, and decoupled from the value that failed. The task is UX polish on `oxygen-cli` / `oxygen-executable` parse errors, not a new feature.

**Current behavior (verified from code):**

*Tokenizer:* `modules/general/cli/src/main/scala/oxygen/cli/Arg.scala:34-227` tokenizes raw `List[String]` into `Args(PositionalArgs, NamedArgs)` and surfaces brace errors as plain `Either[String, _]` strings (`"Missing closing brace for opening brace at index $i"`, `"Unexpected closing brace at index $i"`). In `modules/general/executable/src/main/scala/oxygen/executable/CliApp.scala:45-46` these are printed verbatim via `Console.printLine(message)` and exit `2` (`ExecutableError.usageErrorExitCode`) — no help text, no color.

*Parse errors:* `modules/general/cli/src/main/scala/oxygen/cli/CliParseError.scala:19-38` defines the error ADT (`MissingRequiredPositional(name)`, `MissingRequiredNamed(name)`, `FailedValidation(message)`, `UnparsedPositional`, `UnparsedNamed`, `NamedUnexpectedValues`, `MissingEnvVar`, plus `PositionalOr/NamedOr/RootOr/RootAnd` combinators). Construction sites attach a single generic hint via `HelpHint.Error`:
  - `PositionalArgsParser.Single:399-400` — `MissingRequiredPositional(name)` + `HelpHint.Error("Missing required value")`
  - `NamedArgsParser.Named:871` — `MissingRequiredNamed(longName)` + `HelpHint.Error("Missing required param")`
  - `NamedArgsParser.Toggle:908` — `"Missing required param"` as above
  - `PositionalArgsParser.Single:399` — decode failure `Left(msg)` → `FailedValidation(msg)` + `HelpHint.Error(msg)` where `msg` is the raw `PlainTextSchema`/`JsonSchema` decode message (e.g. `"For input string: \"abc\""` for `Int`)
  - `NamedArgsParser.Named:866-868` — `NamedUnexpectedValues(longName, values)` + `"Requires a single value"`
  - `ExecutableParser:66-84` — leftover args → `UnparsedPositional`/`UnparsedNamed` + `Help.UnparsedPositional/Named` rendering `"Unparsed value ${v} at index ${idx}"` / `"Unparsed param --$name at index $idx"` in `Help.scala:144-158`
  - `ExecutableParser:66` — `MissingEnvVar` → `Help.Raw(message)` where message is `"Required environment variable [$VAR] is not set"` from `NonCLIExecutableParser`

*Rendering:* `CliParseResult.Fail(error, help)` is rendered only as `fail.help.toString` via `Help.Repr.format` (`CompiledCliApp.scala:94-95` `renderParseFail`). `HelpHint.Error` is rendered red (`Help.scala:154`) but sits in the *right column* next to the param's help entry — the left column is just `"--longName, -c"` or `"[name]"`. No top-level header like `"Error: 3 problems found"`, no echo of the offending input value, no suggestion ("did you mean --verbose?"), no enum-value hint beyond `Enum: a, b` already present, no footer like `"Try --help"`.

**Why this is weak:**

1. *Generic missing messages* — two different required positionals both say `"Missing required value"` with only the `Help.Positional("[first]")` line distinguishing them; two missing flags both say `"Missing required param"` identically. A user scanning quickly cannot tell *which* value is missing without cross-referencing the help column.
2. *FailedValidation is context-free* — the schema message (`"Invalid Int ..."`) does not mention the param name or the input that was rejected (`--count abc` → `"For input string: \"abc\""` but not `"Invalid value 'abc' for --count"`).
3. *Unparsed is developer-centric* — `"Unparsed param --verboze at index 3"` does not explain "unknown option" nor suggest a near match (`--verbose`). The `index` is an internal token index, useful for debugging the parser but noisy for users.
4. *No input echo for NamedUnexpectedValues* — `"Requires a single value"` does not show how many values were supplied or what they were.
5. *Tokenizer errors bypass Help* — brace mismatches never show help, just a lone line.
6. *No summary* — with `RootAnd` accumulating 3-4 failures, the output is just N help rows with sporadic red hints; there is no counts header, no separation between "errors" and "usage".

**Who it affects:** Every `oxygen-executable` user — any app extending `CliApp` + `derives CompiledCliApp.DeriveRootApp` (example `example/apps/example-app/src/main/scala/oxygen/example/exampleApp/ShowcaseApp.scala`, `example/apps/web-server/src/main/scala/oxygen/example/webServer/WebServerMain.scala`, and all services using `@named`/`@positional`/`@flag`/`@toggle`). The error is the first thing a user sees on a typo. Low priority suggests correctness is not blocked — this is polish.

**Inferred acceptance criteria (what "improved" most plausibly means given Low scope):**

1. Missing-required messages include the param identity — e.g. `Missing required positional '[name]'` / `Missing required option --token` (or `HelpHint.Error` rewritten to embed the name). At minimum the hint should not be the same string for every param.
2. FailedValidation messages include both the param name and the rejected raw input — e.g. `Invalid value 'abc' for --count: For input string: "abc"` / `Expected Int for [port] but got 'xyz'`. Schema message stays, but is prefixed with context.
3. Unparsed/unknown-flag messages say "Unknown option" and suggest a close match when applicable (`--verboze` → `Did you mean --verbose?`), using a bounded Levenshtein check over `CliHelp.collectParamNames` / `CompiledCliApp` help. No suggestion when distance too large.
4. NamedUnexpectedValues includes count/values — e.g. `Option --output expects a single value but got 2: 'a' 'b'`.
5. Output has a header/footer: `Error: failed to parse arguments (3 errors):` at top and `Try '--help' for usage` at bottom, with color still red for errors but now clearly separated from the help table. `renderParseFail` is the injection point.
6. Tokenizer `Either[String,_]` brace errors are routed through `Help.Raw` (or a dedicated `HelpHint.Error`) so they render with help, not lone lines, and include the same header.
7. Existing behavior preserved: still reports *all* errors at once (`RootAnd` accumulation), still exits `2`, still renders help. No parsing semantics change — only messages + rendering. Tests updated/added, help goldens not broken unexpectedly.
**Scope is almost certainly `modules/general/cli` + `modules/general/executable` core — not `oxygen-sql`, `oxygen-json`, or docs beyond the 2-line Errors section in `docs/docs/executable/index.md:258-261`. The title says "in CLI" and the owning modules are `oxygen-cli`/`oxygen-executable` per `build.sbt:241-268` and `docs/docs/executable/cli.md`.**

## Open Questions

1. **Intended breadth:** Did "Improve parse error messages" mean only the missing/validation hints, or also the Unparsed/unknown-flag suggestion + header/footer + tokenizer fix? The checklist line gives no hint — OXY-101 epic body (if it exists in Jira) might narrow this.
2. **Exact wording:** Should missing messages say "Missing required option --foo" vs "Missing required param --foo" vs "Missing required value for --foo"? Each matches a different existing string. Same for toggle: "Missing required flag --enable-x / --disable-x" ?
3. **Input echo format:** When echoing the rejected value, should we quote it (`'abc'`), truncate at N chars, or escape newlines? Should we show the raw `PositionalArg.value` exactly as typed or the normalized decode input?
4. **Did-you-mean scope:** Should suggestion cover only named options (`--longName` / `-c`) or also positional value enums (`Mood`)? Should it be case-sensitive? Threshold 2 vs 3 edit distance? Should `-c` vs `-C` case-flip count as distance 0?
5. **Header/footer copy:** Is the desired header `"Error: failed to parse arguments (N errors):"` or `"error(N):"`? Should the footer always be `Try '--help' for usage` or `Try 'my-app subcmd --help'`? Does `OXYGEN_CLI_JSON=true` suppress the header?
6. **ADT enrichment:** Is it acceptable to keep the `HelpHint.Error` string-only channel (simpler), or should `CliParseError.FailedValidation` carry structured `paramName + rawInput + cause` so typed rendering/testing is possible? The latter is cleaner but touches more call sites.
7. **Color / no-color:** Should the suggestion and header respect `NO_COLOR` / `Constants.oxygenCliJson` suppression? Currently `Help` uses `ColorString` with ANSI; confirm header should be colored red via `Help.Raw` / `HelpHint.Error`.
8. **Tokenizer help:** Should brace errors (`"Missing closing brace ..."`) render the full help table or just a minimal `"Parse error: ..."` + `--help` pointer? Today they bypass help entirely.

## Expanded Description

**What this likely is:** Extend the current minimal `PageMessage` / `PageMessages` toast system into a richer, featureful notification + dialog primitive. Today the system is deliberately minimal (see Step 3 verification); this task is the follow-up to make it production-usable for real apps.

**Current state (verified from code):**

- `PageMessage` (`modules/ui/web/src/main/scala/oxygen/ui/web/PageMessage.scala:7-72`) is `final case class PageMessage(id: UUID, type: PageMessage.Type, content: Widget)` with `Type = Primary|Positive|Negative|Info|Warning|Error|Custom(Styling)` and helpers `PageMessage.primary/info/warning/error/...` that take `String` or `Widget*`. No title, no duration, no actions, no icon, no dismiss control, no persistence flag.
- `PageMessages` (`PageMessages.scala:5-54`) is `Chunk[PageMessage]` with `add/remove/clear` plus `PageLocal extends PageLocalState[PageMessages]` (backed by `PageLocalState`) and ZIO helpers `PageMessages.add/remove/schedule(message, duration)` — `schedule` forks a daemon that adds, sleeps, then removes. No per-message duration default, no `schedule` overload without explicit duration, no grouping/dedup.
- `PageMessagesBottomCorner` (`component/PageMessagesBottomCorner.scala:12-200`) is the sole renderer: fixed `bottom:0 right:0`, `PageMessages.PageLocal` attached, `O.Scrollable` list capped at `maxWidth 750px / minWidth 250px / maxHeight 75vh`, each card is `flex row` with `preWrap + break-word + overflow-wrap:anywhere` content and a single `×` dismiss button. Auto-included by `HolyGrail` (`layout/HolyGrail.scala:37,105-114` — `includePageMessages = true` by default, `noPageMessages` / `includePageMessages(s)` to opt out). Wrapping fix for long text landed separately (OXY-109) — `whiteSpace.preWrap` + `flex:1 1 auto / minWidth:0` prevents the overflow bomb, but the card itself is still one-size.
- `Modal` (`component/Modal.scala:15-200`) already exists as a deferred `PWidget` with scrim, size presets `sm/md/lg/xl/full`, `compact/comfortable` padding, and `Modal.option` for optional close semantics. `Drawer` also exists. But there is no `Dialog` / `AlertDialog` / `Confirm` wrapper and no bridge between `PageMessages` and `Modal` — i.e., no way for a message to carry an action that opens a dialog, and no way to `open dialog` as a page-message-like global imperative (vs. embedding `Modal` inline in a page's widget tree).
- Showcase usage (`example/apps/ui/src/main/scala/oxygen/example/ui/page/showcase/pages/MessagesPage.scala:13-31`) confirms the current limited scope: four buttons each fire `PageMessages.add(PageMessage.info/positive/warning/error("..."))`, plus long-text variants with `"... " * 50`. No actions, no dialog.
- No `Dialog` component exists in `modules/ui/web` — grep for `Dialog` only hits `PageMessagesBottomCorner` docs and `Modal` comments ("Defaults are tuned for a typical confirm/dialog"). `create/nodes.scala` does define `val dialog: Node = Node("dialog")` (native `<dialog>` tag) but it is unused.
- No docs for page messages exist in `docs/docs/ui/` — `docs/docs/ui/index.md` Quick Start notes `PageMessagesBottomCorner` is auto-included by `HolyGrail` but does not document `PageMessage` API; `docs/docs/ui/builders.md` and `docs/docs/ui/agent-guide.md` mention `toUI` / page messages only as error handling (`UIError.toPageMessages`).

**What "more featureful page messages, open dialog, etc" most plausibly means (ordered by likelihood):**

1. **Richer `PageMessage` model:** `title: Option[String]` (or `Widget`), `description` vs `content`, per-message `duration: Option[Duration]` (auto-dismiss timeout, `None` = sticky), `dismissible: Boolean`, `icon: Option[Widget]` (or auto by `Type`), `actions: Chunk[MessageAction]` where `MessageAction = (label: String, action: UIO[Unit] | WidgetAction)` — e.g., "Undo", "Retry", "View details". Current `content: Widget` already allows arbitrary widgets, but there is no *structured* action row and no *typed* dismiss/open semantics callers can rely on without hand-rolling.
2. **"Open dialog" as a first-class companion:** Either (a) a `PageDialogs` global akin to `PageMessages` (e.g., `PageDialogs.open(Modal(...))` / `PageDialogs.confirm(title, body): UIO[Boolean]`) that renders a modal overlay via `PageLocalState`, or (b) a `PageMessage` action that opens a `Modal` — e.g., `PageMessage.info("Saved", action = Button("View") -> openDialog(...))`. Title says "open dialog" comma-separated from "page messages", suggesting a parallel global dialog primitive, not just a button inside a toast.
3. **Placement / stacking polish:** Configurable corner (`bottomRight` vs `topRight` vs `bottomCorner` vs `top`), max visible count, newest-on-top vs bottom, animation (slide-in/out), grouping, and `closeAll` already exists but could be refined (per-type clear, dismiss after action).
4. **Convenience helpers:** `PageMessages.info/warning/error` that accept `String` + `Duration` + `actions`, `PageMessages.schedule` overloads, `UIError.toPageMessages` integration keeping working, and maybe `FormResult` -> page message bridging (`FormResult.Error` auto-toasts).
5. **"etc" catch-all:** Likely placeholder for follow-ups like inline message variants (`PageMessagesInline` or `InlineAlert` for non-corner placement), toast vs banner vs dialog choice, accessibility (`aria-live="polite"` / `role="alert"` / `aria-label`), and docs. Title's vagueness is consistent with a High-priority but underspecified roadmap bucket after OXY-109.

**Who it affects:** Every `oxygen-ui-web` app using `HolyGrail` (which auto-includes the corner) — essentially all Oxygen UIs (`example/apps/ui`, `example/apps/ui-electron`, `example/apps/example-app` via `example/ui`). More featureful messages + imperative dialog unblock common product patterns: "Saved — Undo", "Upload failed — Retry", "Confirm delete — Cancel / Delete", "Session expired — Sign in again (opens dialog)", without each team hand-rolling a modal store.

**Why it matters (Priority High):** `PageMessage` is the user-visible feedback channel for every mutation/error. With only a string + type + fixed dismiss, teams must either bypass it (custom local state per page) or live with poor UX (no actions, no timed toasts, no confirm flows). OXY-109 (Higher bug, long-text wrap) and OXY-110 (High task, featureful) are intentionally adjacent: first fix the overflow, then make the component actually useful. This is the UI equivalent of OXY-74 (add logging to http-server) — a High polish item that is not blocking but is needed before the framework feels complete.

**Inferred acceptance criteria:**

1. `PageMessage` extended with at least `title: Option[Widget/String]` and `actions: Chunk[MessageAction]` (or `footer: Option[Widget]`) so callers can render `"Saved"` + `"Undo"` button inside the toast without forking the component. Backwards compat: existing `PageMessage.info("...")` / `PageMessages.add` still compile (new fields defaulted).
2. Auto-dismiss semantics: `PageMessages.schedule(msg, duration)` remains, plus either `PageMessage` carries `duration: Option[Duration]` or `PageMessages.add(msg, duration)` overload, with per-type defaults (e.g., `info` 4s, `error` sticky). Existing `PageMessagesBottomCorner` respects duration (or a new `PageMessagesToast` wrapper handles timers).
3. Dialog primitive: a global `PageDialogs` (or `Dialogs`, `Modals`) store akin to `PageMessages.PageLocal` that can `open(Widget)` / `open(Modal)` / `confirm(title, body): UIO[Boolean]` imperatively from any `UIO`/`onClick` handler, and is rendered once in `HolyGrail` (or via a new `HolyGrail.withDialogs` slot). Alternatively, at minimum `PageMessage` actions can trigger `Modal.option` without manual page-local wiring. Choice documented; either satisfies "open dialog" but global store is more likely given the imperative phrasing.
4. Renderer updated: `PageMessagesBottomCorner` (or a new `PageMessagesToasts` / `Toasts` component) handles title + body + action row layout, icon by type, sticky vs timed styling, and preserves the OXY-109 wrapping fix (`preWrap`, `break-word`, `overflow-wrap:anywhere`). Mobile still caps at `min(maxWidth, calc(100vw - 24px))` and scrolls.
5. Showcase + tests: `MessagesPage` (or `DialogsPage`) demonstrates new APIs — info/success/warning/error with actions, timed vs sticky, dialog confirm flow. No dedicated `modules/ui/web/src/test` for page messages exists today, so at minimum manual showcase verification + any existing `PWidget` render smoke tests still pass. If a test harness is added, it covers `PageMessages.add/remove/schedule` and `PageDialogs.open/close`.
6. Docs: short section in `docs/docs/ui/builders.md` or new `docs/docs/ui/messages.md` showing `PageMessages.add(PageMessage.info(...))` + `schedule` + actions + dialog usage, with note that `HolyGrail` auto-includes the overlay and how to opt out / customize (`PageMessagesBottomCorner(...)`, `includePageMessages(false)`).
7. No breaking change to `PageMessagesBottomCorner.default` or `HolyGrail.includePageMessages` — existing apps that do `PageMessages.add(PageMessage.info("Hi there!"))` (`UIMain.scala:27`) continue to work.

## Open Questions

1. **Scope of "more featureful":** Does this issue require (a) `title` + `actions` + `duration`/`sticky` on `PageMessage` only, or (b) that plus a standalone global `PageDialogs`/`Dialogs` primitive? Title lists "page messages, open dialog" comma-separated — are these two deliverables in one issue or alternative phrasings of the same toast-plus-action idea?
2. **Dialog primitive shape:** Should `open dialog` be a global `PageDialogs.open(Modal): UIO[Unit]` / `confirm(...): UIO[Boolean]` (imperative, like `PageMessages.add`) rendered once in `HolyGrail`, or is it sufficient to document per-page `Modal` usage and add `PageMessage.actions` that trigger a page-local `Modal`? Should dialogs stack (multiple open) or be single?
3. **`PageMessage` API:** Should `title` be `String` or `Widget` (or both overloads)? Are actions `Chunk[(label, UIO[Unit])]` (simple) or full `Widget` row? Should there be `icon`/`dismissible`/`duration` fields on the model, or are those renderer config on `PageMessagesBottomCorner`? Must existing `PageMessage.info("...")` remain source-compatible?
4. **Duration / auto-dismiss policy:** Default timeout per `Type` (e.g., `info` 5s, `error` sticky)? Should `schedule` remain the only timed path, or should `PageMessages.add(msg)` auto-schedule from `msg.duration`? Should closing a toast cancel its timer?
5. **Relation to OXY-109:** OXY-109 (Higher, "Fix long text not wrapping") is the wrapping bug already fixed in `PageMessagesBottomCorner`. Should OXY-110 re-verify that fix under the new layout (title + actions row must not reintroduce overflow), or is OXY-109 assumed done? Should `MessagesPage` long-text variants be kept as regression fixtures?
6. **Placement & a11y:** Keep bottom-corner only or add `topRight`/`bottomCorner` config? Required a11y (`aria-live`, `role="alert"` for errors, focus management for dialogs)? Is animation (slide/fade) in scope?
7. **Docs & showcase location:** New `DialogsPage` vs extending `MessagesPage`? New `docs/docs/ui/messages.md` vs section in `builders.md`? Should `docs/docs/ui/index.md` Quick Start be updated to mention `PageDialogs`?

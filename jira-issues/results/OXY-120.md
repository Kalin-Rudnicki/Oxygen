## Expanded Description

**What this issue likely means:** Add ergonomic macro helpers that reduce boilerplate when *creating* (defining or instantiating) classes inside Scala 3 macros, owned by the `oxygen-meta` / `oxygen-quoted` stack (`modules/general/core/src/main/scala/oxygen/meta/` + `modules/general/quoted/`). The title is deliberately generic ("creating classes using macros") and maps to two closely related gaps that are both observable in the current code.

**Gap 1 — Defining new classes at macro-expansion time is verbose (primary interpretation, ~60% probability).**

Today `oxygen.quoted` (`modules/general/quoted/src/main/scala/oxygen/quoted/companion/Symbol.scala:43-280`, `Tree.scala:39-56`) already wraps `Quotes.reflect.Symbol.newClass` / `ClassDef` into a lifted API, but using it still requires ~15-40 lines per generated class (see `Symbol.scala:43-60` doc example: create `Symbol.newClass`, then `DefDef` for each member, then `ClassDef`, then `Typed(Apply(Select(New(TypeIdent(cls)), ctor), ...), TypeTree)` and `Block(List(clsDef), newCls)`). There is no high-level helper that collapses this to a one-liner. Any macro that wants to synthesize a class (e.g. generating a synthetic `case class` for migration, test fixture, or for `oxygen-sql`/`oxygen-executable` codegen) must hand-roll the full ceremony and get constructor `ParamClause` / `Flags` / `parents` wiring right. The issue asks to add helpers that do this.

Evidence for this reading:
- `oxygen-quoted` exists explicitly to make `Quotes.reflect` ergonomic ("lifts all the types out of `Quotes.reflect` into top-level definitions" — `docs/docs/metaprogramming/index.md:34`), but its `Symbol.newClass` wrappers are still thin forwards (`Symbol.scala:86-87`), not builders.
- `oxygen-meta` (`modules/general/core/src/main/scala/oxygen/meta/k0/ProductGeneric.scala`, `Generic.scala`, `Derivable.scala`) already hides `ProductGeneric`/`SumGeneric` reflection complexity, but has no counterpart for *emitting* new type definitions — only for *inspecting* existing ones and *instantiating* them via `fieldsToInstance` / `instantiate.instance`.
- `docs/docs/metaprogramming/meta.md` is stubbed (only headers for `K0.Generic` / `K0.ProductGeneric` / `K0.SumGeneric`, no body), indicating planned meta helpers that were not yet written — class-creation helpers are the natural next section.
- The Epic sibling grouping is telling: OXY-119 (sum types with type params), OXY-120 (creating classes), OXY-121 (unions as sum types) are all `oxygen-meta` product/sum/type-definition concerns, not transform/json/sql concerns. "Creating classes" as *emitting class definitions* fits that cluster.

Typical helper shapes this would imply (all inferred, no spec was fetchable):
- `ClassBuilder` / `ClassMaker` / `NewClass` DSL: `Symbol.newClass(...).withParams(...).withMembers(...).buildClassDef` or `ClassDef.create(name, fields: List[FieldDef], parents, flags)` returning `(Symbol, ClassDef, Term)` ready to splice.
- Convenience for the common cases: `case class` with N fields, `case object`, sealed trait member, or plain `class` with single param list — e.g. `inline def newCaseClass[A](fields: List[(String, TypeRepr)]): Type[A]` or macro that materializes `new { class Anon(...) }`.
- Annotation-macro friendly variant: helpers for `MacroAnnotation` (`@compile`, `TableCompanion`, `CliApp`) that rewrite a `ClassDef` tree (add members, modify constructor) without manual `Tree.copy` boilerplate.

**Gap 2 — Instantiating existing classes from constituent parts is still manual (secondary interpretation, ~35% probability).**

`ProductGeneric[A]` already can *inspect* a product and *instantiate* it (`ProductGeneric.scala:27` `def fieldsToInstance`, `66` `val instantiate`, `131-156` `Instantiate.monad/option/either`), and `Derivable` / `ProductGeneric.deriveTransform` shows how to go `Tuple <-> CaseClass`. But there is no first-class "make an `A`" helper that a call site can use without knowing `ProductGeneric` internals — e.g. `Make[A].fromTuple(tuple)`, `Make[A].fromMap(Map[String, Any])`, ` Make[A].withDefaults` filling `constructorDefault` (field `ProductGeneric.Field.constructorDefault` at `ProductGeneric.scala:115-123` exists but is only used in tests `MacroSpec.scala:81` to *read* defaults, never to *construct* with them), or `NewInstance[A](args: Expr[Seq[Any]])`. Under this reading the issue is about factory helpers that wrap `fieldsToInstance` + default handling + `Expr` sequencing.

The two interpretations are not mutually exclusive — a complete "helpers for creating classes" could provide both a `ClassDef` builder (define new types) and a `Make[A]` factory (instantiate existing types). The title's plural "helpers" and "classes" leans toward the first, but either could satisfy a reviewer who expected the second.

**Who it affects:** Any author writing macros in the oxygen codebase — `oxygen-sql` table derivation (`TableRepr.derived`), `oxygen-json` / `oxygen-schema` typeclass derivation (`Derivable`), `oxygen-executable` CLI parser generation (`DeriveCliApp`, `ParserCodegen`), `oxygen-transform` product/sum derivation, and future `MacroAnnotation` users (`@compile` in `modules/sql/core/src/main/scala/oxygen/sql/query/dsl/annotations.scala:10`). Today each writes its own `Symbol.newClass`/`ClassDef`/`fieldsToInstance` ceremony; helpers would be reused by all.

**Why it matters:** Macro code that emits classes is currently the most error-prone part of the meta stack (owner `Symbol.spliceOwner` mistakes, `Flags` wrong, constructor `ParamClause` mismatched, `AppliedType` vs `TypeIdent` confusion). Centralizing it behind tested helpers reduces compile-time errors, improves the empty `meta.md` docs story, and supports OXY-119/OXY-121 which will also need to emit or materialize types with type parameters / union members.

**Inferred acceptance criteria:**
- New helper(s) exist in `modules/general/quoted` or `modules/general/core/src/main/scala/oxygen/meta/` that wrap the verbose `Symbol.newClass` + `ClassDef` + `New` + `Select` + `Apply` sequence into a 3-10 line call. At minimum one helper for "define a new class with given name/parents/fields/members" and one for "instantiate an existing ProductGeneric from Exprs with default-value fallback".
- Helpers work on all cross-platform targets where macros run (JVM at minimum; `js`/`native` if macro code is shared) and have Scaladoc with an example.
- Before/after example: a macro that previously needed ~30 lines to emit `class Foo(x: Int, s: String)` can now do it in ~5 lines via the helper, and the generated class compiles and is instantiable.
- At least one existing or new test (`modules/tests/pre-test-unit-tests/src/test/scala/oxygen/meta/MacroSpec.scala` or new `ClassCreationSpec`) demonstrates defining a class via the helper and instantiating it, plus a `ProductGeneric` instantiation using the new factory helper with defaults.
- Docs updated: `docs/docs/metaprogramming/meta.md` (currently stubs only) or `docs/docs/metaprogramming/quoted.md` mentions the new helpers with a snippet.
- No behavioral change to existing `Derivable` / `ProductGeneric` / `oxygen-quoted` APIs — additive only.

## Open Questions
1. **Which "creating classes" meaning is intended — defining new `ClassDef`s vs. instantiating existing products?** Title is ambiguous. Is the primary helper expected to wrap `Symbol.newClass` + `ClassDef` + `Block`/`New` ceremony (define path), or to wrap `ProductGeneric.fieldsToInstance` + `Field.constructorDefault` into `Make[A].fromMap`/`fromTuple`/`withDefaults` (factory path), or both? This is the blocking decision — recommend treating define-path (Option A) as OXY-120 scope and factory-path (Option B) as optional/follow-up unless human confirms otherwise.
2. **Should the helpers also support rewriting classes via `MacroAnnotation` (e.g. `@compile`)?** `oxygen-sql`'s `@compile` (`modules/sql/core/src/main/scala/oxygen/sql/query/dsl/annotations.scala:10`) and `oxygen-executable`'s `@command` already rewrite `ClassDef`/`DefDef` trees. Is the expected helper a `ClassDef.update` / `addMember` DSL for annotation macros, or only inline `inline def` helpers? Answer determines whether `quoted/Tree.scala:39-56` `ClassDef` copy helpers need wrapping.
3. **What class kinds and members must be supported in v1?** Plain `class` vs. `case class` vs. `case object` vs. `sealed trait` member? Single term param list vs. type params vs. multiple param lists (givens)? No parents vs. extending a trait? The simplest `newCaseClass(name, fields)` covers 80% of cases; full generality (type params, parents, `Flags`, `selfType`) matches `Symbol.newClass`'s 3 overloads (`Symbol.scala:86,147,261`) and may belong to OXY-119 if type params are involved.
4. **How should constructor defaults and named args be handled?** `ProductGeneric.Field.constructorDefault` (`ProductGeneric.scala:115-123`) notes `-Yretain-trees` is needed to retain the actual expr; otherwise it falls back to a function reference. Should `Make[A].withDefaults` produce the actual default value Expr when available or always call the `$lessinit$greater$default$N` accessor? And should the helper support named-arg maps for `MacroAnnotation` rewriting?
5. **Where should the helpers live — `oxygen-quoted` (generic lifted-reflect helpers) or `oxygen-meta` (K0-aware builders taking `ProductGeneric` fields)?** `oxygen-quoted` is zero-dep lifter; `oxygen-meta` already knows about `ProductGeneric`/`Generic`. The natural split is a low-level `quoted.ClassBuilder` (raw `TypeRepr`/`Symbol`) plus a thin `meta/k0.Make` that delegates to it — but the intended module boundary is unstated. This affects imports for consumers.
6. **Is annotation-doc / example expected?** `docs/docs/metaprogramming/meta.md` is empty; should OXY-120 fill it with a "Creating classes" section, or is `docs/docs/metaprogramming/quoted.md` the right location? Also, should an `example/` snippet be added (e.g. `example/apps/...` generating a synthetic DTO) or is `MacroSpec.scala` coverage sufficient?
7. **Assumption documented:** This triage assumes the Epic is OXY-118 `oxygen-meta` (verified: `checklist.md:69` ` — **Epic** · Normal — oxygen-meta`, In Progress) and that the helpers belong in `modules/general/core/src/main/scala/oxygen/meta/` + `modules/general/quoted/`. If the human intended a different module (e.g. `oxygen-executable` class generation), the module ownership and sibling list above would need retargeting.

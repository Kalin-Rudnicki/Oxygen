## Expanded Description

**What this is:** Split the current monolithic `Json.Type.Number` (which today covers every numeric `Json.Number(BigDecimal)` — `Int`, `Long`, `BigInt`, `Double`, `BigDecimal`, etc.) into two distinct JSON type discriminants: an integer type and a fractional/number type. The title "separate `Int` JsonType (json + schema)" and the cross-reference in `jira-issues/results/OXY-72.md:81` ("Comparable to OXY-149 (separate `Int` JsonType)") make it clear this is the `oxygen-json` + `oxygen-schema` counterpart to OXY-72's tuple work — a small cross-cutting shape addition.

Today:

* `modules/general/json/src/main/scala/oxygen/json/Json.scala:85` — `enum Type derives StrictEnum { case String, Number, Boolean, Array, Object, Null }` — six cases, `Number` is the only numeric type.
* `Json.scala:43-45` — `def tpe: Json.Type` maps `_: Json.Number => Json.Type.Number` unconditionally; there is no `isWhole` branch.
* `Json.Number` holds `BigDecimal` and all numeric helpers (`Json.number(Int)`, `Json.number(Double)`, etc.) funnel through it (`Json.scala:223-230`).
* `JsonDecoder.BigDecimalDecoder` (`JsonDecoder.scala:186-211`) already distinguishes `narrow` vs `narrowWhole` (the `narrowWhole` checks `isWhole`), and `JsonEncoder` mirrors it, but the *type* error path still reports `Json.Type.Number` (`JsonDecoder.scala:196`).
* `modules/general/schema/src/main/scala/oxygen/schema/NumberFormat.scala` already distinguishes `Whole` (`Int8/16/32/64/BigInt`) vs `Fractional` (`Float32/Float64/BigDecimal`), and `JsonSchemaEmitter.scala:112-115` already emits `"integer"` for `Whole` and `"number"` for `Fractional`. So the schema *format* layer already splits integers from floats, but the `Json.Type` / `JsonAST` layer does not — `JsonSchemaEmitter.astSchema` (`JsonSchemaEmitter.scala:124-132`) still only has `Number` → `"number"` and no `Integer` case.

The intended change is to make the JSON type system match JSON Schema draft 2020-12 (and OpenAPI) where `type: "integer"` and `type: "number"` are distinct, and to give `oxygen-json` a first-class integer discriminant so decoders, schema compilation, and compatibility checking can tell `123` (integer) from `1.5` (number) without re-inspecting the `BigDecimal`.

**Who it affects:**
* Any consumer that pattern-matches on `Json.Type` or `JsonError.Cause.InvalidType` (JSON API boundaries, generic derivation, tests).
* Any `oxygen-schema` user whose API model contains integral fields (`Int`, `Long`, `Short`, `Byte`, `BigInt`) — emitted JSON Schema currently emits `"integer"` via `NumberFormat` but loose `Json`/AST schemas still emit `"number"`.
* MCP / `oxygen-http` tool `inputSchema` generation (`JsonSchemaEmitter` is the MCP inputSchema backend — `JsonSchemaEmitter.scala:5-15`).
* Compatibility/diffing (`modules/general/schema/src/main/scala/oxygen/schema/compat/Compared.scala:332-336`) — integer-vs-number evolution needs explicit rules.

**Why it matters (Priority Normal):** Without this, `Json.Type` is coarser than JSON Schema and loses information: an integer value and a fractional value are indistinguishable at the type level, so error messages, `JsonAST`-typed schemas, and future `integer`-specific validation are imprecise. High-priority siblings (OXY-70 Option/Required, OXY-72 Tuple) show the schema module is being hardened — this is the numeric counterpart. None of the current call sites are broken, but the abstraction is leaky.

**Inferred acceptance criteria:**
1. `Json.Type` gains a distinct integer case (name TBD — see Open Questions; likely `Integer` to avoid shadowing `scala.Int`, as `OXY-149` title uses backticks for concept not literal case name). `StrictEnum` derivation picks it up.
2. `Json#tpe` and `Json.Number` handling distinguishes integer vs fractional (either via `BigDecimal.isWhole` branching or via a new `Json.Integer`/`Json.Int` case class/subtype). At minimum `tpe` returns `Integer` for whole numbers and `Number` for fractional numbers.
3. `JsonParser` (currently always `Json.Number(coreNumber)` at `JsonParser.scala:88-138`) either preserves the integer/fraction distinction or the `tpe` logic derives it from the stored `BigDecimal`. No silent re-parsing change is acceptable for existing tests.
4. `JsonDecoder` / `JsonEncoder` subtype decoders for `Json.Number` still work, and a new `JsonDecoder[Json.Integer]`-style subtype (or `JsonError.InvalidType` now reporting `Integer` vs `Number`) is added if a new node type is introduced.
5. `oxygen-schema` plumbing recognizes the new type:
   * `IntermediateRepr.JsonNumber` / `RawCompiledJsonSchema.JsonNumber` / `FullCompiledJsonSchema.JsonNumber` already carry `NumberFormat`, but `JsonAST` and emitter `astSchema` must gain an `Integer` branch.
   * `JsonSchemaEmitter.numberSchema` and `astSchema` emit `{"type":"integer"}` for integer and `{"type":"number"}` for fractional; `JsonSchemaEmitter.scala:112-132` is the reference.
   * `Compared` / `ComparisonResult` diffing treats `integer → number` as widening (backward-compatible) and `number → integer` as narrowing (breaking), analogous to `NumberFormat` whole/fractional logic and the existing `JsonAST` branches at `Compared.scala:322-336`.
6. Existing tests pass; new tests prove `Json.parse("123").tpe == Integer`, `Json.parse("1.5").tpe == Number`, `JsonDecoder[Int]` rejects fractional, and `JsonSchema[Int]` emits `{"type":"integer"}` while `JsonSchema[Double]` emits `{"type":"number"}`.
7. No breaking change to public `Json.number(...)` helpers unless a new `Json.integer(...)` helper is added (see Open Questions).

## Open Questions

1. **Case name:** `Integer` vs `` Int `` vs `Int` object? `scala.Int` shadowing argues for `Integer` (JSON Schema spec term), but the ticket writes `` `Int` `` (conceptual). Confirm `Json.Type.Integer` is acceptable, or if the ticket literally wants ``case `Int` `` / `case Int` with backticks. `StrictEnum` encoded values and docs will propagate this name.
2. **ADT shape — new node or just new type?:** Should `Json` gain a new `final case class Integer(value: BigDecimal) extends Json` alongside `Number` (so pattern matching can distinguish at compile time), or should `Json.Number` stay the sole holder and `tpe` be derived via `value.isWhole`? New node is more type-safe and matches `String/Bool/Arr/Obj` pattern, but is a breaking API change for every `case n: Json.Number =>`. Derived `isWhole` is non-breaking but conflates representation with classification.
3. **`isWhole` rule & exponent:** `BigDecimal("1.00").isWhole == true`, `BigDecimal("1e3") == 1000` is whole, `BigDecimal("0.000")` is whole — should these be `Integer`? JSON Schema `integer` means "number without fractional part" under `number.isWhole`, so yes — but confirm parser exponent normalization (`JsonParser.scala:120-136` already normalizes `1e3` via `*10.pow(shift)`), and whether trailing `.0` should count as integer for `tpe`.
4. **Builder helpers:** Should `Json.number(Int)` now return `Json.Integer`? Should a new `Json.integer(...)` factory be added? If `Json.Number` stays, `Json.number(Int)` returning `Json.Number(BigDecimal(5))` but with `tpe == Integer` is consistent; if new node is added, `Json.number` should probably delegate to `Json.Integer` for integral inputs and `Json.Number` for fractional — confirm desired API.
5. **Decoder expectation:** When `JsonDecoder[Int]` (via `narrowWhole`) decodes `Json.Number(BigDecimal("1.5"))`, today error is `InvalidType(Number, Number)` — after split, should it be `InvalidType(Integer, Number)`? And should `JsonDecoder[BigDecimal]` accept both `Integer` and `Number`? The `narrow` vs `narrowWhole` split (`JsonDecoder.scala:198-211`) suggests `BigDecimal` accepts both, `Int` requires whole — confirm error type expectations for tests.
6. **Backwards compatibility posture:** Is a breaking change to `Json.Number` pattern matches acceptable, or must `Json.Integer` be added as a *subtype* of `Json.Number` (e.g. `sealed trait JsonNumberTag; case class Number extends JsonNumberTag; case class Integer extends JsonNumberTag`) so existing `case _: Json.Number =>` can be widened via a shared trait? The minimal non-breaking path is the `isWhole` branch without a new case class — confirm preferred trade-off.
7. **Schema `JsonAST` with integer:** Should `JsonSchema.jsonInteger` be added (parallel to `jsonNumber` at `JsonSchema.scala:53-59` giving `ASTSchema` with `Some(Integer)`), or is `JsonAST` generic enough to just be parameterized? And should `JsonSchemaEmitter.astSchema` for `Integer` emit `{"type":"integer","format":"int32"}` or plain `{"type":"integer"}`? Currently `numberSchema` adds format via `NumberFormat` — `astSchema` is bare type only.
8. **Compatibility semantics — integer widening:** Should `Compared` treat `integer → number` as non-breaking (widening) and `integer → integer` with different `NumberFormat` (e.g. `Int32 → Int64`) as compatible, while `number → integer` is breaking? This mirrors DB `Column` widening (`SmallInt→Int→BigInt` in `Column.scala`) but needs explicit confirmation for API review.

## Expanded Description

**What it likely means:** Create the initial, minimal viable prototype of the `oxygen-sockets` **client** — a type-safe, ZIO-based WebSocket client that complements the sibling **server prototype (OXY-131)** under Epic **OXY-130 `oxygen-sockets`**. Together they validate the approach for typed, bidirectional socket communication in the `oxygen` stack, analogous to how `oxygen-http` provides `DeriveEndpoints`/`DeriveClient` for request/response HTTP.

**Context — oxygen-sockets does not exist yet:** Verified by exhaustive search: `grep -r "oxygen-sockets|sockets|Socket|websocket|WebSocket"` across `modules/`, `docs/`, `build.sbt` returns zero hits outside `jira-issues/checklist.md` and the unrelated `java.net.Socket` usage in `modules/general/test-container/src/main/scala/oxygen/test/container/TestContainerService.scala:3,35-52` (a test-container readiness probe, not a WebSocket abstraction); `find . -iname "*socket*"` returns only that test-container file; `build.sbt:51-220` defines no `oxygen-sockets` module; `docs/docs/future-plans.md` is empty; `modules/http/zio` (`modules/http/zio/src/main/scala/oxygen/http/client/`, `modules/http/zio/.jvm/src/main/scala/oxygen/http/server/`) contains no WebSocket handling — `Client.scala` is HTTP `Request`/`Response` only (no `websocket` method), `Server.scala` is `ZServer.Config`/`NettyConfig` only. Sibling OXY-131 ("Create initial `oxygen-sockets` server prototype") is itself To Do/untriaged, so neither the wire protocol nor the module layout exists. Any description is therefore inferred from the two titles + the `oxygen-http`/`oxygen-events` patterns + domain knowledge of `zio-http` WebSockets, not from code.

**Domain interpretation — what "oxygen-sockets client prototype" means:**

In this repo, "sockets" in Scala/ZIO 2.x + `zio-http 3.7.4` idiom means **WebSockets** (RFC 6455) — full-duplex, long-lived connections where client and server exchange string/binary frames after an HTTP `Upgrade` handshake. The three plausible readings of "sockets" were considered:

1. **(Frontrunner) WebSockets over zio-http** — Typed WebSocket client built on `zio.http.Client.websocket`, `zio.http.WebSocket`, `WebSocketFrame` (text/binary/close/ping/pong), integrated with `oxygen-json`/`oxygen-schema` codecs for typed messages and with `ZIO Hub`/`Queue`/`Stream` for async send/receive. This fits the `oxygen-http` precedent (typed codecs, `DeriveClient` macro derivation) and the `oxygen-events` precedent (streaming `EventProcessor` style) and is the only reading that justifies a *new* `oxygen-sockets` module alongside `oxygen-http`.
2. **(Rejected) Raw TCP `java.net.Socket` wrapper** — A thin wrapper around `java.net.Socket`/`InetSocketAddress` like the test-container probe. Rejected because it would not merit an epic ("oxygen-sockets" as a product) — raw TCP is too low-level and has no codec/routing/type-safety story comparable to `oxygen-http` or `oxygen-events`. The epic would have been called `oxygen-tcp` if that were the intent.
3. **(Rejected) Socket.IO / STOMP-style higher-level protocol** — A framed pub/sub protocol on top of WebSockets. Rejected because the titles say "initial prototype" — a prototype would start at the WebSocket transport layer before layering a pub/sub protocol. Could become a follow-up, but not the initial prototype.

The frontrunner (1) is therefore: a **typed WebSocket client** that can `connect(url)` to a WebSocket endpoint, `send[A: JsonCodec](a: A)` typed messages, `receive[B: JsonCodec]: ZStream[Any, Throwable, B]` or `Hub`-based, handle `close`/`ping`/`pong`, and interoperate with the server prototype (OXY-131) for a round-trip demo. It is the **client mirror of OXY-131**, just as `oxygen-http-client` (OXY-3 In Progress, `modules/http/zio/src/main/scala/oxygen/http/client/Client.scala:5-64`) mirrors `oxygen-http-server` (OXY-2, `modules/http/zio/.jvm/src/main/scala/oxygen/http/server/Server.scala`).

Analogy to existing patterns:
- `oxygen-http`: `DeriveEndpoints[Api]` macro derives `Seq[EndpointSchema]` server-side; `DeriveClient[Api]` macro derives typed client methods (`DerivedClientEndpointImpl.scala`). `oxygen-sockets` would likely derive typed socket handlers from a trait like `trait MySockets { def chat: SocketEndpoint[In, Out] }`.
- `oxygen-events`: `Event[S,K,V]` + `EventProcessor` + `InMemory` vs `Pulsar` backends — streaming, async. Sockets prototype may borrow `Hub`/`Queue` patterns from there.
- `zio-http` itself: `zio.http.WebSocketApp`, `WebSocketChannelEvent`, `Channel`, `WebSocketFrame` — the prototype would wrap these in an oxygen-idiomatic layer (typed codecs, ZIO `Scope`-managed lifecycle).

**Who it affects:** Future users of `oxygen-sockets` who need real-time bidirectional communication — live UI updates (`oxygen-ui-web`/`oxygen-ui-electron`), collaborative editing, notifications, chat, streaming query results, or replacing polling over `oxygen-http`. Without a sockets client, consumers must drop to raw `zio.http.Client` WebSocket handling per service — untyped frames, manual JSON encode/decode, ad-hoc reconnect, no `oxygen-schema` integration.

**Why it matters (Priority Normal):** Normal (not High, not Lowest) suggests a foundational but not fire-fighting capability — analogous to OXY-129 (Normal, Slyce grammar) or OXY-131 (Normal, server prototype). Epic OXY-130 is `To Do` (not `In Progress`), so sockets is a planned future surface, not a current blocker. The prototype is the first slice to validate the module's existence, transport choice (`zio-http` WebSocket vs alternative), codec story, and client/server interop before investing in full features (rooms/channels, auth, backpressure, reconnection, JS target).

**Inferred acceptance criteria (minimal viable prototype):**

1. A new module or subproject exists (expected `modules/sockets` or `modules/general/sockets`, cross-compiled JVM/JS or JVM-only — see Required Changes for placement) with a `SocketClient` type that can `connect` to a `ws://`/`wss://` URL, send typed messages (at minimum `String`/`Json`, ideally `A: JsonCodec`), and receive messages as a `ZStream` or `Dequeue` — with lifecycle tied to `ZIO Scope` (auto-close on scope exit). Works against the server prototype (OXY-131) for an in-memory or loopback round-trip test (no external infra needed, mirroring `ViaHttpSpec`/`DirectSpec` for HTTP).
2. Codec integration: at least `String` and `Json`/ `JsonCodec`-typed send/receive; the prototype demonstrates one typed round-trip (e.g. `case class Echo(msg: String) derives JsonCodec` sent and received) without falling back to untyped `WebSocketFrame` at call sites.
3. `Scope`-managed lifecycle and `close` handling: `client.connect(url): ZIO[Scope, Throwable, SocketConnection]` (or similar) that releases the socket on scope close, and exposes `isClosed`/`awaitClose` or `Hub` termination.
4. No breaking change to `oxygen-http` — sockets is a new module/namespace (`oxygen.sockets.client`), not a mutation of `oxygen.http.client.Client`. If it temporarily lives inside `modules/http/zio` as `oxygen.http.socket`-like package, it is clearly marked prototype and does not alter `Client`/`Server` signatures.
5. Existing `oxygen-http` and `oxygen-events` tests continue to pass; no new dependency beyond `zio-http` (already `3.7.4`) and existing `oxygen-json`/`oxygen-schema` (for typed codecs). If JS is in scope, `Fetch`/`WebSocket` browser API is considered (see Open Questions).

## Open Questions
- **Module placement:** Should `oxygen-sockets` be a top-level `modules/sockets` sibling to `modules/events`/`modules/http` (like `oxygen-events` with `core`/`in-memory`/`pulsar` backends later) or `modules/general/sockets` as a single `CrossProject` (like `oxygen-json`, `oxygen-schema`) or an extension inside `modules/http/zio` (`oxygen.http.socket` package) until it matures? This determines `build.sbt` churn and `JSPlatform` support.
- **WebSocket vs raw TCP vs Socket.IO:** Does the prototype target plain RFC 6455 WebSockets (text/binary frames over `zio-http`) — the frontrunner — or raw `java.net.Socket` TCP, or a higher-level Socket.IO/STOMP pub/sub framing on top of WebSockets? The epic `oxygen-sockets` implies WebSockets, but confirmation avoids building the wrong transport.
- **Client API — manual `connect` vs macro-derived `DeriveSocketClient`:** Should the prototype expose `SocketClient.connect(url): ZIO[Scope,_,SocketConnection]` with manual `send`/`receive` (simpler, fits "prototype") or a trait-derived API like `trait MySockets { def chat: SocketEndpoint[In, Out] }` + `DeriveSocketClient` macro (more oxygen-idiomatic, mirrors `DeriveClient`) — or both (manual as core, derived as sugar)? Which `receive` shape: `ZStream`, `Hub`, `Queue`, or `Channel`?
- **Codec story:** Must the prototype reuse `oxygen-json`'s `JsonCodec[A]` (text frame `toJsonString`/`decode`), `oxygen-schema`'s `JsonSchema[A]` (with compiled schema support), or `PlainTextSchema` for header/path-like params? Can `In`/`Out` be arbitrary `A: JsonCodec` or must they be envelopes like `Event[String, K, V]` (borrowing from `oxygen-events`)? Does binary frame `Array[Byte]` + `JsonCodec` transcoding matter for this slice?
- **Authentication and headers:** How does the client authenticate the WebSocket upgrade? Reuse `oxygen-crypto`'s `BearerToken`/`BasicCredentials` via `Authorization` header (like `OidcClient.bearerMiddleware:173-178`), query param token, or `Sec-WebSocket-Protocol`? Should `SocketClientConfig` mirror `Client.Config`'s `headers`/`auth` story?
- **Platform scope — JVM-only or Cross (JS)?** Browser `WebSocket` (JS `WebSocket` global) vs `zio-http` JVM `WebSocket` have different APIs. Must the prototype compile for `JSPlatform` (browser client used by `oxygen-ui-web` at `example/apps/ui/src/main/scala/oxygen/example/ui/UIMain.scala`) or is JVM-only sufficient for the first slice? This decides `CrossProject` vs `.jvm` and whether `Fetch`/`WebSocket` polyfill is needed.
- **Lifecycle and reconnection:** Is `Scope`-finalized `close` sufficient for the prototype, or must the client support auto-reconnect with backoff, heartbeat `Ping`/`Pong` (like `zio-http` `WebSocketFrame.ping/pong`), and a `reconnect: ReconnectConfig(maxRetries, delay)` config? Deferring reconnection keeps the prototype small but should be explicit so it is not expected.
- **Dependency on OXY-131 and demo bar:** Can the client be prototyped standalone (against a public `wss://echo.websocket.org` or a local `zio-http` echo `WebSocketApp`) or must it interop with the server prototype OXY-131 in the same PR? What is OXY-131's timeline and what does its handler shape look like (e.g. `trait SocketServer { def handle(conn: SocketConnection): Task[Unit] }`)? What minimal demo (e.g. `example/apps/socket-demo`) proves client+server work together?

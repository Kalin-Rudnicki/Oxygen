## Expanded Description

**What it likely means:** Build the first shippable server side of a new `oxygen-sockets` module — a WebSocket layer for the Oxygen stack, parallel to `oxygen-http` (Epic OXY-2). The epic OXY-130 is the container for `oxygen-sockets`; OXY-131 (this issue) and OXY-132 (client prototype) split it into server and client halves. Priority Normal and the word "prototype" signal a minimal, demonstrable slice — enough to prove the approach and unblock the client (OXY-132) — not a production-hardened, fully typed bidirectional RPC framework.

**Most plausible interpretation (frontrunner):** A **typed WebSocket server prototype on top of zio-http's WebSocket support** (`zio.http.Channel`, `WebSocketChannelEvent`, `Handler.webSocket`), mirroring how `oxygen-http` turns annotated traits into HTTP routes. Concretely, the prototype would:

- Introduce a new module (e.g. `modules/sockets/zio` or `modules/http/sockets`) with a server trait annotation model such as:
  ```scala
  trait ChatSocket derives DeriveSocketServer {
    @socket("/chat")  def chat(in: Stream[Nothing, ChatMsg]): Stream[Nothing, ChatMsg] = ???
    // or @socket.route with @param.path / @param.query like oxygen-http
  }
  ```
  where the handler is bidirectional (`Stream` in + `Stream` out, or `Channel => Stream`), uses oxygen schemas (`JsonSchema`/`PlainTextSchema`) for codec, and is derived via macros in the same `oxygen.quoted` / `oxygen.meta` style as `DeriveEndpoints`.

- Alternatively (simpler prototype, also plausible): a **thin raw wrapper** around `zio.http.Handler.webSocket` / `Channel` that proves wiring — e.g. `SocketServer.serve(route: String)(handler: Channel => ZIO[Scope, Nothing, Unit])` + `SocketServer.layer` — with one echo demo and without macro derivation. The title's "prototype" and Normal priority make this thin-wrapper reading viable for the *initial* slice, with typed derivation deferred to a follow-up. Either satisfies "server prototype" but implies different scope.

- Wire into `Server` / `CompiledEndpoints` or as a sibling `SocketServer` layer: either `CompiledSocketEndpoints.toRoutes` or `SocketServer.install(socketRoutes)` alongside `Server.layer.serving`. zio-http WebSockets upgrade via `Routes` that include `Handler.webSocket` — oxygen's server will need to expose that.

- Provide an example (e.g. `example/apps/web-server` echo socket) and a single integration test (client connects, sends message, receives echo over WS upgrade).

**Why it matters:** `oxygen-http` SSE/LineStream covers server→client push but not bidirectional, low-latency, stateful channels (chat, collaborative editing, live cursors, terminal, gaming). OXY-133 Epic `oxygen-ui-rework` and `oxygen-ui` (Epic OXY-83 In Progress) likely consume sockets for real-time UI. Without a sockets prototype, real-time features must fall back to polling or SSE hacks. Priority Normal (not High) reflects that basic HTTP is In Progress (OXY-2/OXY-3) and sockets is a follow-on capability; it is not on the critical path for SQL/json/transform.

**Inferred acceptance criteria (minimal viable prototype):**

1. New module `oxygen-sockets` (or `oxygen-sockets-zio`) exists in `build.sbt` and compiles (JVM at minimum; JS client can be deferred to OXY-132). At least `modules/sockets/zio/src/main/scala/oxygen/sockets/server/SocketServer.scala` and a derivation helper (`DeriveSocketServer` or `SocketRouteRepr`) are present.
2. A server can expose at least one WebSocket endpoint (upgrade) that echoes or routes typed messages, built on `zio.http` WebSocket (`Handler.webSocket` / `Channel` / `ChannelEvent`) — verified by an integration test: start server via `SocketServer` (or `Server` extension), connect a zio-http `Client` WebSocket, send a JSON message, receive the expected response, close.
3. Codec is schema-driven (reuses `oxygen.json.JsonCodec` / `oxygen.schema.JsonSchema` or `PlainTextSchema`) — messages are encoded/decoded via `JsonCodec` rather than raw strings/bytes, at least for the demo type.
4. No break to existing `oxygen-http` server (`ViaHttpSpec`/`CompiledApiSpecSpec` still pass). If sockets reuses `Server.Config`/`Server.layer`, a fallback/either is documented.
5. Example app wiring shows how to start the socket server alongside the HTTP server (or as part of it) — e.g. `WebServerMain` registers a demo `ChatSocket` and the echo route is reachable at `ws://localhost:$port/chat`.
6. Doc stub exists (`docs/docs/sockets/index.md` or `agent-docs/sockets/prototype.md`) describing how to define a socket handler and how OXY-132 client will connect.

## Open Questions
- **Prototype scope — raw vs typed?** Should the initial slice be a thin `Handler.webSocket`/`Channel` wrapper (echo, `String` frames) or a macro-derived typed trait `trait ChatSocket derives DeriveSocketServer { @socket("/chat") def chat(in: Stream[ChatMsg]): Stream[ChatMsg] }` with `JsonSchema`-derived codecs? The former is a true prototype; the latter is closer to the long-term `oxygen-http`-style API but doubles the macro work.
- **Transport — zio-http WebSocket vs raw TCP?** Title says `oxygen-sockets` (plural, generic) — does the team mean WebSockets (HTTP upgrade via zio-http, browser-compatible) or raw `java.net.ServerSocket` / `java.nio` TCP sockets? zio-http WebSocket is almost certainly intended (the http module already depends on `zio.http`), but should be confirmed — it determines whether `SocketServer` uses `Handler.webSocket` or `java.net`.
- **Module path and sharing with `oxygen-http`:** Should sockets be `modules/sockets/zio` (new top-level `oxygen-sockets` module, new `oxygen-sockets-zio` artifact) or `modules/http/sockets` under the existing `oxygen-http` module? Should it depend on `oxygen-http` (reusing `Server.Config`, `ServerErrorConfig`, `ParamRepr`, `DerivedServerEndpointImpl` patterns) or be independent with its own `SocketServer.Config`?
- **Integration with HTTP server — same port or separate?** Must WS routes be served on the same port as HTTP (one `zio.http.Server` with mixed `Routes`) or can the prototype start a separate socket server on its own port? Same-port is more ergonomic (`ws://localhost:$port/chat` alongside `http://localhost:$port/api`) but requires `CompiledEndpoints`/`Server` changes; separate is simpler but leaves a follow-up.
- **Message codec, framing, and close semantics:** Are messages JSON text frames via `oxygen.json.JsonCodec` (recommended — reuse `oxygen-schema`), binary frames, or `PlainTextSchema`? Should the prototype handle `Ping`/`Pong`, `Close` with status codes, and malformed-message errors via a dedicated close frame or an error channel? Should backpressure be modeled via `Stream` or `Channel` directly?
- **Auth, query params, and headers on upgrade:** Should the WS upgrade request support `@param.query`/`@param.header`/`@param.path` (like `RouteRepr` does for HTTP) and auth (reuse `UserInfoService` / Bearer token), or can the prototype ignore them and handle auth inside the channel handler? Affects whether the prototype needs `ParamRepr` parsing.
- **Client contract for OXY-132:** What does OXY-132 (client prototype) expect the server to expose — a URL path, a typed trait, or a `SocketClient.connect(path): Stream` shape? Locking the server/client codec and trait shape together avoids a mismatch where the server prototype's demo cannot be consumed by the client prototype.
- **Platform and artifact naming:** `oxygen-http` is `oxygen-http-zio` (`oxygen.http`). Should the artifact be `oxygen-sockets-zio` / `oxygen.sockets` with the same `CrossProject(JSPlatform, JVMPlatform)` split (server JVM-only, client JVM+JS)? Should the package be `oxygen.sockets.server` mirroring `oxygen.http.server`?
- **Assumption to confirm:** That `oxygen-sockets` means WebSockets over zio-http (not raw TCP), that OXY-131 and OXY-132 are a server/client pair under Epic OXY-130 as inferred from `checklist.md` adjacency and naming, and that reusing `oxygen.json`/`oxygen.schema` codecs for message framing is desired. If any of these assumptions is wrong, the Required Changes file list above is mis-targeted.

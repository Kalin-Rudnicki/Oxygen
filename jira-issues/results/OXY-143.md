## Expanded Description

**What this likely is:** Create a reusable ZIO service (`ZLayer`-provided) that centralizes **config file lifecycle** — loading, merging, watching, validating, and persisting JSON/YAML config files — so application code (and `oxygen-executable`'s `@envConfig`) does not hand-roll `Path`/`FileSystem` + `JsonDecoder` + `YamlParser` + `ConfigLoader` logic in each service.

Today config file handling is fragmented and either private or one-shot:

1.  **`oxygen-executable` bootstraps config from an env var at startup only.** `modules/general/executable/src/main/scala/oxygen/executable/generic/ConfigLoader.scala:9-44` (`private[executable] object ConfigLoader`) resolves an `@envConfig("VAR", "fallback")` String via `Path.normalizedAbsolute(raw)` → `path.status` → `File`→ `readFileJson` (JSON or `YamlParser.parseJson` for `.yaml`/`.yml`) or `Directory`→ `mergeDirectoryJson` (`childStream` → `readOptFileJson` → `reduceLeft(_ ++ _)`). It is then decoded via `JsonDecoder` in `ExecutableParser.scala:308` and `ParserCodegen.scala:158-161`. This is `private`, effects-only at parse time, with no runtime API to re-read, write, list, or watch files, and no atomic-write or validation helper.

2.  **`Path` / `FileSystem` primitives already exist but are not composed into a config abstraction.** `modules/general/zio/src/main/scala/oxygen/zio/system/Path.scala` (trait `Path` with `read`, `write`, `append`, `createEmptyFile`, `children`/`childStream`, `recursiveFileStream`, `readDecodeJson`, `readDecodeString`, `toJavaFile`, `normalized` etc.) plus `FileSystem.scala` (`FiberRef[FileSystem]` with `.current`) give the FS layer. The building blocks for a config service — `Path.of`, `normalizedAbsolute`, `Type.File`/`Directory`/`DoesNotExist`, `extension` checks, `readDecodeJson`/`YamlParser` — are all present but not grouped.

3.  **Example apps show the config-file sprawl the service would replace.** `example/apps/web-server/src/main/scala/oxygen/example/webServer/WebServerMain.scala:36-48` defines `Config(Http, Token, DbConfig, MigrationConfig, LiveUIApi.Config, FileSystemResourceApi.Config, LiveStripeService.LiveOrUnimplementedConfig)` `derives JsonCodec` loaded via `def env(@envConfig("APP_CONFIG") config: Config)`. `example/apps/example-app/configs/dev/app.json` (`{"env":"dev"}`), `prod/app.json`, `prod/archive/legacy.json` (`{"env":"prod","tier":"archive"}`), plus `src/main/resources/task-config.json` (`{"action":"sync","priority":7}`) and `showcase-settings.json` (`{"theme":"midnight","retries":3}`) are the on-disk artifacts. `ShowcaseApp.scala:14-22` uses `@envConfig("SHOWCASE_SETTINGS") settings: Option[ShowcaseSettings]` and `@envConfig("TASK_CONFIG") task: TaskConfig`, showing the fallback-file / directory-merge pattern that today must be re-implemented with `ConfigLoader` semantics if done outside the CLI parser.

4.  **No existing "ConfigFileService" exists.** Grep for `ConfigService`, `ConfigFileService`, `managing config` in `modules/`, `example/`, `docs/`, `agent-docs/` finds no type or TODO — only `ConfigLoader`, `DbConfig`, `Server.Config`, `Client.Config`, `TestContainerConfig`, etc. The gap is verified: there is no public service for config file management.

Inferred intent: provide a typed, injectable service such as:

```scala
trait ConfigFileService {
  def load[A: JsonDecoder](path: String): IO[ConfigFileError, A]
  def loadOrDefault[A: JsonDecoder](path: String, default: A): IO[ConfigFileError, A]
  def save[A: JsonEncoder](path: String, value: A): IO[ConfigFileError, Unit] // atomic write
  def list(directory: String): IO[ConfigFileError, Chunk[Path]]
  def mergeDirectory[A: JsonDecoder](dir: String): IO[ConfigFileError, A] // JSON merge like ConfigLoader.mergeDirectoryJson
  def watch[A: JsonDecoder](path: String): Stream[ConfigFileError, A] // optional fs watch
  def exists(path: String): IO[ConfigFileError, Boolean]
}
object ConfigFileService {
  val live: ZLayer[FileSystem, Nothing, ConfigFileService] = ???
  // or: given JsonCodec derivation, YAML vs JSON handling, FileSystem.current wiring
}
```

with `ConfigFileError` mapping `FileSystemError` + `YamlParser` + `JsonDecoder` failures (similar to `MigrationError`/`TestContainerError` patterns), supporting both `.json` and `.yaml`/`.yml` as `ConfigLoader.readOptFileJson` already does, and reusing `FileSystem.current` so it is testable via `TestContainer`/`ZLayer` injection. The service would be the runtime counterpart to the CLI-time `ConfigLoader` — load at startup via `@envConfig`, then manage files during the app's lifetime (e.g., feature flags, per-workspace settings, or an admin `oxygen-http` endpoint to GET/PUT config).

**Who it affects:** Any service that stores configuration on disk beyond the initial `@envConfig` load — `WebServerMain` and similar `CliApp`s that today do one-shot `ConfigLoader` at parse time but have no runtime API to persist updated config, list `configs/` directories, or watch for changes without restarting. Also library consumers of `oxygen-zio`/`oxygen-executable` who currently copy-paste `Path.of` + `readDecodeJson` + `reduceLeft(_ ++ _)` logic.

**Why it matters (Priority Higher):** `Higher` (not `Low`/`Normal`) signals this is a precursor / building block, not polish. `oxygen-executable` Epic-adjacent work (`OXY-34` Clean up server configuration paradigm · Normal, `OXY-35` client · Normal, `OXY-79`/`OXY-80` HTTPS Lowest, `OXY-74`-`77` logging/metrics) all touch how `Config` is modeled and provided. A central config-file service unblocks those cleanups by giving them a single, testable place to define `JsonCodec` + path resolution + directory-merge + atomic-write + error model, rather than each feature adding ad-hoc `Path` code. `Higher` vs `Lower` (e.g., `OXY-94 on conflict`) indicates this is seen as blocking follow-on DX, not just an ergonomic addition.

**Inferred acceptance criteria:**

1.  A new service type (e.g., `oxygen.zio.config.ConfigFileService` or `oxygen.executable.ConfigService`) with `ZLayer` constructors (`live`, `liveWithFileSystem`, `test`) is available from the appropriate module (`modules/general/zio` is the natural owner because it already owns `Path`/`FileSystem`; `modules/general/executable` is the alternative if tightly coupled to `@envConfig`/`JsonDecoder`). At minimum it supports `load[A: JsonDecoder]` and `save[A: JsonEncoder]` for a single file path (JSON + YAML via `YamlParser`), `mergeDirectory` for a directory of `*.json`/`*.yaml` files (same `reduceLeft(_ ++ _)` merge as `ConfigLoader.mergeDirectoryJson:42`), and `list`/`exists`/`delete` passthroughs.
2.  Errors are typed (`ConfigFileError` ADT wrapping `FileSystemError.PathDoesNotExist`, `FileSystemError.UnableToDecodeFileContents`, `YamlParser` parse error, `JsonDecoder` failure — all via `safeGetMessage` like `ConfigLoader.loadDecoded:14`), not raw `Throwable`/`String`.
3.  Atomic write semantics for `save` (write to temp file then `moveTo`/`copyTo`, or `Path.write` with `createEmptyFile` guard) and optional `createDirectories` handling, reusing `Path` API (`createDirectories`, `write`, `moveTo`).
4.  Respects `FileSystem.current` (`FiberRef[FileSystem]`) so tests can swap in an in-memory FS (consistent with `TestContainerService` pattern and `Database.layer` testability). A test layer or in-memory `FileSystem` stub is provided or documented.
5.  Supports both JSON and YAML file extensions (`.json`, `.yaml`, `.yml`) via `fileName.extension` match as `ConfigLoader.readOptFileJson:28-33` does, with `ZIO.none` for non-config extensions and an error for no valid files in a directory.
6.  Integrates with `oxygen-executable`: an `@envConfig` value can be round-tripped through the service (e.g., `service.load[WebServerMain.Config](path)` decodes the same `JsonCodec` that `@envConfig("APP_CONFIG")` uses), and docs note when to use `@envConfig` (startup) vs the runtime service (dynamic config).
7.  Tests + docs: unit tests for load/save round-trip, directory merge (`children.reduceLeft(_ ++ _)`), missing path → typed error, invalid extension → error, YAML handling, atomic-write; integration test via `example` or `modules/general/zio` test; a brief `docs/docs/executable/` or `docs/docs/zio/` note (or `agent-docs/`) describing the service, its `ZLayer`, error model, and relationship to `ConfigLoader`/`@envConfig`.

## Open Questions

1. **Owning module — where should the service live?** `modules/general/zio` (owns `Path`/`FileSystem`/`FileSystemError`) is the natural home for a FS-backed service, keeping `oxygen-executable`'s CLI-time `ConfigLoader` private but shareable via a shared util. Alternatively, `modules/general/executable` makes sense if the service is viewed as "the runtime companion to `@envConfig`" and needs direct access to `ConfigLoader`'s `JsonDecoder` wiring. A third option is a new `modules/general/config` cross-project — but no checklist epic proposes it. Which dependency direction is desired? This determines the service's package (`oxygen.zio.config` vs `oxygen.executable.config`) and its `ZLayer` signature (`ZLayer[FileSystem, _, _]` vs `ZLayer[Any, _, _]`).

2. **Read-only vs read+write — is `save` in scope?** "Managing config files" could mean read+merge+watch (load-time management, like `@envConfig`'s directory merge) or full CRUD including persisting updated config back to disk (atomic `save`, `delete`, `createDirectories`). If write is in scope, what atomicity guarantee is required (temp-file + `moveTo` vs simple `Path.write`)? If read-only, the service is essentially a typed, injectable `ConfigLoader` and `save` is follow-up.

## Expanded Description

**What this likely is:** Extend the `oxygen-meta` (`oxygen.meta.k0`) derivation kernel so that `derives` / `Derivable.derived` works for **generic sealed sum types** — i.e. `sealed trait` / `sealed abstract class` / `enum` parents that carry one or more type parameters, where each case forwards those params or erases to `Nothing`. Canonical motivating example (already present as a fixture in `modules/tests/pre-test-unit-tests/src/test/scala/oxygen/json/JsonSpec.scala:82-86`):

```scala
sealed trait GenericSum1[+A] derives JsonCodec
object GenericSum1 {
  final case class WithA[+A](int: Int, string: Option[String], generic: A) extends GenericSum1[A]
  final case class WithoutA(x: Int) extends GenericSum1[Nothing]
}
```

Today `sealed trait Foo derives JsonCodec` (non-generic) and `final case class Bar[A](...) derives JsonCodec` (generic product) both derive fine via `Generic.of[A]` → `ProductGeneric` / `SumGeneric`. But `sealed trait Foo[A] derives JsonCodec` historically hit a deliberate de-scope in `SumGeneric.unsafeOf` — the comment in `JsonSpec.scala:80` still reads *"Currently de-scoped in SumGeneric.unsafeOf ('Type params on sum types is not yet supported')"* — because `SumGeneric` had no logic to resolve a child's applied type args from its `extends Parent[...]` clause.

**What the commit already did (verified in HEAD):** `f88bbbd4 support type params on SumGeneric (raw A or Nothing in extends)` (2026-08-06, included in `origin/main` and this worktree's `HEAD ec0cc73d`) implements the minimal useful subset:

- `SumGeneric.unsafeOf` now extracts `rootAppliedArgs` from the parent's `AppliedType`, and for each child calls `resolveChildAppliedArgs(childSym, parentSym, parentArgs)` (`modules/general/core/src/main/scala/oxygen/meta/k0/SumGeneric.scala:159-288`).
- `resolveChildAppliedArgs` supports exactly two `extends` arg shapes (documented at `SumGeneric.scala:152-158`): (1) **raw forwarding** of the child's own type param (`extends Parent[A]` where `A` is the child's `A`), and (2) **`Nothing`** (`extends Parent[Nothing]` for non-generic cases). Any other arg (e.g. `extends Parent[Option[A]]`, `extends Parent[String]`, bounds) aborts with `report.errorAndAbort("Type params on sum types only support forwarding raw type params or Nothing in extends; ...")`.
- Child generics are then materialized via `childGenericsRec` with the resolved `appliedArgs` and `appliedTypeRepr(sym, appliedArgs)` (`SumGeneric.scala:290-340`), so `ProductGeneric.unsafeOf` sees the correctly-applied `TypeRepr` for each case (e.g. `WithA[String]` when deriving `GenericSum1[String]`).
- Test coverage was added alongside: `GenericSum1` fixture + 4 `directRoundTripTest` cases in `JsonSpec.scala:238-247` covering `GenericSum1[String]` (`WithA` with/without `Option`, `WithoutA`, and `GenericSum1[Product1]` with nested product as `A`).

**What remains in scope vs. intentionally out of scope:** The commit message explicitly says *"Remove the deliberate de-scope for generic sealed sums. Child type args are resolved from the parent application when cases forward raw type params or use Nothing (e.g. GenericSum1[A] / WithoutA)."* The raw-or-Nothing rule is therefore the **intended v1 contract** for OXY-119, not a partial fix. More general `extends` shapes (applied types like `Parent[Option[A]]`, concrete instantiations like `Parent[Int]`, multiple interacting params like `Parent[A, B]` with `case class Foo[A](...) extends Parent[A, String]`, or variance/bounds re-mapping) are not implied by the title's minimal wording and have no code signal or sibling issue pointing at them — they would be follow-ups if needed.

**Downstream typeclass surface that benefits (verified by `grep -r extends Derivable`):** Every `Derivable[F]` whose `sumDeriver` is `withInstances` (i.e. generic-sum-capable) automatically inherits generic-sum support once `SumGeneric` does, with no per-typeclass change:

- `oxygen.json.JsonDecoder` / `JsonEncoder` (and thus `JsonCodec`) — `DeriveSumJsonEncoder` / `DeriveSumJsonDecoder` (`modules/general/json/.../generic/DeriveSum*.scala`) — verified working via `GenericSum1` JSON round-trips.
- `oxygen.schema.JsonSchema` — `Derivable.SumDeriver.withInstances` (`modules/general/schema/src/main/scala/oxygen/schema/JsonSchema.scala:610-612`).
- `oxygen.meta.FromExprT` / `ToExprT` — `Derivable` sum derivers (`modules/general/core/src/main/scala/oxygen/meta/FromExprT.scala:203-211`, `ToExprT.scala:192-199`).
- `oxygen.core.TypeTag` (via `DeriveTypeTag` — separate path, but benefits from correct `TypeRepr` application).

Conversely, `oxygen-sql` typeclasses (`Columns`, `ResultDecoder`, `RowRepr.ProductRepr`, `InputEncoder` in `modules/sql/core/src/main/scala/oxygen/sql/schema/*`) explicitly use `Derivable.SumDeriver.notSupported` (`*.scala:30-31, 155-156, 158-159, 153-154`) — they intentionally do not derive sum types at all (SQL rows are products), so OXY-119 does not touch them; no change needed.

**Who it affects:** Any module that models `sealed trait Result[+A]` / `sealed trait Eff[A]` / `sealed trait Page[Env]` with a type param and wants `derives JsonCodec` / `derives JsonSchema` / `derives TypeTag` without hand-writing encoders/decoders per instantiation. `modules/ui/web/Page[-Env]`, `PWidget[-Env, +Action, -StateGet, +StateSet, ...]`-adjacent sealed hierarchies, and domain `sealed trait` wrappers around effect types are representative consumers; today they must either erase the param, duplicate codecs per concrete `A`, or avoid `derives` entirely.

**Why it matters (Higher priority):** Without this, the `oxygen-meta` kernel has an asymmetric gap: generic products already work (`ProductGeneric` correctly substitutes `typeArgs` via `substituteTypes` at `ProductGeneric.scala:408-416`), but generic sums do not, so the most common Scala pattern for typed result hierarchies (`sealed trait Outcome[A] { case Success[A](value: A); case Failure(msg: String) }`) cannot use the one-line `derives` that non-generic sums can. `Higher` (vs `Normal` for OXY-120/OXY-121) suggests this was blocking `oxygen-json`/`oxygen-schema` adoption for generic domain models and was deliberately prioritized above the neighbouring `oxygen-meta` tasks.

**Inferred acceptance criteria:**

1. `sealed trait GenericFoo[A] derives JsonCodec` (and the same via `derives JsonSchema`, `derives ToExprT`/`FromExprT`) compiles and round-trips for at least: `A = String`, `A = Int`, `A = Product1` (nested product), and `A = Nothing` leg (`WithoutA`) — i.e. the 4 existing `JsonSpec.GenericSum1` assertions continue to pass (`directRoundTripTest[GenericSum1[String]]` / `GenericSum1[Product1]`).
2. Both `extends GenericFoo[A]` (raw forwarding) and `extends GenericFoo[Nothing]` (erased leg) are supported; any other `extends` arg shape fails with a clear `report.errorAndAbort` mentioning "raw type params or Nothing" (verified by reading `resolveChildAppliedArgs` error paths at `SumGeneric.scala:270-283`).
3. Multi-param parents (`sealed trait Foo[A, B]`) follow the same rule per-param (verified by code: `parentArgs: List[TypeRepr]` + per-name `mapping` at `SumGeneric.scala:252-287` iterates over all args, so `case class Bar[A, B](...) extends Foo[A, B]` and mixed `extends Foo[A, Nothing]` both satisfy the contract — no extra code change).
4. Non-generic sum derivation (`sealed trait Foo derives JsonCodec` with object/case-object/case-class children, `NestedGeneric` vs `FlatGeneric` vs `EnumGeneric` discrimination, `UnrollStrategy` handling) is unchanged — no regression in existing `Sum3`, `NestedSums`, `FormResult`, `ColorTransform`, etc.
5. Stale de-scope comment in `JsonSpec.scala:80` is updated or removed to reflect that generic sums are now supported (docs hygiene, not functional).

## Open Questions

- Is the raw-or-Nothing `extends` rule (`extends Parent[A]` or `extends Parent[Nothing]`, nothing else) the **complete** intended scope for OXY-119, or is a follow-up desired for richer `extends` args such as `extends Parent[Option[A]]`, `extends Parent[List[A]]`, or `extends Parent[String]` (concrete instantiation)? Recommendation: treat raw-or-Nothing as v1 (shipped in `f88bbbd4`); file a separate follow-up if richer shapes are needed — they require `TypeRepr` substitution beyond simple forwarding and would be a distinct story.
- Should multi-param parents (`sealed trait Foo[A, B]`) be explicitly covered by an additional test fixture (`GenericSum2[A, B]`) to lock the `List[TypeRepr]` path, or is the single-param `GenericSum1[A]` sufficient for acceptance? Recommendation: add `GenericSum2[A, B]` with 1–2 round-trips as low-cost regression coverage; code already handles it.
- Should the stale de-scope comment at `JsonSpec.scala:80` be updated in the same PR as the checklist flip, or is the checklist flip alone sufficient to close the Jira? Recommendation: update the comment in the same one-line commit — it is the only remaining code hygiene.

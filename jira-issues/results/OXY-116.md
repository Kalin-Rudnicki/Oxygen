## Expanded Description

**What this likely is:** Replace the stub `notHandled` client error handlers for the framework's **provided (built-in) response/error models** with real `ClientErrorHandler[E]` implementations that correctly surface failures to callers instead of `Die`-ing the fiber.

Today `modules/http/zio/src/main/scala/oxygen/http/client/ClientErrorHandler.scala:39-72` defines the `trait ClientErrorHandler[E] extends Cause.Folder` with two methods to implement: `wrapDeath(error: Throwable, trace: StackTrace): Option[E]` (for defects/fiber deaths) and `wrapDecodingFailure(error: ResponseDecodingFailure): Option[E]` (for error-response decode failures). It then provides givens:

- Real / functional: `throwable`, `httpDecodingFailure`, `requestDecodingFailure`, `responseDecodingFailure` via `throwableSubtype` (unwrap via `TypeTest`), and `string` (`wrapDecodingFailure → error.safeGetMessage.some`, `wrapDeath → None`).
- Stub: `nothing`, `RawResponse`, `RawResponseText`, `RawErrorResponse`, `RawErrorResponseText` all = `notHandled` (`wrapDeath → None`, `wrapDecodingFailure → None`) at `ClientErrorHandler.scala:65-70`.

`notHandled` means `DerivedClientEndpointImpl.scala:126-144` `convertErrors` falls through to `Cause.Die(t, trace)` — any defect or decode failure when `E` is one of those `Raw*` types is an unhandled defect (fiber failure), not a typed `E` value the caller can `catch`/`mapError`. This forces every call site that uses a `Raw*` error model (convenient for proxy/mirror endpoints that want raw status+headers+body) to either avoid typed errors or handle defects manually, defeating the purpose of the provided model.

Sibling `modules/http/zio/.jvm/src/main/scala/oxygen/http/server/ServerErrorHandler.scala:13-46` has the same pattern for server side with identical `notHandled` stubs for `RawResponse`, `RawResponseText`, `RawErrorResponse`, `RawErrorResponseText`, plus `string`/`throwable` also `notHandled` (asymmetry with client, see Open Questions). OXY-117 is the server mirror; OXY-116 is the client mirror.

A minimal "real" `ClientErrorHandler[Raw*]` should:

1. **`wrapDeath`**: synthesize an `E` from the `Throwable`+`StackTrace` instead of returning `None`. For `RawResponseText`/`RawErrorResponseText` this is tractable: `RawErrorResponseText(Status.InternalServerError, Headers.empty, error.safeGetMessage, MediaType.text.plain.some)` (or `Status.fromInt` mapping if the throwable carries a status). For `RawResponse` (which holds `zio.http.Body`) it must create a `Body` from the message (`Body.fromString(...)`) and choose a status (typically `500 InternalServerError`, or `Status.NotExtended` as sentinel). The handler must decide status/headers/content-type for the synthetic response.
2. **`wrapDecodingFailure`**: wrap `ResponseDecodingFailure` (`ResponseDecodingFailure.scala:129-151` — `sources: List[Source]` + `cause: DecodingFailureCause`) into `E` instead of `None`. For `RawResponseText`, `Status.BadGateway` or `500` with `body = error.show` (or `error.cause.toString`) is the obvious mapping. The same `Body` vs `String` construction choice applies.
3. Possibly also provide handlers for additional "provided" models that currently lack a `ClientErrorHandler` entirely: `ServerErrors` (the default error envelope `modules/http/zio/src/main/scala/oxygen/http/model/ServerErrors.scala`), `RawSuccessResponse`/`RawSuccessResponseText` (currently no given at all — would also be `notHandled` implicitly via macro fallback `clientErrorHandlerExpr` failure), `Redirect`, `PageHtmlResponse`, `ContentWithType`/`ByteContentWithType`. The macro in `modules/http/zio/src/main/scala/oxygen/http/client/generic/EndpointRepr.scala:65-66` requires an implicit `ClientErrorHandler[E]` for `route.ErrorOut`; today it would `fail` compilation if `E` is e.g. `ServerErrors` or `Redirect` unless a handler is in scope. Providing them makes `ErrorOut = ServerErrors` endpoints compile without a custom handler.

**Who it affects:** Any endpoint that uses a provided model as its `ErrorOut` type (proxy/mirror, docs passthrough, error-forwarder, UI page that wants raw body). Also any endpoint using `String`, `Throwable`, or `ServerErrors` as error output that wants decode/die translated to a value instead of a defect. The `it-test` fixtures `ViaHttpSpec`, `DirectSpec`, `UserApi` today define custom `given ClientErrorHandler[ApiError]` (that only handles `ResponseDecodingFailure` → `DecodingFailure`, leaving `wrapDeath = None`) and `given ClientErrorHandler[RegistrationError]/UIApiError = notHandled` — those patterns would benefit from reference handlers for primitive error types; the provided-model handlers establish the canonical shape.

**Why it matters (Priority Higher):** `Higher` (vs `Low` for `OXY-112 Basic auth`) signals this is not polish — the current `notHandled` stubs mean real user code that picks a provided model hits unhandled defects at runtime, breaking the typed-error contract `DerivedClientEndpointImpl:43 handleResponse(...) convertErrors(clientErrorHandler)` is supposed to provide. The server counterpart OXY-117 being `Higher` as well indicates both sides of the error mapping are considered blockers for dogfooding `Raw*` / `ServerErrors` in production handlers.

**Inferred acceptance criteria:**

1. `modules/http/zio/src/main/scala/oxygen/http/client/ClientErrorHandler.scala` no longer delegates the `Raw*` givens to `notHandled`; each has a real `new ClientErrorHandler[E] { def wrapDeath ...; def wrapDecodingFailure ... }` that returns `Some(E)` for the expected failure modes (at minimum `wrapDecodingFailure` → `Some(...)` with the failure message; `wrapDeath` either `Some(...)` or documented `None` if `Raw*` should not synthesize on defects — but then it is not "real").
2. Handlers preserve existing givens (`throwable`, `httpDecodingFailure`, `responseDecodingFailure`, `string`, `nothing`) without regression; new handlers for previously uncovered provided models (`ServerErrors`, `RawSuccessResponse*`, `Redirect`, `PageHtmlResponse`, `ContentWithType` family) are added only if the issue expects them (see Open Questions) — at minimum the four `Raw*` stubs are replaced.
3. `Compiles`: an endpoint `trait FooApi { def foo(): ZIO[Any, RawErrorResponseText, String] }` (or `ErrorOut = ServerErrors`) compiles via `DeriveClient` without a manual `given ClientErrorHandler` in scope (verified by `EndpointRepr.clientErrorHandlerExpr` finding the new given).
4. `Tests`: `http/it-test` or `http/zio/src/test` unit tests covering: (a) `RawErrorResponseText` handler maps `ResponseDecodingFailure` to an error value with status `500`/`502` and body containing `error.show`, (b) `wrapDeath(new RuntimeException("boom"))` → `Some(RawErrorResponseText(...))` with `safeGetMessage` preserved, (c) `ViaHttpSpec`-style integration where a server returns `500` with plain-text error and the typed client with `ErrorOut = RawErrorResponseText` receives a typed failure (not a defect), plus regression that `ClientErrorHandler[String]` still maps only `ResponseDecodingFailure` and not deaths.
5. `OXY-117` server side is NOT in scope — do not change `ServerErrorHandler.scala` in the same PR (leave it for OXY-117), but keep the designs symmetric.

## Confidence
- **Rating:** 4 / 6 — good evidence, one clear frontrunner
- **Justification:**
  - `ClientErrorHandler.scala:67-70` `notHandled` for `RawResponse`/`RawResponseText`/`RawErrorResponse`/`RawErrorResponseText` is a verified code gap and the only `notHandled` cluster in that file; the title `Add real client error handlers for provided models` maps 1:1 to replacing those stubs with handlers that implement `wrapDeath` + `wrapDecodingFailure`. Sibling `ServerErrorHandler.scala:42-45` has identical stubs and sibling issue OXY-117 with identical wording confirms the pattern is intentional, not coincidental.
  - The pre-existing real handlers (`throwableSubtype`, `string` wrapping `ResponseDecodingFailure.safeGetMessage`) are the exact template a `Raw*` handler would copy, and `DerivedClientEndpointImpl:126-144` shows how `wrapDeath`/`wrapDecodingFailure` are consumed (`Cause.Folder` → `convertErrors` + `handleResponse`). Priority `Higher` aligns with the defect-vs-typed-error semantics being load-bearing.
  - Downgraded from 5/6 because (a) exact membership of "provided models" is ambiguous — strictly the four `Raw*` with `notHandled`, vs. broader set (`ServerErrors`, `Redirect`, `PageHtmlResponse`, `ContentWithType`, `RawSuccessResponse*` which currently have no implicit at all) inferred from `modules/http/model/` contents; (b) the synthesized `Raw*` status/headers/body mapping is not specified anywhere — synthesizing `500` vs `502` vs preserving `ResponseDecodingFailure`'s would-be status requires a product choice; (c) no Jira body or `TODO` mentions `provided models`, so full scope (whether to also add `ClientErrorHandler[ServerErrors]` etc.) remains inferred.

## Open Questions

1. **Membership of "provided models" — four `Raw*` or broader?** Strict reading = the four `Raw*` that currently have `given ... = notHandled` at `ClientErrorHandler.scala:67-70`. Broader reading = all `modules/http/model/` types that have a `ResponseCodec` and could plausibly be `ErrorOut`: `ServerErrors`, `RawSuccessResponse`/`RawSuccessResponseText`, `Redirect`, `PageHtmlResponse`, `ContentWithType`/`ByteContentWithType`. Should this task add handlers for `ServerErrors` (most useful — typed `ServerErrors` error envelope for clients that want structured server errors) and possibly `Redirect`/`PageHtmlResponse`, or strictly the four `Raw*`? No explicit epic link helps narrow — OXY-3 `oxygen-http-client` hints broader is plausible.

2. **Synthetic status for `wrapDeath` / `wrapDecodingFailure`:** What `Status` should a synthesized `RawResponse` carry? `Status.InternalServerError (500)` for both cases is simplest and matches `ServerErrorConfig.exposeInternalErrors` semantics (`ServerErrors.fromCause` defaults to including traces on failure). Alternatives: `502 BadGateway` for `ResponseDecodingFailure` (upstream decode failure) vs `500` for `Throwable` death. Should headers include `Content-Type: text/plain`?

3. **`wrapDeath` vs `None` for `Raw*`?** Should `wrapDeath` return `Some(Raw*)` (defects become typed `ErrorOut`) or `None` (defects remain `Die`, only `ResponseDecodingFailure` becomes typed)? `throwable` handler uses `throwableSubtype` (only unwraps if `E` is `Throwable`), while `string` returns `None` for `wrapDeath`. For `Raw*`, the "real" expectation is likely `Some` for both (proxy wants to forward defects as responses), but confirming avoids changing the failure semantics unexpectedly.

4. **`RawSuccessResponse*` in scope?** `RawSuccessResponse`/`RawSuccessResponseText` (`ExpectedStatuses.StatusRange.Success`) have no `given ClientErrorHandler` today — should they remain absent (success-range cannot naturally represent an error) or get a handler that synthesizes `200 OK` with error body (odd)? Recommend leaving absent.

5. **Server-side overlap / asymmetry:** `ClientErrorHandler.string` maps `ResponseDecodingFailure` to `safeGetMessage`, but `ServerErrorHandler.string = notHandled` and `ServerErrorHandler.throwable = notHandled` (vs client `throwable = throwableSubtype`). Should client `String`/`Throwable` semantics be mirrored on server for "provided models," or is the server intentionally `notHandled` for those (deferred to OXY-117)? This task should not change server handlers, but confirming the asymmetry is intentional helps keep CL symmetry clean.

6. **Body construction — `Body.fromString` vs `ReadOnlyCachedHttpBody`?** `RawResponse.body` is `zio.http.Body` (streaming) at `rawResponse.scala:11`; constructing `Body.fromString(t.safeGetMessage)` is straightforward in tests but in production the synthesized body should probably be `Body.fromString(show)` with `MediaType.text.plain`. Confirm this satisfies callers that later do `body.asString` (`RawResponseText` vs `RawResponse` distinction).

7. **Assumption to confirm:** That "provided models" means `modules/http/zio/src/main/scala/oxygen/http/model/` framework models (`Raw*`, possibly `ServerErrors`/`Redirect`/`PageHtmlResponse`) and not `modules/api-models` example models (`ApiError`, `LoginError`, `RegistrationError`, `UIApiError` — whose client handlers are `notHandled` or `wrapDeath=None` in `example/apps`/`modules/api-models/src/main/scala/oxygen/example/api/model/error/`). The `Raw*` reading is strongly supported by the `notHandled` cluster, but a human confirm of the intended model list closes the loop.

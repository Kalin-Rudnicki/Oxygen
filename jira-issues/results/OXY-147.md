## Expanded Description

**What this likely is:** Add a first-class "omit from JSON" capability to `oxygen-json` that mirrors the existing `Secret` pattern, but for **suppression** rather than **redaction**.

Today `oxygen-json` has three conditional-omission wrappers whose encoders gate `addToObject`:

- `Option[A]` (`JsonEncoder.OptionEncoder`) — `addToObject = value.nonEmpty` — field omitted when `None` (covers both `null` on the wire and missing-key on decode via `OptionDecoder.onMissingFromObject = Some(None)`).
- `Specified[A]` (`SpecifiedEncoder`) — `addToObject = value.toOption.nonEmpty` — field omitted when `WasNotSpecified` (PATCH three-state: `{}` vs `{"f": null}` vs `{"f": val}`).
- `Nullable[A]` — no omission (`addToObject` is always `true` in current `NullableEncoder` — verified, it has no override), so `null` is always emitted; field is still optional on decode? Actually `NullableDecoder` has no `onMissingFromObject` override so missing = error, making it "required-but-nullable".

There is **no unconditional-omit mechanism**. If a model has a transient/internal field that must never appear on the wire (e.g., derived cache, internal ID, `passwordConfirmation`, `transientState`), the current workarounds are: (a) custom `JsonEncoder`/`JsonCodec` hand-written for the whole product, (b) separate DTO without the field, or (c) filtering the `Json.Obj` post-encode via `mapJsonOutput`. None composes with `derives JsonEncoder`.

This task adds both halves of the Secret pattern for omission:

1. **`JsonEncoder.Omit[A]` typeclass (and `OmitValue[A]` / `Omit[A]` wrapper, by analogy with `SecretValue[A]`):**
   - `JsonEncoder.Omit[A]` / `JsonEncoder.Secret`-style sub-trait with `addToObject = false` unconditionally (or `encodeJsonAST` never called because derivation skips it). Parallels `JsonEncoder.Secret[A]` (`JsonEncoder.scala:329-374`) and `SecretValue.scala:3-5` (`given [A: JsonEncoder] => JsonEncoder[SecretValue[A]] = enc.secret`).
   - Lets a field be typed as `Omit[String]` / `OmitValue[Foo]` so the *type itself* carries omit semantics, usable without annotation.

2. **`@jsonOmit` annotation (`oxygen.json.jsonOmit`):**
   - `final case class jsonOmit() extends Annotation derives ToExprT, FromExprT` in `annotations.scala:20` alongside `jsonSecret`, `jsonField`, `jsonFlatten`, etc.
   - Lets an ordinary field be omitted without changing its Scala type: `case class User(name: String, internalCache: Map[String,String] @jsonOmit) derives JsonEncoder`.

**Derivation integration (mirrors `jsonSecret`):**

- `JsonEncoder.productDeriver` (`JsonEncoder.scala:380-397`) currently caches `JsonEncoder[b]` per field and switches to `.secret` when `@jsonSecret` is present (`field.annotations.optionalOf[jsonSecret].isEmpty` check). The omit analogue would either (a) wrap with `.omit` / replace encoder with an `OmitEncoder`, or — simpler and more efficient — be detected earlier in `DeriveProductJsonEncoder.makeEncodeObjectFields` / `makeEncodeSplitObjectFields` (`DeriveProductJsonEncoder.scala:14-70`) where the `addToObject` guard already exists (`if $instanceExpr.addToObject($fieldExpr) then ...`). For `@jsonOmit` the field would be compiled to `Growable.empty` unconditionally, or the `addToObject` guard would short-circuit.
- Decoder side: an omitted field must tolerate missing-key on decode. For a wrapper type `Omit[A]`, `JsonDecoder[Omit[A]]` would provide `onMissingFromObject` (similar to `Specified.WasNotSpecified.some` / `Option.None.some`) so `DeriveProductJsonDecoder.makeDecodeJsonAST` (`DeriveProductJsonDecoder.scala:33-50`) does not raise `MissingRequired`. For an annotated plain field `foo: String @jsonOmit`, the decoder needs a default — either `withDefault` or `onMissing` semantics — otherwise decoding JSON that never contains the key would fail. The design must decide whether `@jsonOmit` fields are expected to round-trip (decode ignores incoming key if present, or treats missing as default/zero) or are decode-ignored entirely.

**Who it affects:** Anyone deriving `JsonEncoder`/`JsonCodec`/`JsonDecoder` for case classes that contain internal/transient fields, plus downstream consumers of emitted JSON (docs/OpenAPI via `oxygen-schema`, MCP, `oxygen-http`).

**Why it matters (Priority Normal):** Normal (not High) signals hygiene/completeness — not blocking like OXY-70 schema differentiation (High) but analogous to `jsonSecret` which shipped as a small additive feature. Without it, teams leak internal fields or duplicate DTOs; with it, a one-line annotation solves the problem and the typeclass variant covers generic wrappers.

## Open Questions
- Is `Omit` intended as **unconditional** omit (always `addToObject=false`) or **conditional/predicate** omit (e.g., omit when `Option` is `None`, or when a predicate holds)? The title "annotation omit" (truncated) suggests unconditional, but a predicate form like `@jsonOmitWhen(_.isEmpty)` is a plausible extension not mentioned.
- What should `JsonDecoder` do for a field annotated `@jsonOmit` on a plain `A` (e.g., `internalId: String @jsonOmit`)? Should derivation require a Scala default value (`= ""` / `= Map.empty`), require the type be `Option`/`Specified`/`OmitValue`, or provide an `Omit`-specific default via `withDefault`? The `Secret` precedent has no decoder counterpart, so this is a new decision.
- Should a JSON payload that **does** contain the omitted key be (a) silently ignored on decode, (b) decoded into the field, or (c) rejected? Silent ignore is most common for omit (forward-compat), but security-sensitive omits might prefer rejection.
- Naming: title says `JsonEncoder.Omit` typeclass — is the intended wrapper type `JsonEncoder.Omit[A]` (nested trait), `OmitValue[A]` (like `SecretValue[A]`), `Omit[A]` (top-level opaque), or `JsonOmit[A]`? Follow `SecretValue` precedent vs nested `JsonEncoder.Secret` — alignment affects `oxygen.predef.json` exports and `JsonCodec` givens.
- Should `oxygen-schema` hide `@jsonOmit` fields from emitted JSON Schema / OpenAPI / `FullCompiledSchemas` (`properties`/`required`), or should schema still describe them? Hiding is intuitive (the wire never has the field), but it creates a schema/codec divergence if decoders still accept the key.
- How does `Omit` compose with `Secret` (`@jsonSecret @jsonOmit`), `Option`/`Specified`/`Nullable`, and `jsonFlatten`? Assume `omit` wins (field contributes `Growable.empty` regardless of other modifiers), but should the compiler warn/error on `@jsonOmit @jsonFlatten` or `@jsonOmit @jsonSecret`?
- Is the trailing "omit" in "`@jsonOmit` annotation omit" a truncation of a longer phrase (e.g., "omit on encode only", "omit from docs", "omit unless ...") that would narrow scope? Fetching the Jira body (`https://kr-oxygen.atlassian.net/browse/OXY-147`) would resolve this directly.
- Does `JsonCodec` need an `Omit` given (like `option`/`nullable`/`specified` in `JsonCodec.scala:66-68`), or is `Omit` encoder-only with decoder provided separately? If round-tripping is desired, a `JsonCodec[OmitValue[A]]` given is expected.

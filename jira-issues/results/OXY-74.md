## Expanded Description

**What this likely is:** Add structured, configurable request/response (and lifecycle) logging to the `oxygen-http-server` (`modules/http/zio/.jvm/src/main/scala/oxygen/http/server/` — Epic OXY-2 In Progress). The title is 4 words with no Jira body fetched, so the exact scope must be inferred from existing code and the symmetric sibling tasks OXY-75 (metrics to http-server), OXY-76 (logging to http-client), OXY-77 (metrics to http-client).

**Current state (verified by reading `CompiledEndpoints.scala`, `ZioHttpServer.scala`, `CurrentRequest.scala`, `Client.scala`/`ZioHttpClient.scala`, `Server.scala`, `oxygen.zio.logging`):**

1. **Server already logs, but hardcoded and minimal.** `CompiledEndpoints.scala:40` does `ZIO.logInfoAnnotated("Handling http request", "method" -> ..., "path" -> ...)` on entry, `CompiledEndpoints.scala:45-46` does `ZIO.logInfoAnnotated("Returning http response", "method" -> ..., "path" -> ..., "code" -> ...)` on both success and failure via `.tapBoth`, and `.tapDefect { ZIO.logErrorCause("Unhandled defect", _) }` at `CompiledEndpoints.scala:42`. `ZioHttpServer.scala:22,25` logs `starting web-server...` / `web-server started on port` at `Info`. `CurrentRequest.scala:43` logs domain-to-API error conversion at a dynamic level via `ErrorLevel[E].level(error)` + `ZIO.logAtLevel`. `McpServer.scala:99` logs `Unhandled error in MCP endpoint` via `logErrorCause`. All of this is at fixed levels (`Info`/`Error`/`Warning`), not configurable, with no timing, no request-id, and no way to suppress or raise verbosity per-environment.

2. **Client already has configurable logging — the precedent to mirror.** `modules/http/zio/src/main/scala/oxygen/http/client/Client.scala:18-45` defines `Client.Config(kind, path, logLevel: LogLevel)` with helpers `relativeUrl`, `relativeUrl(logLevel)`, `layer(urlString, logLevel = LogLevel.Info)`, `fromClient(..., logLevel)`. `ZioHttpClient.scala:9,25,27` stores `logLevel` and does `ZIO.logAtLevel(logLevel)("Sending request [method] url", Cause.Empty)` and `ZIO.logAtLevel(logLevel)("Response status: ...", Cause.Empty)` plus `ZIOAspect.annotated("api-name", "endpoint-name")` at `ZioHttpClient.scala:30`. `Client.layer.live` / `raw` / `default` wire the logLevel through. This pattern is the obvious template for the server.

3. **Server.Config does NOT carry a logLevel.** `modules/http/zio/.jvm/src/main/scala/oxygen/http/server/Server.scala:17-26` defines `Server.Config(errorConfig: ServerErrorConfig)` — only `exposeInternalErrors`/`includeTraces`-like flags. Port/host/TLS live in `zio.http.Server.Config`/`NettyConfig` provided separately via `Server.layer.customized / live / simple`. There is no field to control the `logInfoAnnotated` calls in `CompiledEndpoints.toRoutes(config)`. The `docs/docs/http/server/index.md` placeholder (`TODO : Oxygen HTTP Server`) and `docs/docs/http/index.md` provide no logging spec; `oxygen.zio.logging` (`LogConfig`, `Logger`, `RichLogLevel`, `LogLevels` with `Important`/`Detailed` between `Info`/`Debug`) exists but is not wired into http-server config.

4. **Sibling structure confirms observability initiative.** The To Do list groups `OXY-74 Add logging to http-server (Low)`, `OXY-75 Add metrics to http-server (Lower)`, `OXY-76 Add logging to http-client (Low)`, `OXY-77 Add metrics to http-client (Lower)` — symmetric logging+metrics for client and server. Priority `Low` (not Normal/High) suggests small, non-blocking DX polish, not a production bug. OXY-76 is notably already partially implemented on the client (configurable `logLevel`), which implies OXY-74 is the server-side parity piece.

**Most plausible interpretation (frontrunner):** Make server request/response (and optionally startup) logging configurable via a `logLevel` field on `Server.Config` (or a narrow `Server.LoggingConfig`), mirroring `Client.Config.logLevel`, so operators can tune verbosity per-environment (`Trace` in dev/test via `ViaHttpSpec` override, `Info` in prod, `None` to silence). Wire it through `CompiledEndpoints.toRoutes` / `CompiledEndpoints.handle` to replace the hardcoded `logInfoAnnotated` calls with `ZIO.logAtLevel(logLevel)`-style annotated logging, preserving the existing `method`/`path`/`code` annotations and `tapDefect` error logging. Optionally include request duration and unify with `ErrorLevel` for domain-error paths.

**Alternative plausible scopes (why ambiguity remains):** (a) richer structured logging — add `durationMs`, `requestId`/`traceId`, `userAgent`, `queryParams`, `headers` (redacted), or `body` snippet; (b) per-endpoint `MetricLabel`-like log annotations or opt-out per route via `@param`/`@route` annotation; (c) log redaction / PII filtering; (d) integration with `oxygen.zio.logging.LogConfig` (Oxygen logger vs ZIO default). Any of these satisfies "Add logging" but changes the touched files and estimate.

**Who it affects:** Service authors running `oxygen-http-server` (every consumer of `Server`, `CompiledEndpoints`, `Server.Config`). Today they get fixed `Info`-level request/response logs in all environments; after, they can set `Trace`/`Debug` in tests and `Warning`/`None` in prod without forking the module.

**Why it matters (Low priority):** Low (not Lowest) signals nice-to-have observability / debuggability, not a correctness fix. As `oxygen-http` matures under Epic OXY-2, missing server logging configurability is DX friction alongside metrics (OXY-75) and client logging parity (OXY-76). Small effort, easy to verify, good first observability slice.

**Inferred acceptance criteria:**

1. `Server.Config` (or a new `Server.LoggingConfig` nested inside it) exposes a `logLevel: LogLevel` (default `LogLevel.Info` to preserve current behavior, with `LogLevel.None` to disable). Optionally `logLevel` also controls the `ZioHttpServer` startup messages or they keep `Info`.
2. `CompiledEndpoints.toRoutes(config)` (and `CompiledEndpoints.TreeScan`/`SeqScan` if needed) respects the configured level — e.g., `ZIO.logAtLevel(config.logLevel)` / `ZIO.logAtLevelAnnotated` instead of hardcoded `logInfoAnnotated`. The existing annotations (`method`, `path`, `code`) and `tapDefect` error path are preserved.
3. Config is constructible via `ZLayer.succeed(Server.Config(...))` and works with `Server.layer.live`/`simple`/`customized` helpers; no breaking change for callers who use `Server.Config.default` (they get the default level).
4. Brief note in `docs/docs/http/server/index.md` (replacing the `TODO` placeholder) or `docs/docs/http/index.md` explaining the new field and how to set it per-environment; example updated if needed (`example/apps/web-server/.../WebServerMain.scala` currently builds `Server.Config(errors)` + `Server.layer.simple(port)` as two steps).
5. No behavior change to routing, error mapping, or schema — purely observability. No DB/schema migration.

## Open Questions

1. **Scope — `logLevel` configurability vs richer logging:** Is the intended deliverable just `Server.Config.logLevel: LogLevel` threading to `CompiledEndpoints.toRoutes` (parity with `Client.Config.logLevel` + `ZioHttpClient.logAtLevel`), or should it also include `durationMs`/`requestId`/`traceId`, `headers`/`queryParams` (with PII redaction), or `body` snippet logging? Should `oxygen.zio.logging.LogConfig` / `Logger.oxygenDefault` be involved, or is `LogLevel` alone sufficient?
2. **Per-endpoint control:** Should individual endpoints opt out (or set a different level) via a new `@route.logLevel` / `@param` annotation or `EndpointMiddleware` flag, or is a single global `Server.Config.logLevel` enough? Does the symmetric `OXY-76 Add logging to http-client` expect per-client-instance level vs per-request level?
3. **Error-level routing:** Response logging currently uses `Info` for both success and error (`tapBoth` with same `logInfoAnnotated` at `CompiledEndpoints.scala:44-46`). Should error responses (4xx/5xx) log at `Warning`/`Error` based on status code or `ErrorLevel[E]` (as `CurrentRequest.scala:43` does for domain errors), or keep `Info` for all returns?
4. **Lifecycle logLevel:** Should `ZioHttpServer.scala:22,25` `starting web-server...` / `web-server started on port` messages respect `Server.Config.logLevel` or stay at `Info` (operators typically want lifecycle at `Info` regardless of request verbosity)? Needs a one-line decision.
5. **Default / `None` semantics:** Does `LogLevel.None` mean fully silent (no request/response logs), and should `LogLevel.Trace` emit extra fields (e.g., `queryParams`, `headers`) or just lower the level gate for the same messages? Should `Server.Config.default` remain `Info` to preserve current behavior?
6. **Config surface coordination with OXY-34:** `OXY-34 Clean up server configuration paradigm (Normal)` will likely enrich `Server.Config` from single-field `errorConfig` to include `port`/`host`/`netty` etc. Should this logging field be added as `Server.Config.errorConfig/logLevel/port/host` in that shape now, or added minimally (`errorConfig` + `logLevel`) and migrated when OXY-34 lands? Sequencing affects `WebServerMain.Config.Http` example.
7. **Client parity assumption:** Sibling `OXY-76 Add logging to http-client` is titled as a new task, but `Client.Config.logLevel` + `ZioHttpClient.logAtLevel` already implements configurable client logging (`Client.scala:21,31-45`, `ZioHttpClient.scala:9,25-30`). Should OXY-74 assume OXY-76 is either already done (just parity) or that OXY-76 will add richer client logging (e.g., `duration`/`body`) that OXY-74 should mirror for symmetry?
8. **Assumption to confirm:** That "http-server" refers to the `oxygen-http` server under Epic OXY-2 In Progress (`modules/http/zio/.jvm/src/main/scala/oxygen/http/server/` — `Server.scala` / `CompiledEndpoints.scala` / `ZioHttpServer.scala`) and not to `oxygen-executable`'s `LiveUIApi`/`FileSystemResourceApi` helpers or a different server infra. Confirmed by module proximity and sibling OXY-75/OXY-76/77 grouping, but worth explicit sign-off.

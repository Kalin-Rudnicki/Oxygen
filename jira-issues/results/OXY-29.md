## Expanded Description

**What it likely means:** Define the compatibility/comparison spec for the HTTP layer — the analogue of `oxygen.schema.compat` (which diffs `RawCompiledSchemas` / `FullCompiledSchemas` for type schemas) but for the compiled HTTP API spec (`RawCompiledApiSpec` / `RawCompiledEndpoint` / `RawCompiledRequest` / `RawCompiledResponse`).

Phases 1–3 of the HTTP spec are already implemented and tested (`agent-docs/http-docs/http-feature-plan.md`): `oxygen.http.schema.compiled` defines the serializable IR (`RawCompiledApiSpec` + `RawCompiledApi` + `RawCompiledEndpoint` + `RawCompiledParam` / `RawCompiledPathSegment` / `RawCompiledRequestBody` / `RawCompiledResponseBody` / `CompiledParamType` / `CompiledExpectedStatuses`) in pure cross source, `CompiledApiSpec.compile(Seq[EndpointSchema])` compiles live `EndpointSchema`s through a single `Compiled` run into that IR, `ApiSpecEndpointMiddleware` serves it at `GET /oxygen/api-spec`, and `ApiSpecPage` renders it. Phase 4 — "API-incompatibility detection" — is explicitly pending: *"Persist the compiled spec (avro/sql-migration paradigm), diff via `oxygen.schema.compat` extended to the endpoint/API layer, fail CI on breaking changes; env-var-gated update."* (`agent-docs/http-docs/http-feature-plan.md:74-76, 229-231`). OXY-29 is the spec/comparison half of Phase 4; `OXY-38` ("Add compatibility checking for endpoint schema") is the enforcement/CI-gating half.

**In concrete terms, the task is to create a pure, testable comparison library** that takes two `RawCompiledApiSpec` (from vs. to) and produces a structured compatibility result (breaking vs. compatible vs. compatible-with-additions), reusing the existing type-level `Compared[ComparisonResult]` machinery for the shared `schemas` bundle and adding HTTP-specific rules on top:

* **Type-level reuse:** The `schemas: RawCompiledSchemas` field is diffed exactly as today — `FullCompiledSchemas` + `Compared.compareRoot` / `ComparisonResult` (`ExactEqual` / `FromIsMoreSpecific` / `ToIsMoreSpecific` / `NotComparable`). An endpoint body/param that references a type whose schema comparison is `NotComparable` or a backwards-incompatible narrowing is itself incompatible.
* **Endpoint/API-level rules (HTTP semantics — this is what OXY-29 must codify):**
  * Removing an endpoint / removing an API is breaking (clients call it).
  * Adding a new endpoint / new API is backwards-compatible (existing clients unaffected).
  * Changing an endpoint's identity (method, path pattern — const vs. param, rest param) is breaking; adding an *alternative* path shape to `NonEmptyList[RawCompiledPaths]` needs a compatibility rule (new alternative is compatible, removing one is breaking).
  * Query/header params: adding an `Optional` / `ManyOptional` param is compatible; adding `Required` / `ManyRequired` is breaking (old clients would not send it); removing any param is breaking if clients were sending it, but from a server-compat perspective removing a required param is also breaking; changing `CompiledParamType` cardinality (Required ↔ Optional, Many, etc.) is breaking in the narrowing direction; changing a param's `CompiledSchemaRef` type is governed by type-level compat.
  * Request body: `Empty → Single` is breaking (now requires a body); `Single → Empty` may be compatible (server now accepts empty) depending on product intent — spec must decide. Changing the body schema type delegates to type-level compat.
  * Response body/status: widening a response (adding a new success case to a sum, expanding `OneOf` statuses) is compatible for clients that handle unknown cases gracefully; narrowing or changing `ServerSentEvents` / `LineStream` framing is breaking. `CompiledExpectedStatuses` and `RawCompiledCaseStatus` (`OXY-29`-adjacent — added in Phase 1 for per-case status support) need explicit rules; status codes are currently de-emphasized (`ResponseSchema: // TODO needs lots of additional details`) so the spec should initially treat status as descriptive, not as a primary compatibility signal unless product decides otherwise.
  * Docs/name changes (`doc`, endpoint `name`, API `name`) are non-breaking (cosmetic).
  * `mcp: Option[McpEndpointSchema]` — included in `RawCompiledEndpoint` — likewise needs a rule; likely non-breaking to add/remove MCP exposure but should be explicit.
* **Serialization & presentation:** Like `ComparisonResult` / `Compared`, the HTTP compat result should be `JsonCodec`-serializable where useful and have `toIndentedString` / `pruned` / `isDifferent` helpers and a `show` for CI logs. It should compose with the type-level `Compared` monad (`traverse`, `flatMap`) so a single `Compared[HttpComparisonResult]` can evaluate both levels.

**Who it affects:** Any service that publishes an HTTP API via `oxygen-http` (`modules/http/zio`) and wants CI to catch breaking API changes before deploy. Until this exists, adding a required query param, renaming a path segment, or narrowing a response type produces no automated signal — review relies on human inspection of the `/oxygen/api-spec` JSON diff.

**Why it matters (Higher priority):** Without an HTTP compat spec, the compiled spec (Phases 1–3) is observable but unenforced — the "persist + diff, fail on breaking changes" loop that already protects DB schemas (`oxygen.schema.compat`) and SQL migrations (`MigrationGenerator.classify` / `MigrationCheck`) has no HTTP analogue. This is the missing gate before OXY-31/OXY-32 docs middleware and any public API stability guarantees.

**Inferred acceptance criteria:**

* A new comparison module exists (e.g. `oxygen.http.schema.compat` or `oxygen.http.schema.compiled.compat`) that can compare two `RawCompiledApiSpec` values (with `withoutLineNos` for stability) and returns a structured result distinguishing at least: exact-equal vs. backwards-compatible addition vs. breaking change. The result reuses `oxygen.schema.compat.AddedRemovedBoth` / `FromToValues` patterns where appropriate.
* All HTTP structural elements listed above have an explicit rule (even if initially "treat as breaking" for unknown cases) and the rule is documented in code comments or a doc section.
* Type references are resolved through `FullCompiledSchemas` / `FullCompiledApiSpec.schemas.resolve` and type-level differences propagate to the endpoint-level result (i.e., an endpoint whose body type became incompatible is reported as breaking at the endpoint level).
* JSON round-trip for the comparison result (if persisted) and human-readable rendering for CI failure messages (mirroring `ComparisonResult.toIndentedStringNoTypes`).
* Tests that construct two small `RawCompiledApiSpec` fixtures (via `CompiledApiSpec.compile` on hand-built `EndpointSchema` dummies or via direct `RawCompiled*` construction) and assert the compatibility classification for each rule (add optional param = compatible, add required param = breaking, remove endpoint = breaking, narrow body type = breaking, widen sum response = compatible, method change = breaking, etc.). Tests live alongside `CompiledApiSpecSpec.scala` (`modules/http/it-test/src/test/scala/oxygen/http/CompiledApiSpecSpec.scala:18-50` is the existing Phase 1 harness).
* Docs updated (either `agent-docs/http-docs/http-feature-plan.md` Phase 4 section or `docs/docs/http/` when that doc lands) to describe the compatibility table, mirroring how `docs/docs/sql/migrations.md:60-63` documents the SQL migration compatibility table.

## Required Changes (only if Confidence >= 3)

**Module ownership:** `oxygen-http` (`modules/http/zio` — the only module that owns `oxygen.http.schema.compiled`) and `oxygen-schema` (`modules/general/schema` — for reuse of `Compared`/`ComparisonResult`/`AddedRemovedBoth`/`FromToValues`). No `oxygen-ui` or example-app changes expected for OXY-29 itself (UI rendering already done in Phase 3); `oxygen-http` IT tests own the new specs.

* [ ] **Design the HTTP compatibility result type** — new files, e.g. `modules/http/zio/src/main/scala/oxygen/http/schema/compat/HttpComparisonResult.scala` (or `modules/http/zio/src/main/scala/oxygen/http/schema/compiled/compat/ApiComparisonResult.scala` — exact package to be confirmed with maintainers). Model likely mirrors `oxygen.schema.compat.ComparisonResult`:
  * Variants such as `ExactEqual`, `Compatible` (additions only — new endpoint, new optional param, widened sum response), `Incompatible(breaks: Seq[HttpBreak])` with a `HttpBreak` ADT enumerating *why* (removed endpoint, changed method/path, promoted param to required, narrowed body type, incompatible type-level diff, etc.), plus optionally `RecursiveReference`-style handling if endpoints share types that resolve recursively. Include `toIndentedStringNoTypes`, `pruned`, `isDifferent` / `isCompatible` helpers mirroring `ComparisonResult.scala:7-60`. Derive or hand-write `JsonCodec` if the result will be persisted.
  * Complementary type: `HttpCompared` or reuse `oxygen.schema.compat.Compared` directly by building the HTTP comparison as a `Compared[HttpComparisonResult]` program that `traverse`s endpoints/params and `flatMap`s into `Compared.compareRoot` for each `CompiledSchemaRef`. Decide whether HTTP needs its own `Compared`-like monad or can directly compose with `oxygen.schema.compat.Compared`.

* [ ] **Implement endpoint/API-level diff** — new file(s) `modules/http/zio/src/main/scala/oxygen/http/schema/compat/HttpCompat.scala` (or `CompiledApiSpecCompat.scala`):
  * Entry point `def compare(from: RawCompiledApiSpec, to: RawCompiledApiSpec): Compared[HttpComparisonResult]` (and convenience `compareFull(from: FullCompiledApiSpec, to: FullCompiledApiSpec)`). Internally normalize with `withoutLineNos` (available on `RawCompiledApiSpec:153` and `RawCompiledSchemas`) before comparison.
  * **API grouping:** Diff `apis: ArraySeq[RawCompiledApi]` by `name` (treat `None` as `"<root>"`) using `AddedRemovedBoth` — added API = compatible, removed API = breaking, paired API = recurse into endpoints.
  * **Endpoint identity:** Diff `endpoints: ArraySeq[RawCompiledEndpoint]` within each API by `name` (endpoint `name` is stable — derived from the Scala function name). Added endpoint = compatible; removed = breaking; paired endpoint = deep compare.
  * **Paired endpoint comparison:** For each `(from: RawCompiledEndpoint, to: RawCompiledEndpoint)` with the same `name`, compare:
    * `request.method: Option[Method]` — change = breaking.
    * `request.paths: NonEmptyList[RawCompiledPaths]` — use `AddedRemovedBoth.Many` over the alternative path shapes (segment-by-segment: `Const` string equality, `Param` name + `CompiledSchemaRef` type-level compat, `RestParam` presence). Adding a new alternative = compatible, removing = breaking.
    * `request.queryParams` / `request.headers` / `response.headers: ArraySeq[RawCompiledParam]` — diff by `name`; for paired params compare `kind: CompiledParamType` (Required ↔ Optional/Many narrowing = breaking) and `schema: CompiledSchemaRef` via `Compared.compareNonRoot` (delegate to type-level result); added `Optional`/`ManyOptional` = compatible, added `Required`/`ManyRequired` = breaking, removed param = breaking (conservative — document the choice).
    * `request.body: RawCompiledRequestBody` / `response.body: RawCompiledResponseBody` — `Empty` ↔ `Single` transitions need an explicit rule (propose `Empty → Single` = breaking, `Single → Empty` = compatible for request, opposite for response — confirm with PO); `Single`/`ServerSentEvents`/`LineStream` schema refs via type-level `Compared`; switching `Body` discriminator (e.g. `Single` → `ServerSentEvents`) = breaking.
    * `response.status: CompiledExpectedStatuses` / `response.caseStatuses: ArraySeq[RawCompiledCaseStatus]` — initially treat as non-breaking annotation unless product decides otherwise; at minimum, adding a new `RawCompiledCaseStatus` entry = compatible, removing = breaking, changing code = breaking. Document that status is descriptive because decoding relies on discriminators not status branching (`model.scala:36-44`).
    * `doc: Option[String]` / `api.doc` — ignore (non-breaking).
    * `mcp: Option[McpEndpointSchema]` — treat as non-breaking descriptive field for now (adding/removing MCP exposure does not break HTTP clients); confirm with `agent-docs/mcp/mcp-feature-plan.md` owners.
  * Thread a single `Compared` program so that type-level diffs are evaluated lazily and memoized via `Compared.internal.CompareRoot` / `CompareNonRoot` (see `Compared.scala:17-35`) — do not eagerly resolve every `FullCompiledSchema` outside the monad.

* [ ] **Tests** — extend `modules/http/it-test/src/test/scala/oxygen/http/CompiledApiSpecSpec.scala` (existing 5 tests) or add `modules/http/it-test/src/test/scala/oxygen/http/HttpCompatSpec.scala` (parallel to `modules/general/schema/src/test/scala/oxygen/schema/CompatSpec.scala` and `MigrationGeneratorSpec.scala`):
  * Helper to build minimal `RawCompiledApiSpec` fixtures without needing a full `EndpointSchema` derivation — either hand-construct `RawCompiled*` case classes or derive via `CompiledApiSpec.compile` on synthetic `EndpointSchema` dummies (prefer the latter for realistic `CompiledSchemaRef` wiring, mirroring how `CompiledApiSpecSpec` uses `UserApi`).
  * Assert `ExactEqual` for identical specs; `Compatible` / `FromIsMoreSpecific`-like for adding an optional query param / adding a new endpoint / widening a sum-typed response body; `Incompatible` / `NotComparable`-like for removing an endpoint, changing method/path, promoting a param to required, narrowing a product field, switching body from `Single` to `ServerSentEvents`.
  * JSON round-trip test for the HTTP comparison result if it derives `JsonCodec` (mirrors `CompiledApiSpecSpec.scala:46-50`).
  * Line-number stability test: verify `withoutLineNos` before compare eliminates spurious diffs (mirrors `Compiled.scala:17-19` guidance).

* [ ] **Documentation** — update `agent-docs/http-docs/http-feature-plan.md` Phase 4 section (currently a 2-line stub at `http-feature-plan.md:229-231`) with the compatibility table and the `Compared`-based design, mirroring how `docs/docs/sql/migrations.md:60-63` documents the SQL migration compatibility table. When `docs/docs/http/` materializes (OXY-81 "Add docs for oxygen-http"), migrate the table there. Include the env-var / persist-vs-check split so readers understand OXY-29 vs. OXY-38.

If the compatibility table is kept intentionally narrow (method/path/required-param/type-level only, deferring body `Empty↔Single` and status rules), it could be a 3; if a full exhaustive table plus JSON persistence + `show` polish is required in the same ticket, it edges toward 8 — default to 5 for the spec-only scope described above, with OXY-38 carrying the persistence/CI work.*

* **Autonomy:** 4 / 6 — an agent can implement the spec with only this briefing + the repo.
  * *Justification:* Precedent is strong (`oxygen.schema.compat` gives the exact `Compared`/`ComparisonResult`/`AddedRemovedBoth` template; `model.scala` / `FullCompiledApiSpec` give the diff target; `CompiledApiSpecSpec` gives the test template), and the work is isolated to `modules/http/zio` + `modules/general/schema` with clear conventions. The 2-point gap is product ambiguity: the breaking-vs-compatible table for HTTP (especially body `Empty↔Single`, status codes, and whether removing a query param is breaking) has no written product spec, so an agent must either propose a conservative table and flag it for review or ask 1–2 questions before finalizing. * **Ambiguity-to-resolve:** 3 / 6 — moderate; work can start but needs a few decisions before merge.
  * *Justification:* The module, data model, and integration point (`oxygen.schema.compat`) are unambiguous, but three product/design calls block a confident DONE: (1) the exact HTTP compatibility table — which structural changes are breaking vs. compatible (see Open Questions); (2) whether the task includes only the in-memory comparison spec or also the persist-to-file / CI-fail wiring (the latter is cleanly separable as `OXY-38`, but the issue title does not explicitly say "in-memory only"); (3) the desired result granularity — binary (`Compatible`/`Incompatible` like SQL migrations) vs. richer lattice (`ExactEqual` / `FromIsMoreSpecific` / `ToIsMoreSpecific` / `NotComparable` like schema compat). All three are resolvable with a short design note or by proposing a conservative default and documenting assumptions.*

## Open Questions

* **Compatibility table — which HTTP changes are breaking?** Confirm the intended rules for: (a) adding/removing endpoints and APIs, (b) changing method or path shape (including `RestParam`), (c) adding/removing query/header params by `CompiledParamType` (`Required` vs. `Optional` vs. `Many`), (d) request body `Empty` ↔ `Single` transitions, (e) response body discriminator switches (`Single` ↔ `ServerSentEvents` ↔ `LineStream`), (f) response `CompiledExpectedStatuses` / `RawCompiledCaseStatus` additions/removals, (g) `mcp` field. A conservative default (any structural removal or narrowing = breaking, any pure addition of optional/widened type = compatible) is implementable without blocking, but should be ratified.
* **Binary vs. richer result lattice?** Should the HTTP comparison expose the same four-way `ExactEqual` / `FromIsMoreSpecific` / `ToIsMoreSpecific` / `NotComparable` lattice as `oxygen.schema.compat.ComparisonResult` (so callers can distinguish "new API is a superset" vs. "incompatible"), or a simpler `BackwardsCompatible` / `Incompatible` like `MigrationCompatibility`? The SQL migration path chose binary + `BlockedIncompatible`; the schema path kept the richer lattice — which idiom should HTTP follow?
* **Scope vs. OXY-38 — where is the boundary?** Does OXY-29 include persisting `RawCompiledApiSpec` to a JSON file and a test-harness analogue of `DbMigrationSpec` / `MigrationCheck`, or is that entirely `OXY-38` ("Add compatibility checking for endpoint schema")? The plan doc treats persistence/diff/fail as Phase 4 as a whole; the checklist splits them. Propose treating OXY-29 as spec-only (in-memory `compare`) and OXY-38 as the file/CI gate, but confirm.
* **Package location?** `oxygen.http.schema.compat` (parallel to `oxygen.schema.compat`) vs. `oxygen.http.schema.compiled.compat` (nested under the compiled spec). The former is more discoverable and mirrors the schema module; the latter keeps the compiled spec self-contained. Either works — pick one and be consistent with `OXY-38`'s import path.
* **Status codes — descriptive or normative?** `RawCompiledResponse.status: CompiledExpectedStatuses` is currently de-emphasized because decoding keys off discriminators, not status codes (`model.scala:36-44`). Should status changes contribute to compatibility, or remain non-breaking annotations until the `ResponseSchema // TODO: needs lots of additional details` is resolved? If the latter, the compat spec should explicitly state that status is ignored for now.
* **Line-number stability contract?** Should every caller be required to call `withoutLineNos` before comparing, or should the compat entry point normalize automatically (as the doc suggests for serialization/diff purposes at `modules/general/schema/src/main/scala/oxygen/schema/compiled/Compiled.scala:17-19`)? Decide and document in the `compare` scaladoc.
* **OXY-29 vs. OXY-123 naming?** `OXY-123` is "Add compatibility spec for DB Schema" — the DB analogue of this ticket but for `oxygen-sql` table/column schemas (not the migration-level `OXY-8` gate). Confirm that OXY-29 and OXY-123 are intentionally parallel (HTTP vs. DB) and will share the same `Compared`/`AddedRemovedBoth` design language, so the two specs stay conceptually aligned.

## Expanded Description

**What this likely is:** Get the first end-to-end, macro-generated text parser for the new `oxygen-slyce` module working. The epic OXY-127 `Slyce` (sic) and this task's `Sylce` typo are the same project: **"Use macros to generate text parsers"** — verified as `oxygen-slyce-core` in `build.sbt` on branch `current/feature/slyce` (`description := "Use macros to generate text parsers."`, `crossProject(...).in(file("modules/slyce/core"))`, `dependsOn(oxygen-meta, oxygen-test)`).

The name `Slyce` is a pun on *slice* / *splice* / *Sly* + *Ice* — a macro-driven lexer+parser generator where users define grammars as plain Scala `Token`/`Node` case classes and a macro synthesizes the parser at compile time. The current `slyce` branch is a WIP proof-of-concept that already contains the data model and macro introspection, but the macro itself is a stub (`Macros.showStuff` that just `report.info`s the `ElementRepr` tree and returns `()`) and is littered with `FIX-PRE-MERGE` / `???` placeholders. "Get initial macro-based impl working" means: replace the debug stub with a real `inline def parse[A: Type](source: Source): Either[ParseError, A]` (or similar) that lexes + parses and returns a populated, span-annotated AST.

**Who it affects:** Anyone who needs a typed, zero-boilerplate parser in Oxygen — DSLs, config languages, query languages, code generators, or future `oxygen-sql`/`oxygen-http` grammar work. Today Oxygen has no general parser combinator (only hand-rolled `JsonParser` in `oxygen-json` and `ParsedRegex` in `slyce` itself, plus `ArgsParser` in `oxygen-cli`). Without Slyce users hand-write lexers/parsers or pull in external libs (fastparse, parboiled, cats-parse) with no `Span`/`SourcePosition` integration.

**Why it matters (High priority):** This is the foundational task of the epic — nothing else in OXY-127/OXY-129 can ship until the macro pipeline works. The duplicated "initial initial" in the title emphasizes it is the *very first* working slice (lexer + product/sum + Option/List dispatch). OXY-129 "grammar re-shuffling to prevent conflicts" is explicitly deferred as a follow-up, confirming OXY-128 scope is *without* conflict resolution / grammar rewriting — just a correct macro for unambiguous grammars. Priority `High` signals this is the critical path for the Slyce feature.

**Inferred acceptance criteria for "initial impl working":**

1.  Define the public macro API — at minimum one of:
    ```scala
    inline def parse[A <: Node](source: Source): Either[ParseError, A] // or inline def parserFor[A <: Node]: Parser[A]
    // or derivation-style:
    object Slyce { inline def derived[A <: Node]: SlyceParser[A] = ${ impl[A] } }
    // where SlyceParser[A] has def parse(source: Source): Either[ParseError, A]
    ```
    The exact name is unspecified — `Macros.showStuff` suggests the author was iterating toward `inline def show[A]` / `inline def derive[A]` / `inline def parse[A]`. Any name that synthesizes a parser for `A` from its `ElementRepr` satisfies the title, but it must be documented.

2.  Macro generates a **lexer** from all `Token` leaves: at compile time, each `@regex` string is parsed via `ParsedRegex.parse` (already working; `ParsedRegexSpec` tests pass) into a `ParsedRegex` IR, which is then compiled to a runtime matching strategy. Lexer must implement longest-match / priority (token order vs. regex specificity) — initial impl can use simplest deterministic rule (first-defined wins or longest wins) as long as it is documented; OXY-129 will later add re-shuffling for conflicts.

3.  Macro generates a **parser** from all `Node` structures: product nodes become sequence parsers (`field1 >>> field2 >>> ...`), sum nodes become alternative parsers (`case1 | case2 | ...`), `Option[A]` becomes optional, `List[A]` becomes `many`, `NonEmptyList[A]` becomes `many1`, `A | B` (union) becomes `EitherNode`-like alternative. `Token` fields consume one lexed token; `Node` fields recurse. Parser must thread `Span` construction: each `Token.initializeToken(span, text)` and `Node.initializeNode(span)` is called with the consumed range (`Span.Range` / `ZeroWidth`), verified by `Element.scala:initializeToken/Node` guards. Parser must handle left-recursion if the example grammar requires it (Expr1..Expr4 are deliberately left-recursive) — either via explicit re-associating (Expression ADT) or by rewriting at macro time.

4.  **Span/source fidelity:** `Source` substring helpers (`substringInclusive/Exclusive`) and `SourcePosition`/`SourceLine`/`Span` plumbing are completed so every `Element.span` points into the original `Source` and error reporting can render line:col. `Source.lineStarts` / char indexing must work for `SourcePosition.atSourceIndex` (`SourcePositionSpec` already tests `relativePosition` logic — keep those tests green).

5.  **Error reporting:** On failure, return a typed error (new `ParseError` / `SlyceError` case class) containing expected set, actual token/text, and `Span`/`SourcePosition` — not just `String`. At least `Span.HasPosition` + offending `SourcePosition` must be present so `SlyceAssertions` helpers (`sourceLine.*`, `sourcePosition.*`) can assert.

6.  **Tests + Wiring:** `modules/slyce/core/src/test/scala/oxygen/slyce/core/generic/ParsedRegexSpec` + `SourcePositionSpec` stay green; new tests parse `TmpMacros.Program` or a minimal `Program` example from a `Source.rawText("x := 1 + 2 * 3")`-like input, assert parsed AST equals expected `Program(...)` and every node's `span` covers the correct source range. Build wiring: `build.sbt` already defines `oxygen-slyce-core` (Pure crossProject, deps on `oxygen-meta` % testAndCompile, `oxygen-test` % Test) — ensure it aggregates into `oxygen-modules-jvm/js/native` and CI `+test:compile` passes. `check-for-fix.sh` currently blocks `FIX-PRE-MERGE` on commit — either resolve all such markers or gate with `ALLOW_FIX_PRE_MERGE`.

7.  **Docs/build:** `docs/docs/future-plans.md` is empty (0 lines) and `modules/slyce` has no `README`; at minimum a short `modules/slyce/README.md` or `docs/docs/slyce/index.md` sketching `Token` vs `Node`, `@regex`, and the macro entry point, plus Scaladoc on `SlyceParser`/`parse` method. No migration or HTTP/sql changes.

1.  **Public macro name/signature:** Should the entry point be `inline def parse[A <: Node](source: Source): Either[ParseError, A]`, `inline def parser[A <: Node]: SlyceParser[A]`, `inline def derived[A <: Node]: SlyceParser[A]`, or `transparent inline def compile[A <: Node]: Parser[A]`? Choice determines call-site ergonomics and whether the parser is recreated per call or derived once. Which error type — `ParseError`, `SlyceError`, or `Either[String, A]` — does the human expect?
2.  **Lexer disambiguation rule for v1:** With multiple `@regex` tokens that can match the same prefix (e.g. `Variable "[A-Za-z_][A-Za-z_0-9]*"` vs keyword `"@show"`), what rule should the initial lexer use — declaration order, longest match, sum-type priority (keyword before generic)? OXY-129 will automate re-shuffling — until then, is manual ordering (define keywords before generics) acceptable, or must `Token.Builder` / `@regex` carry a `priority: Int`?
3.  **Parser strategy — codegen vs. interpreter:** Does "macro-based impl" mean the macro splices generated Scala code (recursive `def parse_Expr1(pos: Int): (Expr1, Int)`) inline at the call site (most "macro-based", best perf, spans at compile time), or that the macro builds a runtime `Parser` IR (tables/closures) that is then interpreted (simpler, smaller generated code, easier left-recursion handling)? This changes `ParserGen` from a `Term` builder to an IR builder and affects compilation time.
4.  **Span/std-lib completeness:** Is finishing `Source.substringInclusive/Exclusive` + `Source.lineStarts` + `SourcePosition` helpers part of OXY-128, or should those be split into a separate "Source infra" subtask? The parser cannot correctly annotate `Token.text`/`Node.span` without them, so they are on the critical path — but the human may consider them already done.
5.  **Left-recursion & associativity:** `TmpMacros.Expr1.A(a: Expr2, b: MultOp, c: Expr1)` is left-recursive and mutually recursive (`Expr1..Expr4`). Should OXY-128 support direct left recursion (via `lazy val` parsers or a left-recursion transform), require users to write it non-left-recursive, or use the existing `Expression[Operand, Operator]` helper to encode precedence? The choice changes whether `Expression` is in scope for v1.
6.  **Whitespace/comments:** Are they explicit `Token`s the user defines (`@regex("\\s+".r) final case class Whitespace() extends Token` — opt-in) or implicit skipped tokens handled by the lexer/parser (e.g. `skip: Set[Token]` param, `spaceSep` combinator)? The `TmpMacros` example has no whitespace token yet every real input contains whitespace — so the convention must be chosen before tests can pass.

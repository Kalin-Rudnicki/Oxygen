## Expanded Description

**What this bug likely is:** `PulsarAdminClient.topic.createIfDNE` (and by extension `tenant.createIfDNE` / `namespace.createIfDNE`) is intended to be idempotent — "create if does not exist" — but under concurrent or near-concurrent calls it randomly fails with a Pulsar `Topic already exists` / `409 Conflict` / `PulsarAdminException` instead of succeeding silently. Callers that correctly use `createIfDNE` to ensure infrastructure exists at startup or before producing/consuming still see flaky fiber failures, especially in parallel tests or multi-instance startup.

**Current implementation (verified from code):**

`modules/events/pulsar/src/main/scala/oxygen/pulsar/client/PulsarAdminClient.scala` defines three `createIfDNE` helpers, all using the same **check-then-act** pattern with no exception handling:

* `tenant.createIfDNE(tenant: PulsarTenant): Task[Unit]` at `:49-53` — `list.flatMap { case tenants if tenants.contains(tenant) => logInfo already exists; case _ => create(tenant) }`. `create` at `:42-47` does `client.tenants().createTenantAsync(...).unit` via `ZIO.fromCompletableFuture`.
* `namespace.createIfDNE(namespace: PulsarNamespace): Task[Unit]` at `:74-81` — `self.tenant.createIfDNE(tenant) *> list(tenant).flatMap { case namespaces if contains => logInfo; case _ => create(namespace) }`. `create` at `:70-72` does `client.namespaces().createNamespaceAsync(...).unit`.
* `topic.createIfDNE(topic: PulsarTopic, partitions: Option[Int]): Task[Unit]` at `:122-135` — `self.namespace.createIfDNE(namespace) *> list(namespace).flatMap(filtered ...) *> (if filtered.isEmpty then create(topic, partitions) else if mismatched partitions then logWarning else logInfo)`. `create` at `:110-120` does `client.topics().createPartitionedTopicAsync(...)` or `createNonPartitionedTopicAsync(...)`.

None of the three wraps `create` in a `catch`/`recover` for `PulsarAdminException` `409` / `"already exists"` / `"Topic already exists"`. `grep -rn PulsarAdminException` finds zero handling in `modules/`; grep for `AlreadyExists`/`Conflict`/`409` finds no Pulsar-related handling either — verified.

**Race (why random):**

```
Fiber A: list(topics) -> [] (empty)
Fiber B: list(topics) -> [] (empty)
Fiber A: create(topics) -> succeeds
Fiber B: create(topics) -> throws PulsarAdminException: Topic already exists (409)
```

The same race applies to tenants/namespaces when two services bootstrap concurrently. The title says `Topic already exists` specifically, so the `topic` path is the reported symptom, but the tenant/namespace paths have the identical TOCTOU. "Random" is timing-dependent — only when two callers interleave between `list` and `create` (common at parallel test startup or rolling deploys).

A second non-concurrency contributor is **Pulsar's partitioned-topic listing shape vs creation shape**: `list` at `:93-99` returns fully-qualified URLs that may include `-partition-N` suffixes; `createIfDNE` at `:128` filters by `ignorePartition` and counts partitions, but a topic that already exists as partitioned vs non-partitioned (or eventual consistency of `getListAsync` vs `createPartitionedTopicAsync`) could still race with the check.

Also `list(namespace)` itself can throw/return stale data if the namespace was just created — the chained `self.namespace.createIfDNE(namespace)` at `:126` may still be propagating, so `getListAsync` could miss a topic that another writer just created.

**Who it affects:** Any service that calls `PulsarAdminClient.topic.createIfDNE` to ensure topics exist before producing/consuming — typically at application startup, in `ZLayer` `acquire`, or in test `beforeAll`. Since the method is the documented idempotent entry point, callers do not expect to handle `already exists` themselves. Flaky failures block startup and make Pulsar integration tests non-deterministic. Priority `Higher` (vs `Normal` for adjacent UI tasks OXY-145 etc.) signals this is a correctness/operational blocker, not polish — consistent with other `Higher`/`High` tasks being blocking bugs.

**Why it matters (Priority Higher):** Idempotent setup is a core operational requirement — without it, every concurrent deployment or parallel spec that touches the same `PulsarTopic` (e.g., same tenant/namespace/topic in a shared dev Pulsar) risks a spurious failure that must be retried manually. The current `logInfo "already exists"` path only covers the case where `list` *already* saw the topic; it does not cover the equally valid case where the `create` call loses the race and the server reports `already exists`.

**Inferred acceptance criteria:**

1. `topic.createIfDNE(topic, partitions)` is idempotent under concurrent calls: two fibers calling it simultaneously for the same `(tenant, namespace, topic, partitions)` both succeed (both return `ZIO.unit`), at most one `create*TopicAsync` succeeds, the other treats `PulsarAdminException` with `409` / message containing `already exists` / `Topic already exists` as success and logs `Pulsar topic already exists [...]` at `Info` (not failure).
2. Same idempotency holds for `tenant.createIfDNE` and `namespace.createIfDNE` — they are fixed for consistency even though the title only mentions topics; otherwise the same race can surface one layer up.
3. Mismatched partitions behavior is preserved: if topic exists but `numPartitions != partitions.getOrElse(0)`, still emit `logWarning` with mismatching partitions and succeed (do not throw). Only the `filtered.isEmpty` -> `create` branch changes to be exception-tolerant.
4. Non-`already exists` failures still propagate: e.g., `401 Unauthorized`, `404 Namespace not found` (if tenant creation truly failed), `500 Internal error`, or timeout — those must not be swallowed. Only the narrow `already exists` case is mapped to success.
5. No change to `list` semantics or `PulsarTopic` model; concurrency fix is localized to `PulsarAdminClient`. Existing callers require no code change and see fewer flaky failures.
6. Unit/integration test proves idempotency under race (e.g., mock `RawPulsarAdminClient` where `createPartitionedTopicAsync` fails with `PulsarAdminException` `409` on second call, assert `createIfDNE` still succeeds) and that unrelated exceptions still fail.

## Open Questions

1. **Exact exception to swallow:** What is the precise type/message Pulsar `4.2.0` `pulsar-client-admin` throws on duplicate create? Is it `PulsarAdminException` with `statusCode == 409`, `PulsarAdminException.ConflictException`, or a wrapped `CompletionException` with message `Topic already exists` / `Topic 'persistent://...' already exists` / `Resource already exists`? Should the predicate match status code, message `already exists` (case-insensitive), or both? Confirming against a running broker or Javadoc ensures the catch is not too narrow (still flaky) or too broad (swallows real errors).
2. **Scope — topic only vs all three:** Title says `Topic already exists`, but `tenant.createIfDNE` and `namespace.createIfDNE` have the identical race. Should the fix apply to all three for consistency, or strictly to `topic.createIfDNE` to minimize blast radius? Recommendation is all three (small, safe), but confirm with reviewer.
3. **Partitioned vs non-partitioned mismatch:** If a topic exists as partitioned (`partitions=3`) but `createIfDNE(topic, None)` is called (or vice versa), current code logs a `Warning` about mismatching partitions and succeeds. Should this remain a warning, or should it `ZIO.fail` with a typed `PulsarAdminError.PartitionMismatch` so callers can detect schema drift? Title does not mention partitions, so preserving current warning is assumed.
4. **Logging level on catch:** When `create` loses the race and `already exists` is caught, should it log `Info` `Pulsar topic already exists [...]` (same as the `list`-saw-it path) or silent success (`ZIO.unit`) or `Debug`? Current `list`-hit path uses `logInfo`; mirroring that is assumed least surprising, but silent may be preferred to avoid duplicate log lines when many fibers race.
5. **CompletionException unwrapping:** `ZIO.fromCompletableFuture` wraps `PulsarAdminException` in `CompletionException`/`ExecutionException`. Must `isAlreadyExists` unwrap `getCause` recursively, or does ZIO already unwrap one layer? Quick check of `ZIO.fromCompletableFuture` semantics (and a unit test with a mocked failing future) will confirm, but human confirmation of unwrapping depth avoids a fix that tests green but still flaky in prod.
6. **Retry for transient errors:** Should `createIfDNE` also retry on transient errors (e.g., `PulsarAdminException` with `503 Service Unavailable` or `TimeoutException` during broker leader election) with a short backoff, or should it fail fast and let the caller retry? Title only mentions `already exists`, so failing fast on non-409 is assumed, but Pulsar startup races sometimes need a single retry.

## Expanded Description

**What it likely means:** Define the **compatibility/comparison spec for the DB layer** — the DB analogue of `OXY-29` ("Create compatibility spec for HTTP Schema") and the richer, type-aware counterpart to `OXY-8` ("Add compatibility checking to db migrations").

`OXY-8` already shipped the **binary migration-level gate** in `oxygen-sql-migration`: `MigrationCompatibility` (`BackwardsCompatible` vs `Incompatible`) in `modules/sql/migration/persistence/model/MigrationCompatibility.scala:11-13`, `MigrationGenerator.classify` / `classifyOne` in `modules/sql/migration/MigrationGenerator.scala:52-92` which classifies every `StateDiff` variant (add nullable column = compatible, add non-nullable column = incompatible, drop table/column = incompatible, unique index/FK on existing table = incompatible with the `createdTables` empty-table exception at line 53-54), `MigrationGenerator.bump` mapping to semver (`1.0.0` genesis, major for incompatible, minor for compatible at lines 94-101), and `MigrationCheck` (`modules/sql/migration/src/main/scala/oxygen/sql/migration/MigrationCheck.scala:26-105`) gating writes behind `OXYGEN_MIGRATION_ALLOW_UPDATE` / `OXYGEN_MIGRATION_ALLOW_INCOMPATIBLE` (`Config.allowUpdateEnv` / `allowIncompatibleEnv` at lines 46-47) with `Outcome.PendingUpdate` / `BlockedIncompatible` (lines 70-76, 97-103) surfaced by `DbMigrationSpec` in `modules/sql/test-utils/src/main/scala/oxygen/sql/test/DbMigrationSpec.scala`. That gate is coarse — it only knows "any destructive StateDiff = incompatible".

`OXY-123` is the **spec half** for DB schema at the **table/column/type level** — the `oxygen.schema.compat` analogue (`modules/general/schema/src/main/scala/oxygen/schema/compat/Compared.scala`, `ComparisonResult.scala:7-89`, `AddedRemovedBoth`, `FromToValues`) but for `oxygen-sql`'s own model (`MigrationState`, `TableState`, `Column`, `Column.Type`, `ForeignKeyState`, `IndexState` in `modules/sql/migration/model/MigrationState.scala`, `TableState.scala:9-14`, `modules/sql/core/src/main/scala/oxygen/sql/schema/Column.scala:6-82`). Like `OXY-29` diffs `RawCompiledApiSpec` via `FullCompiledSchemas` + `Compared.compareRoot`, `OXY-123` would define a pure, testable `compare(from: MigrationState, to: MigrationState): Compared[DbComparisonResult]` (or `from: PersistedMigrationFile.state` snapshots) that codifies which DB structural changes are breaking vs. compatible, reusing `Compared` / `ComparisonResult` lattice (`ExactEqual` / `FromIsMoreSpecific` / `ToIsMoreSpecific` / `NotComparable`) for any shared `oxygen.schema` type references and adding DB-specific rules on top.

**In concrete terms, the task is to create a pure comparison library** (no IO, no DB) that answers "is the proposed schema backwards-compatible with the currently persisted schema?" with a structured result suitable for CI gating, version bumping, and human-readable diffs:

*   **State-level diffing:** Takes two `MigrationState` values (from = latest persisted snapshot, to = current-code derived via `MigrationState.fromTables` + `TableState.fromTable`). Diffs extensions (`Set[String]`), schemas (`Set[SchemaRef]`), and tables (`Map[TableRef, TableState]`). Table addition = backwards-compatible; table removal = incompatible; schema create = compatible, schema drop = incompatible (mirroring `MigrationGenerator.classify` but lifted into a richer result rather than a binary flag).

*   **Table-level rules (DB semantics — this is what OXY-123 must codify):**
    *   Adding a new column: `nullable == true` → `BackwardsCompatible` (Postgres allows `ALTER TABLE ADD COLUMN ... NULL` on populated tables); `nullable == false` with no default → `Incompatible` (fails on existing rows) — same as `classifyOne` today, but the spec should surface the column name/type and distinguish "incompatible because non-nullable without default" vs a future "compatible if default supplied" (docs `docs/docs/sql/migrations.md` notes "No default values yet" — OXY-123 should decide whether defaults make `NOT NULL` adds compatible).
    *   Dropping a column / renaming a column → `Incompatible` (data loss / `SELECT *` breakage).
    *   Changing `Column.Type`: `SMALLINT → INT → BIGINT` widening is compatible (Postgres implicit widening, no data loss); `INT → SMALLINT` narrowing is incompatible; `TEXT → VARCHAR(N)` narrowing is incompatible; `TEXT ↔ JSON/JSONB` is incompatible; `Array(elem)` element-type changes delegate to element compat; `Vector` size changes; `UUID` / `BOOLEAN` type changes are incompatible. The `Column.Type` ADT (`Column.scala:34-81`: `SmallInt`, `Int`, `BigInt`, `Real`, `DoublePrecision`, `Text`, `Timestamp`, `ZonedTimestamp`, `Date`, `Time`, `Boolean`, `UUID`, `Json`, `Jsonb`, `LTree`, `Array`, `Vector`) is small today but `// TODO: decimal / VARCHAR/CHAR / ZonedTime / Interval / ...` signals it will grow — the compat table must be exhaustive and forward-extensible.
    *   Nullability toggle: `false → true` (relax `NOT NULL`) → `BackwardsCompatible` (loosening); `true → false` (tighten) → `Incompatible` unless a default/backfill covers existing nulls (same open question as column addition).
    *   Primary key changes (`primaryKeyColumns` in `TableState.scala:11`): adding/removing PK columns, or changing PK composition, is incompatible (changes identity, FK targets, `TableCompanion` generation).
    *   Foreign keys (`ForeignKeyState`, `ForeignKeyRepr`): adding an FK to an *existing* table with data is incompatible (may fail on orphans) unless the FK self-table is also `createdTables` in this migration (empty-table exception at `MigrationGenerator:53-54`); dropping an FK is compatible; renaming (explicit vs auto-named) is compatible (just `RenameExplicitlyNamedForeignKey` / `RenameAutoNamedForeignKey` at `StateDiff.scala:198-200`). FK column-type or target changes must respect column-type compat.
    *   Indices (`IndexState`, `IndexRepr`): `!unique` adds are compatible; `unique` adds on existing tables are incompatible (same `createdTables` exception at `MigrationGenerator:82`); dropping any index is compatible; renaming (explicit vs auto-named at `StateDiff:201-202`) is compatible. Expression/index-method changes are incompatible if they narrow uniqueness.
    *   Extensions / schemas: `CreateExtension` / `CreateSchema` compatible; `DropSchema` incompatible (no `DropExtension` yet — `StateDiff.AlterExtension` has only `CreateExtension` with `// TODO: drop extension?` at line 140).

*   **Type-level reuse (if DB columns carry `oxygen.schema` types):** Some column types ultimately derive from Scala types with `JsonCodec`/`JsonSchema` (e.g. via `TypedJsonb`). Where a column's logical type has an `oxygen.schema` representation, the DB compat result should delegate to `Compared.compareRoot` / `ComparisonResult` for that type so `String → Option[String]` column semantics can be evaluated consistently with the HTTP/JSON schema compat.

*   **Result model & presentation:** Like `ComparisonResult` + `Compared`, the DB compat result should have `ExactEqual` / `FromIsMoreSpecific` / `ToIsMoreSpecific` / `NotComparable` (or at minimum `BackwardsCompatible` / `Incompatible` if the team wants to keep the binary surface of `MigrationCompatibility`), plus richer per-entity breakdowns (`TableComparison`, `ColumnComparison` with `AddedRemovedBoth.Many` for columns/FKs/indices, `FromToValues` for nullability/type). It should support `toIndentedString` / `pruned` / `isDifferent` / `JsonCodec` (if persisted) and compose with `Compared` monad (`traverse`, `flatMap`) so a single `Compared[DbComparisonResult]` can report the whole migration diff.

*   **Relationship to OXY-8 / MigrationCheck:** `OXY-8`'s `MigrationGenerator.classify` + `MigrationCheck` is the **enforcement harness** that gates filesystem writes. `OXY-123` is the **spec** it should eventually consult. After `OXY-123` lands, `MigrationGenerator.classify` could either be replaced by `DbCompatibilitySpec.compare(fromState, toState).eval(...).result.isCompatible` or kept as a thin binary collapse of the richer result (`if any table/column diff is NotComparable → Incompatible else BackwardsCompatible`). The file format already stores `PersistedMigrationFile.compatibility` (binary) plus the full `state` snapshot (`PersistedMigrationFile.scala:20-27`) — the snapshot is what enables cross-version diffing without per-diff inversion logic (docstring at lines 9-11). `OXY-123` should decide whether the persisted file should additionally store the richer `DbComparisonResult` or whether binary + state is sufficient and the rich diff is purely for CI logs.

**Who it affects:** Any service that owns Postgres tables via `oxygen-sql` (`TableRepr.derived`, `MigrationSchema.of`, `MigrationService` in `modules/sql/migration/`) and wants CI to catch breaking DB changes before deploy — the same audience as `OXY-8`, but with actionable per-column diagnostics instead of a coarse `Incompatible` flag. Also affects `oxygen-sql-test` / `DbMigrationSpec` consumers and anyone extending `Column.Type`.

**Why it matters (Higher priority):** Without a DB schema compat spec, the only signal is `MigrationGenerator.classify`'s binary gate plus the semver bump (`MigrationGenerator.bump` at lines 95-101). That conflates very different breakages (drop column vs. add `NOT NULL` without default vs. narrow `INT→SMALLINT` vs. add unique index) into one `Incompatible` bucket that always forces a major bump and `ALLOW_INCOMPATIBLE=true`. A structured spec would let CI report *which* tables/columns broke compatibility, allow finer-grained policy (e.g., "allow widening but not narrowing", "allow FK adds on empty tables only"), and give reviewers a readable diff (`toIndentedString`) rather than a single `Incompatible` label. It also aligns DB schema with the HTTP schema track (`OXY-29` / `OXY-38`) so all three schema surfaces (HTTP, JSON/schema, DB) share the same `Compared` / `ComparisonResult` / `AddedRemovedBoth` design language. Until this exists, reviewers inspect `StateDiff` lists manually and rely on `// TODO: default values` optimism.

**Inferred acceptance criteria:**

*   A new package/object — e.g. `oxygen.sql.migration.compat.DbCompatibilitySpec` or `oxygen.sql.schema.compat.SqlSchemaCompatibility` (exact package to be confirmed; likely `modules/sql/migration/src/main/scala/oxygen/sql/migration/compat/` or `modules/sql/core/src/main/scala/oxygen/sql/schema/compat/` — keep parallel to `oxygen.schema.compat`) — exposes `def compare(from: MigrationState, to: MigrationState): Compared[DbComparisonResult]` (and/or an overload taking `(fromSnapshot: MigrationStateColumn, toState: MigrationState)` / `PersistedMigrationFile` pair to avoid deserializing twice).
*   `DbComparisonResult` is an ADT with `ExactEqual` / `FromIsMoreSpecific` / `ToIsMoreSpecific` / `NotComparable` top-level (or `BackwardsCompatible` / `Incompatible` if collapsing) plus nested `TableResult` / `ColumnResult` / `FkResult` / `IdxResult` that use `AddedRemovedBoth.Many` / `FromToValues` for per-entity diffs, with `toIndentedString` / `pruned` / `isDifferent` matching `ComparisonResult` conventions and `toIndentedStringNoTypes`-like rendering for CI logs.
*   The per-column-type compatibility table is exhaustive over `Column.Type` (`Column.scala:40-81`): widening numeric (`SmallInt→Int→BigInt`, `Real→DoublePrecision`) is compatible in the widening direction, narrowing is `NotComparable` / `Incompatible`; `Text` ↔ `Json`/`Jsonb`/`UUID` cross-kind is `NotComparable`; `Array` element compat delegates; `Vector`/`LTree` extension-aware.
*   Nullability and column addition respect the same rules as `MigrationGenerator.classifyOne` (`Column.scala:6-9` `nullable: Boolean`): add nullable = compatible, add non-nullable = incompatible (or compatible if default is introduced — spec must state the choice and document the `docs/docs/sql/migrations.md` "No default values yet" follow-up).

*   Unit tests construct two small `MigrationState` fixtures (via `TableState.unsafeFromTable` on dummy `TableRepr.derived` fixtures or via direct `TableState` / `MigrationState` construction with hand-built `Column`/`TableRef`/`ForeignKeyState`/`IndexState`) and assert the compatibility classification for each rule (add nullable column = compatible, add required column = breaking, drop column = breaking, widening = compatible, narrowing = breaking, add unique index on existing table = breaking, same on new table = compatible). Tests live alongside `MigrationGeneratorSpec` / `MigrationCheckSpec` in `modules/sql/it-test/src/test/scala/oxygen/sql/migration/` or `modules/sql/core/src/test/scala/oxygen/sql/schema/compat/` and exercise the harness without needing a real `PostgresTestContainer` (pure logic), with a few integration assertions that `MigrationGenerator.classify` collapses identically to `DbComparisonResult.isCompatible`.
*   Docs updated (`docs/docs/sql/migrations.md` Versioning & compatibility section at ~136 lines, or `docs/docs/sql/models.md`) to describe the DB compatibility table, mirroring how `OXY-8`'s docs already list the binary table and how `agent-docs/http-docs/http-feature-plan.md:74-76` describes the HTTP spec. At minimum the persisted `PersistedMigrationFile.compatibility` field and the env-var gate are cross-linked.

## Confidence
- **Rating:** 4 / 6 — good evidence, one clear frontrunner.

**Justification:**

*   **Title maps cleanly to an established repo pattern.** `oxygen.schema.compat` (`modules/general/schema/src/main/scala/oxygen/schema/compat/Compared.scala:8`, `ComparisonResult.scala:8-89`, `AddedRemovedBoth`, `FromToValues`) is the established "compatibility spec" pattern, and the DB analogue has a natural target (`MigrationState` / `TableState` / `Column.Type` in `modules/sql/migration/model/MigrationState.scala`, `TableState.scala`, `modules/sql/core/src/main/scala/oxygen/sql/schema/Column.scala:6-81`) plus the existing binary `MigrationCompatibility` (`MigrationCompatibility.scala:11-14`) / `MigrationGenerator.classify` (`MigrationGenerator.scala:52-92`) that `OXY-8` built. The phrase "Add compatibility spec for DB Schema" matches the `OXY-29` ("Create compatibility spec for HTTP Schema") / `OXY-8` ("Add compatibility checking to db migrations") split verbatim — the repo uses "spec" for the pure comparison-rules library and "checking" for the `MigrationCheck` / `DbMigrationSpec` gate. `OXY-123` being the spec and `OXY-8` being the checking half is therefore non-speculative.
*   **Sibling issues reinforce the split and cross-link.** `OXY-38` ("Add compatibility checking for endpoint schema", Higher) is explicitly the HTTP checking harness counterpart to `OXY-29`'s spec (both Higher), and `OXY-29`'s result file already notes `OXY-123` as "the DB analogue ... for `oxygen-sql` table/column schemas (not the migration-level `OXY-8` gate)" (`jira-issues/results/OXY-29.md:108` open question). That pre-existing cross-reference makes the intended division of `OXY-8` binary gate vs. `OXY-123` richer spec unambiguous.
*   **Code signal confirms absence and affordance.** Grepping for `DbCompat`, `SqlCompat`, `MigrationCompat` (outside `MigrationCompatibility`), `ColumnCompatibility`, `TableCompatibility`, and `oxygen.sql.*compat` across all modules returns only `MigrationCompatibility` / `MigrationGenerator.classify` / `MigrationCheck` and the `oxygen.schema.compat` package — no DB schema `Compared` / `ComparisonResult`-style library, no `TODO` pointing to it, no existing `oxygen.sql.schema.compat` package. Meanwhile `PersistedMigrationFile.scala:9-11` explicitly stores the full `state` snapshot to unlock "reverse / cross-version diffing later" — a deliberate affordance for exactly this kind of cross-snapshot `compare` spec, confirming the intended input shape (`MigrationState` vs `MigrationState`).
*   **Remaining uncertainty keeps rating at 4 not 5-6.** No Jira body was fetchable and the checklist title is only 6 words; the exact desired granularity (full `Compared`-lattice `ExactEqual` / `FromIsMoreSpecific` / `ToIsMoreSpecific` / `NotComparable` vs. keep binary `BackwardsCompatible` / `Incompatible` like `OXY-8`, whether the spec should also handle column `DEFAULT` values to make `NOT NULL` adds compatible, whether `Column.Type` narrowing semantics should be database-fidelity (Postgres cast rules) or conservative (any type change = breaking), and whether the spec should be `oxygen.schema.compat`-integrated or standalone in `oxygen-sql-migration`) is not written down. A plausible alternative reading — that "DB Schema" means `RawCompiledSchemas` / `JsonSchema` for DB-mapped JSON columns rather than `MigrationState` / `TableState` — is essentially the same type-level work but would shift the proposed package/mechanics, so a point of uncertainty remains.

If `OXY-8`'s binary `classify` is sufficient for now, `OXY-123` should still land the richer spec behind a `classifyIsCompatible` collapse so future harness iterations can surface per-column diagnostics without re-cutting the gate.

## Open Questions

- **Scope vs. OXY-8 — where is the boundary?** Does `OXY-123` include replacing `MigrationGenerator.classify` and wiring `MigrationCheck` through the new richer result, or is it spec-only (pure `compare` library) and `OXY-8`'s gate stays binary until a follow-up? The checklist title does not say "in-memory only" — propose spec-only with a thin `classifyIsCompatible` collapse as the default, but confirm whether a single PR should cut over `MigrationCheck` as well.
- **Compatibility table — which DB changes are breaking?** Confirm the intended rules for: (a) `Column.Type` transitions — is `SmallInt→Int→BigInt` widening compatible and `BigInt→Int` breaking, or is any type change breaking conservatively? How to treat `Array(elem)` element widening, `Vector(size)` changes, `LTree` extension changes? (b) `NOT NULL` adds with a DB `DEFAULT` — if `Column` gains a `default: Option[DefaultValue]` in future, should such adds be treated as `BackwardsCompatible`? (c) FK / unique index creation on an existing table with data — always breaking vs. breaking only when data violates the constraint (the current `createdTables` empty-table exception is the precedent)? A conservative default (any narrowing or `NOT NULL` without default = breaking, any constraint add on existing table = breaking) is implementable without blocking but should be ratified.
- **Binary vs. richer result lattice?** Should the DB spec expose the four-way `ExactEqual` / `FromIsMoreSpecific` / `ToIsMoreSpecific` / `NotComparable` lattice like `oxygen.schema.compat.ComparisonResult` (so callers can distinguish "to is a superset" vs "incompatible"), or a simpler `BackwardsCompatible` / `Incompatible` like `MigrationCompatibility`? The SQL migration path chose binary + semver major/minor; the schema path kept the richer lattice — which idiom should DB follow? Propose richer lattice internally with binary `isCompatible` collapse for `MigrationGenerator` consumers, but confirm.
- **Package location?** `oxygen.sql.migration.compat.DbCompatibilitySpec` (co-located with `MigrationState`/`TableState`/`MigrationGenerator`/`MigrationCheck` and near the `PersistedMigrationFile.state` snapshot input) vs `oxygen.sql.schema.compat.SqlSchemaCompatibility` (co-located with `Column.Type`/`TableRepr`) vs `oxygen.schema.compat` extension (shared with `OXY-29`'s HTTP spec). The spec and the existing gate should share an import path — pick one and keep `OXY-8` / `OXY-123` consistent.
- **Persist richer result or binary + snapshot?** `PersistedMigrationFile` already stores `compatibility: MigrationCompatibility` (binary) plus the full `state` snapshot. Should the file additionally store `dbComparisonResult: DbComparisonResult` (richer, JSON-serialized) for audit, or is binary + snapshot sufficient with the rich diff computed on the fly in CI logs? If richer is desired, the `formatVersion` bump and `JsonCodec` for `DbComparisonResult` are in scope.
- **Integration with `oxygen.schema.compat` for JSON-mapped columns?** Some DB columns are `TypedJsonb`/`Json`/`Jsonb` whose logical Scala types have `oxygen.schema` schemas. Should the DB spec delegate to `Compared.compareRoot` for those type parameters (so `Column.Type.Jsonb` with `String` vs `Option[String]` element types can be evaluated), or should DB stay strictly `Column.Type`-level and leave JSON-type evolution to `OXY-29`/`OXY-70`? If delegation is desired, the spec needs `FullCompiledSchemas` inputs alongside `MigrationState`.
- **OXY-123 vs. OXY-29 naming parallelism?** Confirm that `OXY-123` and `OXY-29` are intentionally parallel (DB vs. HTTP) and will share the same `Compared` / `AddedRemovedBoth` / `FromToValues` design language so the two specs stay conceptually aligned. Should a shared `oxygen.compat` trait or doc page describe the common lattice?

## Expanded Description

**What it likely means:** Build the **enforcement/CI-gating harness** that makes the HTTP compatibility spec actionable — the endpoint-schema analogue of `oxygen.sql.test.DbMigrationSpec` + `oxygen.sql.migration.MigrationCheck` (and the Avro `persist compiled schema, diff in CI, fail on breaking changes` paradigm referenced in `agent-docs/http-docs/http-feature-plan.md:74-76`).

`OXY-29` ("Create compatibility spec for HTTP Schema", also Higher) is the paired spec ticket: a pure, in-memory `compare(from: RawCompiledApiSpec, to: RawCompiledApiSpec): Compared[HttpComparisonResult]` library that codifies which HTTP structural changes are breaking vs. compatible (reusing `oxygen.schema.compat.Compared` / `ComparisonResult` / `AddedRemovedBoth` for the shared `schemas` bundle and adding endpoint/API rules on top). `OXY-38` is the **checking** half: persisting the compiled spec to a committed JSON file, diffing it against the current-code spec at test time, and failing CI on drift — with env-var-gated updates that distinguish compatible vs. breaking changes.

In concrete terms (mirroring `docs/docs/sql/migrations.md:28-61`):

* A committed artifact — e.g. `oxygen-http-api-spec.json` (or per-module `src/main/resources/oxygen-http-api-spec.json` / `src/test/resources/...`) — holds the last-approved `RawCompiledApiSpec` as JSON (via `JsonCodec[RawCompiledApiSpec]`, `withoutLineNos` for stability). One bundle file is expected (matching `RawCompiledApiSpec(apis, schemas)`), but a per-API sharding alternative should be considered and rejected/documented.

* A harness — e.g. `oxygen.http.test.ApiSpecCompatibilitySpec` or `EndpointSchemaCompatibilitySpec` in `modules/http/test-utils` (parallel to `modules/sql/test-utils/src/main/scala/oxygen/sql/test/DbMigrationSpec.scala:1-55`) and/or `oxygen.http.schema.compat.HttpApiSpecCheck` in `modules/http/zio` (parallel to `modules/sql/migration/src/main/scala/oxygen/sql/migration/MigrationCheck.scala:1-105`) — that:
  1. Re-compiles the current `Seq[EndpointSchema]` via `CompiledApiSpec.compileWithoutLineNos` (see `modules/http/zio/.jvm/src/main/scala/oxygen/http/schema/compiled/CompiledApiSpec.scala:18-42`).
  2. Loads the committed JSON file from the filesystem (`Path` / `MigrationFs`-like helper) and decodes it via `JsonCodec[RawCompiledApiSpec]`.
  3. Delegates comparison to the `OXY-29` spec (`compare(persisted, current)`) and maps the result to an outcome: `UpToDate` / `PendingUpdate` (compatible addition, needs commit) / `BlockedIncompatible` (breaking change, needs explicit allow).
  4. Exposes the same env-var gate as SQL migrations — e.g. `OXYGEN_HTTP_ALLOW_UPDATE` (write the new file instead of failing) and `OXYGEN_HTTP_ALLOW_INCOMPATIBLE` (additionally allow a breaking change to be written), mirroring `MigrationCheck.Config(allowUpdateEnv = "OXYGEN_MIGRATION_ALLOW_UPDATE", allowIncompatibleEnv = "OXYGEN_MIGRATION_ALLOW_INCOMPATIBLE")` at `MigrationCheck.scala:53-62` and the `docs/docs/sql/migrations.md:58-61` table.

* A reusable test base — e.g. `abstract class ApiSpecCompatibilitySpec extends OxygenSpecDefault` with abstract `def apiSpecPath: String` and `def currentEndpoints: Seq[EndpointSchema]` — that a service wires as:
  ```scala
  object MyApiSpecCompatibilitySpec extends ApiSpecCompatibilitySpec {
    override def apiSpecPath: String = "modules/my-service/src/main/resources/oxygen-http-api-spec.json"
    override def currentEndpoints: Seq[EndpointSchema] = summon[DeriveEndpoints[MyApi]].endpoints.map(_.schema)
  }
  ```
  The spec's single test (`"committed api spec is up to date"`) asserts `UpToDate`, otherwise fails with the pending diff or blocked-incompatible message (mirroring `DbMigrationSpec.scala:31-56`).

**Who it affects:** Any service that defines HTTP endpoints via `oxygen-http` (`modules/http/zio`, Epic `OXY-2`) and wants CI to reject accidental breaking API changes (removing an endpoint, tightening a param to `Required`, changing method/path, narrowing a body type) before merge — the same audience as `OXY-29`, but at the enforcement layer.

**Why it matters (Higher priority):** Without checking, the compiled spec (Phases 1–2, `RawCompiledApiSpec` served at `GET /oxygen/api-spec` via `ApiSpecEndpointMiddleware`) is observable but unenforced — review relies on human inspection of the JSON diff. The SQL migration track already has this gate (`DbMigrationSpec` / `MigrationCheck`), and the HTTP feature plan explicitly calls it out as Phase 4 pending: *"Persist the compiled spec (avro/sql-migration paradigm), diff via `oxygen.schema.compat` extended to the endpoint/API layer, fail CI on breaking changes; env-var-gated update."* (`http-feature-plan.md:74-76, 229-231`). `OXY-38` closes that loop for HTTP.

**Inferred acceptance criteria:**

* A committed JSON artifact path/convention is chosen and documented; `RawCompiledApiSpec` round-trips through `JsonCodec` with `withoutLineNos` (already verified in `CompiledApiSpecSpec.scala:36-41`).
* A filesystem helper (or reuse of `oxygen.zio.system.Path`) loads/writes the JSON file; a `HttpApiSpecCheck`-like object (or `ApiSpecCompatibilityCheck`) implements `check(dir/file, currentSpec, config): IO[Error, Outcome]` with `Outcome = UpToDate | Wrote | PendingUpdate | BlockedIncompatible`, branching on `config.allowUpdate` / `config.allowIncompatible` exactly like `MigrationCheck.scala:88-103`.
* A `Config.fromEnv` that reads `OXYGEN_HTTP_ALLOW_UPDATE` / `OXYGEN_HTTP_ALLOW_INCOMPATIBLE` with `truthy` parsing (`"true"|"1"|"yes"`), plus a `ci` default of `false/false` (mirroring `MigrationCheck.Config:56-68`).
* A `DbMigrationSpec`-like abstract test base that surfaces `PendingUpdate` / `BlockedIncompatible` as test failures with actionable messages ("Re-run with `OXYGEN_HTTP_ALLOW_UPDATE=true`..." / "...and `OXYGEN_HTTP_ALLOW_INCOMPATIBLE=true`"), and that uses `TestAspect.withLiveEnvironment` so `System.env` reads the real OS env (per `DbMigrationSpec.scala:50`).
* Integration with `OXY-29`'s comparison result: `PendingUpdate` when the diff is backwards-compatible (e.g. new optional param, new endpoint, widened sum), `BlockedIncompatible` when the diff is `NotComparable` / breaking (removed endpoint, method/path change, required-param addition, narrowed body). The mapping must be explicit; if `OXY-29` exposes a richer lattice (`ExactEqual`/`FromIsMoreSpecific`/`ToIsMoreSpecific`/`NotComparable`), `OXY-38` collapses it to the binary gate (`UpToDate` vs. `PendingUpdate` vs. `BlockedIncompatible`) — document the collapse.
* Tests that exercise the harness without needing a real server (compile two small `Seq[EndpointSchema]` fixtures or hand-build two `RawCompiledApiSpec` values, write one to a temp file, run `check`, assert outcomes). At minimum: identical specs → `UpToDate`; compatible addition (new optional query param) → `PendingUpdate` (and `Wrote` when `allowUpdate=true`); breaking change (remove endpoint) → `BlockedIncompatible` (and `Wrote` only when both flags true).
* Docs: `agent-docs/http-docs/http-feature-plan.md` Phase 4 section updated from stub (`http-feature-plan.md:229-231`) to describe the persist + check flow, plus a `docs/docs/http/` or `docs/docs/sql/migrations.md`-parallel section when `OXY-81` lands. Example service (`example/apps`) wires the new spec to demonstrate the loop.

## Open Questions

* **Env-var names?** `OXYGEN_HTTP_ALLOW_UPDATE` / `OXYGEN_HTTP_ALLOW_INCOMPATIBLE` mirror `OXYGEN_MIGRATION_ALLOW_UPDATE` / `OXYGEN_MIGRATION_ALLOW_INCOMPATIBLE` (`MigrationCheck.scala:53-54`, `docs/docs/sql/migrations.md:60-61`) and are the proposal — but alternatives like `OXYGEN_API_SPEC_ALLOW_UPDATE` or reuse of the migration vars are plausible. Confirm and grep for collisions before freezing; document in the env-var table.
* **Committed file path — single bundle or per-API sharded?** `http-feature-plan.md:346` explicitly flags "spec persisted as one bundle file, or per-API/per-endpoint files?" as open. Single `oxygen-http-api-spec.json` (the whole `RawCompiledApiSpec(apis, schemas)`) is simplest and matches `CompiledApiSpec.compile`'s single-bundle output; per-API sharding (`oxygen-http-api-spec/<apiName>.json`) gives cleaner diffs for large service sets but needs a directory scan and `AddedRemovedBoth` over files. Which does the team want? Default to single bundle unless told otherwise.
* **Dependency on OXY-29 — stub or wait?** Does `OXY-38` proceed in parallel with a stubbed `compare` (e.g. `from == to` equality only, flagged as stub) or must it wait for `OXY-29`'s `HttpComparisonResult` / `compare` to land? If parallel, how should the stub be marked so the gate is not mistaken for complete? If sequential, should the two be merged into one PR?
* **Package location?** `oxygen.http.schema.compat.HttpApiSpecCheck` (parallel to `oxygen.schema.compat` and co-located with `OXY-29`'s spec) vs. `oxygen.http.test.ApiSpecCompatibilitySpec` (parallel to `oxygen.sql.test.DbMigrationSpec` in a new `modules/http/test-utils`) vs. `oxygen.http.schema.compiled.compat` (nested under compiled). The spec and the check should share an import path — pick one and keep `OXY-29` / `OXY-38` consistent.
* **Outcome collapse — binary or richer?** Should the harness expose the same four-way lattice as `oxygen.schema.compat.ComparisonResult` (`ExactEqual` / `FromIsMoreSpecific` / `ToIsMoreSpecific` / `NotComparable` at `ComparisonResult.scala:7-60`) or collapse to the binary `UpToDate` / `PendingUpdate` / `BlockedIncompatible` like `MigrationCheck.Outcome` / `MigrationCompatibility` (`MigrationCompatibility.scala:11-13`)? The SQL path collapsed to binary + semver bump; the schema path kept the richer lattice — which idiom should the HTTP gate surface to callers? Propose binary for the gate with the richer `Compared.Result` retained in logs (`toIndentedString`).
* **Versioning — snapshot or semver?** SQL migrations version via `oxygen.core.Version` (semver, `GenerateResult.Generated` at `MigrationGenerator.scala`) because history is ordered and applied sequentially; HTTP spec checking may need only a single snapshot file (the current spec), not a versioned history. Should the committed file carry a `version` / `formatVersion` envelope (like `PersistedMigrationFile.currentFormatVersion`) or is a bare `RawCompiledApiSpec` JSON sufficient? If semver is desired, who bumps it and how does `bump` map to the HTTP compatibility table?
* **Live-endpoint vs. compiled-spec input?** The harness could take `Seq[EndpointSchema]` (live, via `DeriveEndpoints[MyApi].endpoints.map(_.schema)`) and compile internally, or take a pre-compiled `RawCompiledApiSpec` (pure).

## Expanded Description

**What this likely is:** The first shippable slice of a new `oxygen-tracing` capability, i.e. bootstrapping distributed tracing for the Oxygen stack (`oxygen-zio`, `oxygen-http` server/client, and by extension `oxygen-sql`/`oxygen-events`). This is the implementation task that follows Epic **OXY-107 — oxygen-tracing** (Normal). The title is 5 words with no Jira body, so scope must be inferred from the single existing tracing file in the repo and from parallel observability work.

**Current state (verified by reading the repo):**

1.  **A minimal `oxygen-tracing` seed already exists in `oxygen-zio`.** `modules/general/zio/src/main/scala/oxygen/zio/tracing/TraceState.scala` (40 lines, pure ZIO, no OTel dep) defines:
    *   `enum TraceState { Root(rootId: UUID), NonRoot(rootId, parentId, currentId) }` with helpers `current: UUID` and `rootAndNewParent: (UUID,UUID)`.
    *   `object TraceState` holding `FiberRef[Option[TraceState]]` (`Unsafe.unsafe.make(None)`), three header constants `X-Oxygen-Trace-Root` / `X-Oxygen-Trace-Parent` / `X-Oxygen-Trace-Id`, and two scoped constructors:
        *   `getOrSetRoot: URIO[Scope, TraceState]` — generates a new root UUID if absent, annotates the ZIO log context via `ZIO.logAnnotateScoped`, and scopes the `FiberRef` via `locallyScoped`.
        *   `setRootAndParent(rootId, parentId): URIO[Scope, TraceState]` — generates a fresh `currentId`, warns on override, annotates all three headers, scopes the new state.
    *   **No http integration.** `CompiledEndpoints.toRoutes`, `ZioHttpServer`, `CurrentRequest`, `ZioHttpClient` never reference `TraceState`. `grep -r TraceState` hits only `TraceState.scala` itself. No `zio-telemetry`, `opentelemetry-api`, `otel-sdk`, `jaeger`, `zipkin`, or `zio-metrics-connectors` dependency in `project/Dependencies.scala` or `build.sbt`.

2.  **HTTP server has request-scoped scaffolding that tracing can reuse.** `CompiledEndpoints.toRoutes(config)` already does `ReceivedRequest.fromRequest -> CurrentRequest.ref.locallyScoped` and `ZIO.logInfoAnnotated` for `method`/`path`/`code`. `CurrentRequest` stores the active request in a `FiberRef`. `AppliedEndpoint` exposes `metricLabels` (TODO) and `fullName`. Server startup is `ZioHttpServer.serve -> server.install(endpoints.toRoutes(config))`. No `RequestMiddleware`/`EndpointMiddleware` currently does tracing/header propagation.

3.  **Observability context.** Sibling observability work is in flight / todo: `OXY-5` (explore non-in-memory metrics — spike, recommends `zio-metrics-connectors` vs OTel), `OXY-56` (zio-metrics integration), `OXY-74`/`OXY-76` (logging http-server/client), `OXY-75`/`OXY-77` (metrics http-server/client), `OXY-93` Epic `oxygen-metrics`. Priority `Normal` (not Higher/High) suggests the first tracing slice is foundational but not blocking `oxygen-http-server` (Epic OXY-2) or `oxygen-sql` (Epic OXY-1) release.

**Most plausible interpretation (frontrunner):** Wire the existing `TraceState` into the http stack as the initial `oxygen-tracing` implementation, without yet taking a hard dependency on OpenTelemetry. Concretely:
*   Add a `TracingMiddleware` (or `RequestMiddleware` + `ResponseMiddleware` pair) that on each HTTP request reads `X-Oxygen-Trace-Root`/`X-Oxygen-Trace-Parent`/`X-Oxygen-Trace-Id` from incoming `Headers`, parses them as UUIDs, and scopes `TraceState` via `setRootAndParent` (or `getOrSetRoot` if headers absent). On the response path, echo `X-Oxygen-Trace-Root`/`X-Oxygen-Trace-Id` (and optionally parent) so the caller can correlate.
*   Add a client-side `RequestMiddleware`/`Client` wrapper that reads `TraceState.current` (or calls `getOrSetRoot` if absent), computes `rootAndNewParent`, and injects the three headers into outbound requests. Uses `ZIOAspect` / `FiberRefModification` helpers already present in `oxygen.zio.FiberRefModification` / `zioAspectHelpers`.
*   Expose a `ZIOAspect`/`FiberRefModification` / `ZLayer` helper for non-HTTP callers (e.g., `oxygen-sql` query execution, `oxygen-events` consumers) to run an effect with a trace — `Tracing.withTrace` / `Tracing.rootSpan(name)` / `ZIO.withTracing`.
*   Keep OTel out of this first slice **or** add a thin OTel bridge as an optional module (`oxygen-tracing-otel`) that mirrors `TraceState` into an OTel `Span`/`SpanContext` if the OTel SDK is on the classpath. The doc/design should state which path was chosen and leave a follow-up for full OTel exporter work under OXY-107.

**Why tracing matters now:** Without it, every `ZIO.logInfoAnnotated` in `CompiledEndpoints` and every `ZioHttpClient.logAtLevel` is uncorrelated across service hops. Even with `X-Oxygen-Trace-*` headers flowing, `oxygen-events` (Pulsar) and `oxygen-sql` duration metrics (`MetricBuilders`, `SqlMetrics`) cannot be joined to a request. The initial slice gives `Root/Parent/Current` IDs in logs + headers so subsequent OTel Jaeger/Tempo adoption is a layer swap rather than a rewrite.

**Who it affects:** Every service built on `oxygen-http` (server: `Server`, `CompiledEndpoints`, `AppliedEndpoints`; client: `Client`, `ZioHttpClient`) plus consumers that `ZIO.logAnnotateScoped` via `oxygen.zio.logging.Logger`. No end-user UI change; purely backend observability.

**Inferred acceptance criteria:**
1.  `TraceState` is no longer dead code — at least one server middleware and one client middleware (or a shared `Tracing` object) actually read/write the three `X-Oxygen-*` headers and scope the `FiberRef`.
2.  A request without tracing headers gets a new `Root`; a request with headers propagates `Root/Parent/Current` correctly and appears in log annotations (`X-Oxygen-Trace-Root`, `X-Oxygen-Trace-Id`, `X-Oxygen-Trace-Parent`) for every log line inside the handler (verified via `FiberRefs` / `currentLogAnnotations`).
3.  Existing `CompiledEndpoints` tests (`ViaHttpSpec`, `DirectSpec`) still pass with the default config (tracing on by default or opt-in via `Server.Config` flag — behaviour documented). No break to `Server.layer.simple` / `Server.Config.default`.
4.  Brief doc added (e.g., `docs/docs/tracing/index.md` or `agent-docs/tracing/initial-impl.md` plus update to `build.sbt` dependencies) explaining how to enable tracing and how to inject a trace in non-HTTP contexts.
5.  No OTel runtime required for the minimal acceptance (headers + logs only), but a design note records how OTel would be layered on (or a tiny `oxygen-tracing-otel` module is added with `opentelemetry-api` if the team chose OTel-first).

## Open Questions

1.  **OTel vs header-only:** Is this slice expected to introduce an OpenTelemetry dependency (`opentelemetry-api` / `zio-telemetry-opentelemetry` + OTLP exporter) or to ship the header-only `TraceState` wiring as v1 and defer OTel to a follow-up under Epic OXY-107? `OXY-5` explicitly calls out `zio-telemetry` / OTel as the future path for metrics + tracing — should OXY-108 align with that now?
2.  **Propagation scope:** Must tracing propagate only over HTTP headers (server `RequestMiddleware` + client `RequestMiddleware`), or also over Pulsar/event messages (`EventProducer`/`EventConsumer` headers/attributes) and into `oxygen-sql` / `QueryContext` spans? Does `oxygen-events-in-memory` need in-process propagation at all?
3.  **Header format:** The existing code uses custom `X-Oxygen-Trace-Root` / `X-Oxygen-Trace-Parent` / `X-Oxygen-Trace-Id` (verified in `TraceState.scala:15-17`). Should OXY-108 keep those, adopt W3C `traceparent`/`tracestate`, or support both (read both, write one)? W3C would ease interop with external services / Otel collector; custom is already coded.
4.  **Span model & timing:** Does `oxygen-tracing` need explicit spans with start/end timing (and `MetricBuilders.microTimer` integration) in this first slice, or is `TraceState` FiberRef + log annotation sufficient? Should `CompiledEndpoints.handle` emit a span duration that `oxygen-metrics` (OXY-93) can observe, or should metrics stay separate?
5.  **Config surface & defaults:** Should tracing be enabled by default (`Server.Config.tracing.enabled = true`) or opt-in? Is it `Server.Config.tracing: Option[TracingConfig]` (so `Server.Config.default` is unchanged) or a standalone `Tracing.layer: ZLayer[Any, Nothing, Tracing]` that server/client compose? 6.  **OTel module placement & platform:** If OTel is in scope, should the new code live inside `modules/general/zio` (JVM-only, since OTel Java SDK is JVM) or as a new `modules/tracing/` cross-project (JVM-only with JS/Native stubs)? Should `ViaHttpSpec`/`DirectSpec` have a `defaultTraceState` or `disableTracing` hook similar to the commented `defaultLogLevel` precedent? Confirmed by package proximity and Epic adjacency, but worth explicit sign-off.

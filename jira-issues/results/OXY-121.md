## Expanded Description

**What this likely is:** Extend the `oxygen-meta` derivation kernel (`oxygen.meta.k0.Generic` / `SumGeneric` / `Derivable`) so that **Scala 3 union types** (`A | B`, `A | B | C`, nullable `A | Null`, `Option`-like unions) can be treated as **sum types** for typeclass derivation — i.e. the same `derives JsonCodec` / `derives JsonSchema` / `derives TypeTag` machinery that works for `sealed trait Foo { case Bar; case Baz }` should also work for `type MyUnion = Bar | Baz` or `type JsonValue = String | Int | Boolean | Null`.

Canonical motivating shapes (all inferred from title + code; no Jira body was fetchable):

```scala
// 1 — transparent alias for a 2-way union (the minimal case)
type StringOrInt = String | Int
given JsonCodec[StringOrInt] = JsonCodec.derived  // should try String then Int

// 2 — domain DTO union (named case classes as members)
type ApiResult = Success | Failure
final case class Success(value: String) derives JsonCodec
final case class Failure(msg: String) derives JsonCodec
given JsonCodec[ApiResult] = JsonCodec.derived   // union as ad-hoc sealed sum

// 3 — nullable / Option-like union
type MaybeString = String | Null   // or String | None.type

// 4 — 3+ way union
type Poly = A | B | C
```

Today this does **not** work through `Derivable`:

- `Generic.of[A]` (`modules/general/core/src/main/scala/oxygen/meta/k0/Generic.scala:321-328`) dispatches only on `TypeType.Case` → `ProductGeneric.unsafeOf` or `TypeType.Sealed` → `SumGeneric.unsafeOf`. A union `A | B` (`OrType` in `oxygen.quoted.TypeRepr` → `quotes.reflect.OrType`) has no single `Symbol` with `Sealed` type and no `children` to enumerate — it hits the `case _ => report.errorAndAbort("Not a sum type...")` path in `Generic.of` / `SumGeneric.of` and must be hand-written per typeclass.
- `SumGeneric.unsafeOf` itself (`modules/general/core/src/main/scala/oxygen/meta/k0/SumGeneric.scala:131-395`) assumes `sym.children` + `resolveChildAppliedArgs` + `childGenericsRec` over `Symbol`-based sealed children. It has **no `OrType` branch** — confirmed: `grep OrType SumGeneric.scala` returns zero hits; only `TypeRepr.scala:180-182` defines `orChildren` and `DeriveTypeTag.scala:263-268` handles `OrType` for `TypeTag`, and `UnionRemoving.scala` (`modules/general/core/src/main/scala/oxygen/meta/typing/UnionRemoving.scala:40-122`) already shows how to decompose unions via `TypeRepr.dealiasKeepOpaques.orChildren` into `Set[TypeRepr]`.
- The only existing union-aware derivation is `DeriveTypeTag` (`modules/general/core/src/main/scala/oxygen/core/generic/DeriveTypeTag.scala:87-89,172-174,263-268`) which emits `TypeRef.Union` for `OrType` — but `oxygen-json`, `oxygen-schema`, `oxygen-meta` (`FromExprT`/`ToExprT`/`Show`) have no equivalent `OrType` sum-deriver.
- `UnionRemoving[Total, Removing]` (`modules/general/core/src/main/scala/oxygen/meta/typing/UnionRemoving.scala:16-122`) is the closest prior art for unions: it computes `Remaining` from `Total | Removing` via `orChildren` set subtraction + `OrType` recombination and summons `TypeTest` for runtime dispatch. It is a *filtering* helper, not a *derivation* helper, but it proves the `orChildren` + `OrType.companion.apply` pattern the fix would reuse.

**What "better support" plausibly means (two levels, likely both in scope):**

1. **Level 1 — `Generic`/`Derivable` recognise `OrType` as a sum.** `Generic.of[A | B]` returns a `SumGeneric`-like `Generic[A | B]` whose `children` are `ProductOrSumGeneric` (or `IdentityGeneric`) for each `orChildren` member, so `Derivable[F].derived[A | B]` works whenever `F[A]`, `F[B]` exist. This is the direct "union as sum type" reading. It mirrors how `TypeTag` already treats `A | B` as `Union(Set(...))` and how `SumGeneric.EnumGeneric.extractReturnCaseClasses` (`SumGeneric.scala:559-571`) already handles `case or: OrType => ArraySeq.from(or.orChildren).flatMap { extractSum }` for enum-like unions — the kernel just needs the same at the `Generic` dispatch level.

2. **Level 2 — Per-typeclass codec friendliness for unions.** `JsonEncoder`/`JsonDecoder`/`JsonCodec`/`JsonSchema` need a union sum-deriver that (a) encodes by trying each member's encoder (`TypeTest`-dispatch or `isInstanceOf` chain, like `UnionRemoving`'s `TypeTest` dispatch at `UnionRemoving.scala:94-102`), and (b) decodes by trying members in order until one succeeds (order is user-visible for overlapping unions like `Int | String` where `"123"` could be either). This may require a discriminator strategy (try-each vs. type-field vs. shape-based) analogous to `SumGeneric.OrdinalStrategy`. Level 1 alone makes derivation *possible*; Level 2 makes the resulting codec *useful* and is where "better support" vs. "minimal support" diverges.

**Who it affects:** Any module that models ad-hoc alternatives without a wrapping `sealed trait` — domain results (`Success | Failure`), config variants (`String | Int | Boolean`), API polymorphism without a shared sealed parent, and utility types (`A | Null` for nullable interop). Today these must either wrap in a `sealed trait` (extra allocation + `.asInstanceOf` ceremony) or hand-write `JsonCodec`/`JsonSchema` per union shape. `oxygen-json` (`JsonDecoder`/`JsonEncoder`), `oxygen-schema` (`JsonSchema`), `oxygen-transform` (`Transform` for `A | B -> C | D`), and `oxygen-meta` consumers (`FromExprT`/`ToExprT`/`TypeTag`) would all benefit if unions were first-class sums.

**Why it matters (Normal priority, not Higher):** Compared to OXY-119 (generic sums, `Higher` — blocking `sealed trait Foo[A]` derivation), unions are a convenience / completeness feature for a newer Scala 3 idiom. OXY-118 `oxygen-meta` already has a working sealed-sum kernel; unions are the next natural extension but not a blocker for the existing sealed-trait code. `Normal` signals "fill the gap after OXY-119 ships" rather than "unblock current users". It also pairs with OXY-120 (class-creation helpers): once unions are sums, macros that generate classes may want to generate union aliases too, and `ProductGenericSubset` / `MatchBuilder` / `CaseExtractor` already handle union-like dispatch for `Either`-like shapes.

**Inferred acceptance criteria:**

1. `Generic.of[A | B]` (and `A | B | C`, `A | Null`) succeeds where it previously aborted — i.e. `given Generic[String | Int] = Generic.of[String | Int]` compiles, `generic.children.size == 2` (or N for N-way), and each child generic is the correct `ProductGeneric`/`IdentityGeneric` for its member type (verified via `generic.toIndentedString` or similar).
2. `derives` / `Derivable.derived` works for unions for at least `JsonCodec`, `JsonSchema`, `FromExprT`/`ToExprT` (and ideally `Show`/`Transform`): e.g. `type SI = String | Int; given JsonCodec[SI] = JsonCodec.derived` round-trips (`directRoundTripTest[SI]` for `String` value and `Int` value), and `type AB = A | B` where `A`, `B` are case classes derives and distinguishes members correctly.
3. Codec behavior is specified: encoding dispatches on runtime type (`TypeTest` or `isInstanceOf`, as in `UnionRemoving`), decoding tries members in declaration order (`A | B` tries `A` first, then `B`) and succeeds on first match; overlapping unions (`Int | String` with JSON number `"123"` vs string) follow that order deterministically. Documented in Scaladoc/comment.
4. Edge cases: `A | A` (duplicate), `A | Nothing`, `A | Any`, nullable `A | Null`, and deeply nested ` (A | B) | C ` (which is `A | B | C` after `orChildren` flattening) either normalize correctly or fail with a clear `report.errorAndAbort` mentioning unsupported union shape. `orChildren` de-aliasing via `dealiasKeepOpaques` is reused (as `UnionRemoving` does) so opaque aliases decompose correctly.
5. No regression for sealed sums: `sealed trait Foo derives JsonCodec` with `SumGeneric.FlatGeneric` / `NestedGeneric` / `EnumGeneric` continues to work; `ProductGeneric` / `ProductGenericSubset` / `MatchBuilder` behavior unchanged. Existing `JsonSpec` / `MacroSpec` / `TypeTagSpec` suites remain green.
6. Tests + docs: at least one test file demonstrates union derivation round-trips (e.g. `modules/tests/pre-test-unit-tests/src/test/scala/oxygen/json/JsonUnionSpec.scala` or extensions to `JsonSpec.scala` alongside `GenericSum1`), and `docs/docs/metaprogramming/meta.md` gets a short "Unions as sums (`A | B`)" section explaining the feature and its ordering semantics.

## Open Questions

1. **Should unions reuse `SumDeriver` or get a dedicated `UnionDeriver[ F, A]`?** Title says "treating unions as sum types" suggests reuse (union members as sum cases), which would make `given JsonCodec[String|Int] = JsonCodec.derived` work with no new per-typeclass API. But union encoding (runtime-type dispatch vs. discriminator field) differs from sealed sums; does the product owner want distinct codec behavior? Recommendation: start with reuse (`UnionGeneric` extending `ProductOrSumGeneric` so `SumDeriver` applies), add a dedicated `UnionDeriver` only if codec tests require distinct semantics.
2. **What is the declaration-order vs. specificity dispatch rule for overlapping unions?** For `type Overlap = Int | String`, JSON `123` (number) vs `"123"` (string) are unambiguous, but `type S = SmallInt | Int` where both decode `123` could overlap. Should decoding try members in `A|B` declaration order (as written) or in specificity order (more specific first)?

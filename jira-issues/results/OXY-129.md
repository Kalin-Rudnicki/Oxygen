**Domain interpretation — what "grammar re-shuffling to prevent conflicts" means:**

In parser generators, "conflicts" are ambiguities where the parser cannot decide how to proceed — classically **shift/reduce** and **reduce/reduce** conflicts in LR/LALR grammars, or **ordered-choice shadowing** in PEG grammars, or **FIRST/FOLLOW** overlaps in LL(k) grammars. "Re-shuffling" means automatically reordering, factoring, or rewriting the grammar so these conflicts disappear:

1. **Reordering alternatives within a production** — e.g. in a PEG (ordered-choice) grammar, `expr := addition | atom` vs `expr := atom | addition` — trying longer/more-specific alternatives first prevents premature matching. Auto re-shuffling would sort alternatives by specificity or length.
2. **Left-factoring common prefixes** — e.g. `stmt := "if" expr "then" stmt | "if" expr "then" stmt "else" stmt` shares a prefix that causes LL conflicts; factoring to `stmt := "if" expr "then" stmt ("else" stmt)?` eliminates the conflict.
3. **Precedence/associativity reordering** — e.g. `expr := expr "+" expr | expr "*" expr | atom` is ambiguous; re-shuffling by precedence level (`atom` lowest, `*` higher than `+`) or rewriting to stratified nonterminals (`expr → term → factor`) prevents conflicts.
4. **Eliminating left-recursion / shuffling rule order** — LR grammars tolerate left-recursion but LL grammars do not; reordering or rewriting `A := A "a" | "b"` to `A := "b" A'` prevents infinite recursion.

The title says "re-shuffling" (not "left-factoring" or "precedence declarations"), which most directly suggests **(1) — automatically permuting the order of alternatives/productions and testing for conflict-freedom**, possibly with a heuristic or brute-force search over permutations. This is a known technique for PEG and for LALR grammars where production order affects conflict resolution (e.g. Bison's default shift-over-reduce depends on rule order).

**Who it affects:** Future users of `Slyce` who author grammars via the macro DSL (per OXY-128: `macro-based Sylce impl`). Without re-shuffling, users must manually diagnose conflict reports and reorder their grammars by hand — error-prone and opaque. With it, the library either silently picks a conflict-free ordering or reports that no ordering suffices.

**Why it matters (Priority Normal):** Grammar conflicts are the primary usability pain point of any parser generator. If Slyce reports conflicts without offering an automatic fix, adoption suffers. Priority Normal (vs OXY-128 High) suggests this is not needed for the initial prototype but is important for making the grammar authoring experience tolerable after the core macro machinery works. It is a DX/polish feature on top of the initial impl.

**Inferred acceptance criteria (minimal viable):**

1. Given a Slyce grammar that has at least one conflict under its current rule/alternative order but is conflict-free under some permutation, invoking the re-shuffling pass produces a conflict-free grammar that is semantically equivalent (same language) and the parser generated from the shuffled grammar parses correctly.
2. The pass is either automatic (applied by the macro at compile time when conflicts are detected) or opt-in (e.g. `Grammar(...).reshuffled` / `@reshuffle` annotation) — the title does not specify; automatic-with-fallback is assumed as the more useful default.
3. If no permutation eliminates conflicts, the pass reports the remaining conflicts clearly rather than silently picking a broken ordering.
4. The transformation preserves semantics — reordering does not change which strings are accepted, only how conflicts are resolved (or, for PEG, documents that ordered-choice semantics may shift and requires explicit disambiguation).
5. Existing Slyce tests (from OXY-128) continue to pass; no change to the macro's public API beyond the new opt-in/auto pass.

## Open Questions
- **What grammar formalism does Slyce use?** PEG (ordered choice, no conflicts in the LR sense — "conflicts" would be shadowing/unreachable alternatives), CFG for LALR table generation (shift/reduce, reduce/reduce), or LL(k) (FIRST/FOLLOW)? The answer determines what "re-shuffling" can do and what "conflict" means. Most likely PEG given Scala 3 macro parser combinators, but unconfirmed.
- **What does "re-shuffling" specifically mean?** Permuting alternatives within a production? Reordering productions? Left-factoring? Stratifying by precedence? Removing left-recursion? The title says "re-shuffling" (permutation), not "factoring" or "precedence", so alternative permutation is assumed, but should be confirmed.
- **Automatic or opt-in?** Should the macro automatically reshuffle any grammar with conflicts, or should the user annotate `Grammar(...).reshuffled` / `@reshuffle`? Automatic is more ergonomic but changes PEG ordered-choice semantics silently; opt-in is safer but requires user awareness.
- **Semantic guarantee:** Must the reshuffled grammar accept exactly the same language as the original (true reshuffle), or may it resolve ambiguity by committing to one parse (PEG semantics where order matters)? If PEG, reordering *changes* the language for ambiguous inputs — is that acceptable?
- **Search strategy and bound:** Exhaustive search over all permutations is exponential (`n!`). For a production with 10 alternatives, `10! = 3.6M` candidates is infeasible. What bound and heuristic should be used? (e.g. exhaustive up to `n=6`, heuristic sort by specificity beyond that.)
- **Source positions and diagnostics:** When the grammar is reshuffled, should error messages and conflict reports still refer to the author's original order, or to the reshuffled order? Preserving original positions is friendlier but requires mapping.
- **Dependency on OXY-128:** OXY-129 cannot be implemented until OXY-128's Grammar IR, conflict ADT, and macro pipeline exist. What is OXY-128's timeline and what does its IR look like? Is there a draft branch or design doc not in this worktree?

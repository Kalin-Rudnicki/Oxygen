## Expanded Description

**What this likely is:** Replace the stub `ServerErrorHandler.notHandled` instances for the framework's "provided" (generic / out-of-the-box) error model types with real `convertCause` implementations that map `ExtractedCauses[RequestDecodingFailure]` (request-decode failures) and `ExtractedCauses.NoFailures` (defect/die/interrupt — i.e. handler threw / fiber died) into a typed value of `E` so it is rendered through `errorResponseCodec.encodeResponse(typedError)` with the correct per-case `StatusCodes` status, instead of falling through to the generic fallback in `DerivedServerEndpointImpl.makeErrorResponse`.

Today `modules/http/zio/.jvm/src/main/scala/oxygen/http/server/ServerErrorHandler.scala:7-47` provides:

* **Real:** `HttpDecodingFailure` and `RequestDecodingFailure` → `cause.eitherFailure.toOption` (returns the `RequestDecodingFailure` itself, rendered via its `ResponseCodec`/`JsonSchema` with `400 BadRequest`).
* **Stub (`notHandled` → `None` always):** `Throwable`, `String`, `Nothing`, `RawResponse`, `RawResponseText`, `RawErrorResponse`, `RawErrorResponseText`.

When a handler is `notHandled`, `DerivedServerEndpointImpl.makeErrorResponse:223-236` falls through to:

```scala
case None =>
  extracted match {
    case failures: ExtractedCauses.Failures[RequestDecodingFailure] =>
      val status = if failures.failures.exists(_.value.isMissingAuth) then Status.Unauthorized else Status.BadRequest
      Response(status, BodyUtil.usingJsonSchema(serverErrors(failures, config)))
    case noFailures: ExtractedCauses.NoFailures if exposeInternalErrors =>
      Response(InternalServerError, BodyUtil.usingJsonSchema(serverErrors(noFailures, config)))
    case _: ExtractedCauses.NoFailures =>
      Response.status(InternalServerError) // empty body
  }
```

That is a generic `400`/`401` with `ServerErrors` JSON (or empty `500`) that does **not** use the caller's `errorResponseCodec`. A "real" handler returns `Some(typedError)` so the caller gets `errorResponseCodec.encodeResponse(typedError)` — e.g. a `String` body with the decode message, a `Throwable`/`HttpDecodingFailure` with its own status, or `RawErrorResponse(status=400, headers, body=ServerErrors JSON)` with full control over headers.

The same `notHandled` pattern appears in example-provided domain/API error models that are also "provided models" in the example app sense:

* `example/apps/web-server/src/main/scala/oxygen/example/webServer/api/givens.scala:52` — `given ServerErrorHandler[UIApiError] = ServerErrorHandler.notHandled`
* `example/apps/web-server/src/main/scala/oxygen/example/webServer/mcp/NoteApi.scala:28` — `given ServerErrorHandler[NoteError] = ServerErrorHandler.notHandled`
* `modules/http/zio/src/main/scala/oxygen/http/api/givens.scala:6` — `given ServerErrorHandler[ResourceApi.ApiError] = ServerErrorHandler.notHandled` (experimental)
* On the client side, `example/modules/api-models/src/main/scala/oxygen/example/api/model/error/RegistrationError.scala:19` and `UIApiError.scala:15` are `ClientErrorHandler.notHandled` — the symmetric OXY-116. The server-side stubs are the server mirror.

The intent of the pair OXY-116/OXY-117 is therefore to close the gap where the happy-path `ErrorConverter[DomainError, ApiError]` (`CurrentRequest.handle` / `_.toApi.asRight` in `givens.scala:54-57`) is real, but the **framework-error path** (bad request body, missing auth header, handler defect) for generic / provided error types is not — so users who declare `IO[String, A]` or `IO[Throwable, A]` or `IO[RawErrorResponse, A]` or who start from the `UIApiError`/`NoteError` scaffold get surprising empty `500`s or `ServerErrors` JSON instead of typed errors with correct `@statusCode` mapping via `StatusCodes`.

**Who it affects:** Any `oxygen-http-server` user who (a) uses a generic error type (`String`, `Throwable`, `HttpDecodingFailure`, `RequestDecodingFailure`, `Raw*`) as `E` in `Api derives DeriveEndpoints` (`ZIO[Scope, E, A]`), or (b) scaffolds from the example app's `UIApiError`/`NoteError` or `ResourceApi` experimental API and expects request-decode failures (`400`/`401` for bad body / missing auth) and handler defects (`500`) to surface as typed `E` cases (`@statusCode.BadRequest DecodingFailure(...)`, `@statusCode.InternalServerError`) rather than opaque `ServerErrors`.

**Why it matters (Priority Higher):** Without real handlers, `400` vs `401` vs `500` semantics are inconsistent: a handler that declares `IO[String, A]` will never see a `String` on decode failure — the client receives a JSON `ServerErrors` payload that `ResponseCodec[String]` cannot decode, surfacing as a `ResponseDecodingFailure` client-side. For `UIApiError`/`NoteError` the same: a `400` decode failure is not mapped to `UIApiError.BadRequest` / `NoteError.*` as the example's `ApiError`/`RegistrationError`/`LoginError` handlers do — so consumers cannot match on typed errors. The defect path (`NoFailures` → `500`) is also significant for observability: `ServerErrorConfig.exposeInternalErrors` + `ServerErrors.fromCause` controls trace inclusion, and `notHandled` forces the generic branch even when a typed `500` case (`@statusCode.InternalServerError`) exists.

**Inferred acceptance criteria:**

1. `ServerErrorHandler[String]` is real: `Failures` → `Some(failures.head.value.show)` (or `failures.map(_.value.show).mkString("; ")`) and `NoFailures` → `Some(errorConfig.serverErrors(noFailures).toString)` or `None` → generic `500` depending on `exposeInternalErrors` — consistent with `ClientErrorHandler[String].wrapDecodingFailure => Some(error.safeGetMessage)` and with `givens.scala:24` `DecodingFailure(failures.head.value.show)`.
2. `ServerErrorHandler[Throwable]` is real: likely `given throwableSubtype`-style or `new ServerErrorHandler[Throwable] { convertCause = cause.eitherFailure.map(_.value: Throwable).orElse(cause match { case NoFailures => serverErrors(...).asException }) }`, analogous to `ClientErrorHandler.throwableSubtype`.
3. `ServerErrorHandler[Raw*]` variants are real: `Failures` → `Some(RawErrorResponse(Status.BadRequest or Unauthorized, headers, BodyUtil.usingJsonSchema(serverErrors(failures, config))))` (or `RawResponse`/`RawResponseText` with text body), and `NoFailures` → `RawErrorResponse(Status.InternalServerError, ...)` respecting `exposeInternalErrors` — so callers using raw responses can still get a well-formed body.
4. Example-provided models `UIApiError` (+ `NoteError`, `ResourceApi.ApiError` experimental) get real handlers mirroring `ApiError`/`RegistrationError`/`LoginError` in `givens.scala:17-50`: `Failures` → `UIApiError.BadRequest(failures.head.value.show)` and `NoFailures` → if a `@statusCode.InternalServerError` case exists, map to it via `errorConfig.serverErrors(noFailures)`, otherwise `None` is acceptable — at minimum decode failures must not be `notHandled`.
5. Existing real handlers (`HttpDecodingFailure`, `RequestDecodingFailure`) remain unchanged; `Nothing` stays `notHandled` (there is no value to return; generic fallback is correct).
6. Tests: `it-test` or `zio/test` proving `DerivedServerEndpointImpl` with `E=String` / `E=Throwable` / `E=RawErrorResponse` and `E=UIApiError` decodes a bad request (empty body, wrong shape, missing `Authorization`) as `400`/`401` with typed body that `ResponseCodec[E]` can decode, and a handler that `ZIO.die`s surfaces as typed `500` when `exposeInternalErrors=true` and as empty `500` when `false` (mirroring `ClientErrorHandler` `wrapDeath`/`wrapDecodingFailure` split). Existing `givens.scala:17-27` `ApiError` handler is the reference.
7. Docs: one paragraph in `docs/docs/http/server/index.md` (currently `TODO : Oxygen HTTP Server`) describing when to use which error type and how `ServerErrorHandler` + `ServerErrorConfig` + `ErrorConverter` interact (`CurrentRequest.handle` for domain→api, `ServerErrorHandler` for framework→api).

## Open Questions

1. **Which "provided models" are in scope?** Is the fix for framework-provided generics only (`String`, `Throwable`, `HttpDecodingFailure`, `RequestDecodingFailure`, `RawResponse`/`RawResponseText`/`RawErrorResponse`/`RawErrorResponseText`, `Nothing`) in `ServerErrorHandler.scala`, or also for example-provided scaffold errors (`UIApiError`, `mcp.NoteError`, `ResourceApi.ApiError` experimental) in `example/` and `modules/http/zio/src/main/scala/oxygen/http/api/givens.scala:6`? Both are `notHandled` today, but the title could mean either. Proposed: do framework generics (all except `Nothing`) + update the two example scaffolds as demonstrative fixes; leave `ResourceApi.ApiError` (`@experimental`) as `notHandled` unless its `ResponseCodec` is real.

2. **What should `ServerErrorHandler[String]` encode?** Confirm status/body: `Failures` → `Status.BadRequest` (or `Unauthorized` on `isMissingAuth`) with body `failures.head.value.show` plain text (`MediaType.text.plain`) or JSON string (`"\"..."\""`)? `ClientErrorHandler[String]:62` uses `safeGetMessage` for response decode failures, but server side has `RequestDecodingFailure.show` with `sources` + `DecodingFailureCause`. Should the `NoFailures` branch (handler defect) return `Some(exposeInternalErrors ? ServerErrors JSON as string : "")` or `None` → generic empty `500`? `givens.scala:26` maps `NoFailures → InternalServerError(serverErrors(...))` (which itself is `Option.when(exposeInternalErrors)`), so for `String` the analog is `errorConfig.serverErrors(noFailures).map(_.toString).orElse(None)` — confirm.

3. **What should `ServerErrorHandler[Throwable]` wrap on defect?** On `Failures`, returning `cause.eitherFailure` (`RequestDecodingFailure` as `Throwable`) is clear. On `NoFailures` (handler threw), should it wrap `ServerErrors` as a synthetic `RuntimeException`, re-throw the original defect `Cause[Throwable]`, or return `None` (generic `500`)? For observability, returning a `Throwable` that contains the `ServerErrors` JSON may duplicate `ServerErrorConfig.withDefaults.includeTraces` logic — decide whether to preserve `Cause` traces in the `Throwable`'s `StackTrace`.

4. **How should `Raw*` handlers set `Headers`/`Status`?** For `Failures`, the fallback in `DerivedServerEndpointImpl:229` sets `Unauthorized` vs `BadRequest` based on `isMissingAuth`. Should `RawErrorResponse` handler replicate that status logic and also forward any `ReceivedRequest.headers` (e.g. `WWW-Authenticate: Basic realm="..."` or `Bearer` challenge)? For `NoFailures`, always `500` with `BodyUtil.usingJsonSchema(serverErrors(...))` when `exposeInternalErrors`, else empty body — confirm `RawResponse` vs `RawErrorResponse` `ExpectedStatuses` range (`All` vs `Error`) still matches after the handler returns typed `Raw*`.

5. **Should `Nothing` stay `notHandled`?** There is no value of type `Nothing` to return, so `None` → generic `500` is the only sensible semantics. Confirm this is intentional and should be documented as such (rather than "real" in title meaning it should somehow synthesize a `Nothing`).

6. **Should `UIApiError`/`NoteError` gain an `InternalServerError` case?** Today `UIApiError.scala:6-11` has only `ResourceNotFound` (`404`) and `BadRequest` (`400`), no `500`. Without a `500` case, `NoFailures → InternalServerError(...)` (like `ApiError:26`) is impossible, so the only options are `None` → generic empty `500` or adding a new `case InternalServerError(error: Option[ServerErrors]) @statusCode.InternalServerError`. Adding a case is a minor API break for consumers who match exhaustively — is it desired, or should those scaffolds remain `None` on defects? `RegistrationError`/`LoginError` both have `InternalServerError` (lines 15, 15), `ApiError` has it, `UIApiError` does not — suggests it was intentionally minimal scaffold.

7. **ResponseCodec requirement for new `E` types:** Does `String` / `Throwable` / `Raw*` already have a `ResponseCodec[E]` in scope (via `StringCodec`/`JsonSchema`/`RawResponse` companion), or does adding a real `ServerErrorHandler[String]` also require adding `given ResponseCodec[String]` (e.g. `ResponseCodec.Standard(StatusCodes.Exact(Status.BadRequest), ResponseCodecNoStatus.sseBody ...)` is not right for string errors)? `modules/http/zio/src/main/scala/oxygen/http/core/ResponseCodec.scala` and `modules/http/zio/src/main/scala/oxygen/http/model/rawResponse.scala:9` show `Raw*` have codecs; verify `String` and `Throwable` do.

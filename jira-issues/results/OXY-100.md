## Expanded Description

**What this likely is:** Add `GROUP BY` support to the hand-written query DSL (`modules/sql` — `@compile` / `QueryIO.compile` + `QueryO.compile`) so `SELECT ... FROM ... JOIN ... WHERE ... GROUP BY ...` queries can be written and compiled to SQL at compile time.

Today `oxygen-sql` DSL (`modules/sql/core/src/main/scala/oxygen/sql/query/dsl/Q.scala`, `T.scala`, `docs/docs/sql/queries.md:116-129`) supports `select[A]` (or `select.subQuery`), `join`/`leftJoin`, `where`, `orderBy`, `limit`, `offset`, `Q.insert`/`update`/`delete`, and aggregates `count.*` / `count(field)` / `Q.count(field)`. There is **no `GROUP BY` / `HAVING` support** — verified by grep: `modules/sql/core/src/main/scala/oxygen/sql/generic/model/ParsedQuery.scala:165-244` (`SelectQuery` case class) has fields `select`, `joins`, `where`, `orderBy`, `limit`, `offset`, `ret` with no `groupBy`/`having`; `modules/sql/core/src/main/scala/oxygen/sql/generic/model/part/` contains `WherePart`, `OrderByPart`, `LimitPart`, `OffsetPart`, `JoinPart`, `SelectPart` with no `GroupByPart`; `modules/sql/core/src/main/scala/oxygen/sql/generic/generation/FragmentBuilder.scala:292-417` has `select`/`join`/`where`/`orderBy`/`limit`/`offset`/`ret` with no `groupBy` branch; `modules/sql/core/src/main/scala/oxygen/sql/generic/model/QueryExpr.scala` / `RawQueryExpr.scala` / `BinOp.scala` have no grouping construct; `docs/docs/sql/queries.md` DSL vocabulary table lists no `group by`. Attempting `groupBy(p.groupId)` or `Q.groupBy(...)` in a comprehension either fails to compile in the macro ("not a query expr") or is parsed as plain Scala with no SQL emission.

Postgres/SQL `GROUP BY` has a few facets — title's brevity leaves which subset is intended ambiguous, but all reduce to the same missing DSL+SQL-generation gap:

1. **Simple `GROUP BY` on one or more columns (primary interpretation):** `SELECT p.groupId, COUNT(*) FROM person p GROUP BY p.groupId` / `SELECT p.groupId, COUNT(p.id) FROM person p GROUP BY p.groupId ORDER BY p.groupId` — grouping by query-field refs (`p.groupId`, `p.status`, `p.teamId`) with `count.*` / `count(field)` aggregates in `RETURNING`/`yield`. Multi-column: `GROUP BY p.groupId, p.status`.
2. **`GROUP BY` + `HAVING`:** `GROUP BY p.groupId HAVING COUNT(*) > 5` / `HAVING COUNT(p.id) > $n` — post-aggregation filter. Often co-requested with `GROUP BY`; worth deciding whether `HAVING` is in scope for this issue or deferred.
3. **Expression `GROUP BY` (follow-up):** `GROUP BY DATE_TRUNC('day', n.createdAt)` or `GROUP BY p.groupId || p.status` — grouping by scalar expression, not just field ref. Less likely as minimal viable scope.
4. **Grouping with `DISTINCT ON` vs `GROUP BY`:** Postgres allows `SELECT DISTINCT ON (col) ...` as alternative; not part of this issue.

**Who it affects:** Services using `oxygen-sql` hand-written selects that need aggregation grouped by a key — `countPersonsPerGroup`, `selectGroupIdWithNoteCount`, `SELECT team_id, COUNT(*) FROM person GROUP BY team_id HAVING COUNT(*) > 10`, dashboards, per-group statistics, `GROUP BY` for `jsonb_agg` patterns (OXY-14 notes `GROUP BY pk` is needed for JSON aggregation, workaround is lateral subquery). Current workaround is raw string SQL (`QueryContext` with manual `SELECT ... GROUP BY ...`) or fetching all rows and grouping in Scala (`groupBy` in `NonEmptyList` / `collection.groupBy`) — which defeats single-query aggregation, pushes work to the app, and bypasses compile-time safety.

**Why it matters (Priority Lowest):** `GROUP BY` is fundamental SQL but the DSL can cover many queries without it (point lookups, joins, filtered selects, single global `COUNT(*)` without `GROUP BY`). Priority `Lowest` (vs OXY-17 High, OXY-98 Higher) suggests this is completeness/nice-to-have, not blocking — especially because `count.*` without `GROUP BY` already works for global aggregates, and OXY-98's `zstream agg` + `sparse data` hints that richer aggregation is deferred. Still, without `GROUP BY`, any per-group count/sum must leave the DSL.

**Inferred acceptance criteria:**

1. DSL syntax for `GROUP BY` usable in a `for`-comprehension select after `select`/`join`/`where`, at minimum one ergonomic spelling — e.g.:
   ```scala
   // single key + count(*)
   @compile
   val countByGroup: QueryO[(UUID, Long)] =
     for {
       p <- select[Person]
       _ <- groupBy(p.groupId)
     } yield (p.groupId, count.*)

   // multi-key
   @compile
   val countByGroupAndStatus: QueryO[(UUID, String, Long)] =
     for {
       p <- select[Person]
       _ <- groupBy(p.groupId, p.status)
     } yield (p.groupId, p.status, count(p.id))

   // with where + orderBy + having (if in scope)
   @compile
   val having: QueryIO[Int, (UUID, Long)] =
     for {
       n <- input[Int]
       p <- select[Person]
       _ <- groupBy(p.groupId)
       _ <- having if count.* > n   // or: whereHaving / Q.having
     } yield (p.groupId, count.*)
   ```
   Exact spelling is unspecified by the title — `Q.groupBy`, `groupBy(...)`, `G.groupBy`, or extension on `select` — any satisfies "group by" but must be documented. Minimal viable is varargs of query-field refs (`T.QueryVariableReferenceLike`).

2. Generated SQL is `SELECT ... FROM person AS p GROUP BY p.group_id` (or `GROUP BY p.group_id, p.status`) with correct column qualification from `RowRepr`/`TableRepr` and `ORDER BY`/`LIMIT`/`OFFSET` still correctly ordered after `GROUP BY` (and `HAVING` after `GROUP BY` if supported). Column names are snake_case via `RowRepr.columns`.

3. Works as `QueryO` (no input) and `QueryIO[I, O]` (with `input[I]` / `where` param) and composes with existing clauses: `where`, `join`/`leftJoin`, `orderBy` (e.g., `orderBy(count.*.desc)` or `orderBy(p.groupId.asc)`), `limit`/`offset`. Validate SQL clause ordering: `FROM` → `JOIN` → `WHERE` → `GROUP BY` → `HAVING` → `ORDER BY` → `LIMIT` → `OFFSET`.

4. Compile-time macro support: new `RawQueryExpr.GroupBy`-like parsing (or reuse `VariableReferenceLike`) and `QueryExpr` case, new `GroupByPart` (and optionally `HavingPart`) in `modules/sql/core/src/main/scala/oxygen/sql/generic/model/part/`, extended `ParsedQuery.SelectQuery` with `groupBy: Option[GroupByPart]` (and `having`), parser in `PartialQuery`/`ParsedQuery.SelectQuery.parse` chaining `GroupByPart` after `WherePart`, plus `FragmentBuilder.groupBy` (and `having`) emitting `GROUP BY ...`.

5. `RETURNING` / `yield` handling: returning grouped keys and aggregates together — e.g., `yield (p.groupId, count.*)` decodes as `(A, Long)` via existing `DecoderBuilder` / `RowRepr` (`TypeclassExpr.RowRepr.long` for `count`). No new decoder needed for `count`; but if `sum`/`avg`/`min`/`max` are later added, they would reuse same pattern. For `GROUP BY`, validate that `yield` contains either grouped expressions or aggregates (or decide to emit without validation and let Postgres error `42803 grouping_error` — PSQLCode `grouping_error` already defined).

6. Tests + docs: `docs/docs/sql/queries.md` DSL vocabulary updated with `groupBy` (and `having` if included) and examples; `modules/sql/it-test` compiles the new syntax (`debug = true` snapshot) and integration-tests against real Postgres (`DbMigrationSpec`/`PostgresTestContainer` — see `modules/sql/it-test/src/test/scala/oxygen/sql/CustomQuerySpec.scala`) covering single-key group, multi-key group, group with `WHERE` filter, group with `ORDER BY` on grouped key and on `COUNT(*)`, `HAVING` with `COUNT(*) > ?` (if in scope), and empty-table edge case (0 groups).

7. Coordination: OXY-14 (`jsonb_agg` with `GROUP BY pk`) currently works around missing `GROUP BY` via lateral subquery; after this lands, `jsonb_agg` + `GROUP BY` can be expressed directly. OXY-98 (`zstream agg` / sparse data) likely builds on `GROUP BY`; keep `GROUP BY` orthogonal to any streaming `Agg` helper.

## Open Questions

1. **DSL spelling & arity:** Should the user write `groupBy(p.groupId)` bare, `Q.groupBy(p.groupId, p.status)`, or `Q.orderBy`-style varargs `Q.groupBy(p.groupId, p.status)`? Should it be a `for` line `_ <- groupBy(p.groupId)` (like `where`/`orderBy`) or a chain on `select`? Must compose with `where`/`orderBy` in any order or enforce `GROUP BY` after `WHERE`?
2. **HAVING in scope?** Title says only `group by` — is `HAVING` (the post-aggregation filter, e.g., `HAVING COUNT(*) > 5`) included or deferred to a follow-up? If included, what is the DSL: `having if count.* > n`, `Q.having(count.* > n)`, or `whereHaving(...)`?
3. **Aggregates covered:** Is `count.*`/`count(field)` sufficient for `GROUP BY` v1, or are `sum`/`avg`/`min`/`max`/`jsonb_agg` also expected? OXY-14 needs `jsonb_agg` + `GROUP BY` but currently works around via `LATERAL`; OXY-98 mentions `zstream agg` which may expect `GROUP BY`.
4. **Yield validation:** Should the macro validate that the `yield` tuple contains only grouped keys and aggregates (and error if it selects an ungrouped non-aggregated column), or should it emit SQL as-is and let Postgres return `42803 grouping_error` at runtime? Strict validation is safer but requires `yield` introspection.
5. **Expression GROUP BY:** Must `GROUP BY` support expressions (`DATE_TRUNC('day', n.createdAt)`, `p.firstName ++ p.lastName`) or is field-ref-only sufficient? Restricting to field refs is simpler but limits use-cases.
6. **Applicable query types:** Should `GROUP BY` apply only to `SelectQuery`, or also to `Update`/`Delete` sub-selects? Restrict to `SelectQuery` initially?
7. **Interaction with `distinct`/`ORDER BY` on aggregates:** Can user `orderBy(count.*.desc)` or `orderBy(p.groupId.asc)` after `GROUP BY`? Current `OrderByPart` parses only `QueryVariableReferenceLike`, so ordering by `count.*` would need extension.

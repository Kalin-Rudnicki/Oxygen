## Expanded Description

**What this likely means:** Add a minimal server-side `EndpointMiddleware` to `oxygen-http` (`modules/http/zio` — Epic OXY-2 `oxygen-http-server`) that exposes the **compiled HTTP API spec as JSON** over HTTP, so tooling/browsers/clients can discover the API without source access.

At runtime the server already has `Seq[EndpointSchema]` (derived by macros into each `Endpoint[Api]` via `DerivedServerEndpointImpl.makeSchema` / `RequestCodec.schemaAggregator` / `ResponseCodec`). The `oxygen-schema` compiled layer (`Compiled`, `RawCompiledSchemas`, `FullCompiledSchemas`) knows how to turn live `AnySchema`s into a serializable IR. The missing bridge is between the two: compile every endpoint's schemas into a single shared `RawCompiledApiSpec` (`RawCompiledApi` + `RawCompiledEndpoint` + `RawCompiledRequest`/`RawCompiledResponse` + shared `RawCompiledSchemas` bundle) and serve it.

The title says `/docs.json` — interpreted as `GET /docs.json` (or `GET /oxygen/api-spec`, `GET /api/docs.json`, etc. — exact path is a config detail) returning `application/json` with the compiled spec body. The sibling `OXY-32` ("Create basic `/docs` html endpoint middleware") is the companion that will serve an HTML human-readable view; this issue is the JSON machine-readable counterpart. Together they are **Phase 2 of `agent-docs/http-docs/http-feature-plan.md`** ("Serve the spec via an API → via an `EndpointMiddleware`").

**Who it affects:** Any `oxygen-http` server operator who wants self-documenting APIs; downstream consumers that will fetch the spec (OXY-32's HTML renderer, `OXY-38` endpoint-schema compatibility checking, `OXY-29` HTTP schema compatibility spec, and the example UI `ApiSpecPage` that today fetches `/oxygen/api-spec` via `RawClient` + `JsonCodec[RawCompiledApiSpec]`).

**Why it matters:** Without a serving endpoint the compiled spec (`oxygen.http.schema.compiled`) is in-memory only — useful for tests but not for external discovery. An endpoint middleware makes the spec fetchable at runtime with zero per-endpoint boilerplate (added once at server startup, composes via `>>>` under `Scope`, excludes itself from the served spec by construction). It is the prerequisite for the HTML docs (OXY-32), the compat-detection phase (Phase 4: persist + diff via `oxygen.schema.compat`), and any OpenAPI-like tooling the team later builds — the plan explicitly rejects OpenAPI in favor of this own-format spec.

**Inferred acceptance criteria:**
1. A **simple** `EndpointMiddleware` exists (pure `AppliedEndpoints => URIO[Scope, AppliedEndpoints]`), not a full server rewrite. It reads every `AppliedEndpoint.schema`, compiles via a shared compiler (`CompiledApiSpec.compile(Seq[EndpointSchema])` threading each `AnySchema` through `Compiled.json`/`Compiled.plain` into one `RawCompiledSchemas` bundle), serializes with `JsonCodec[RawCompiledApiSpec]`, and appends a new `AppliedEndpoint` serving it as `GET <path>` with `Content-Type: application/json`.
2. Default path is `/docs.json` per the title, or is trivially configurable (e.g. `Config(path = List("docs.json"))` / `List("oxygen","api-spec")` today). Path is GET-only; the appended endpoint's `EndpointSchema` documents it ("Serves the compiled oxygen-http API spec as JSON.").
3. Compilation happens **once at middleware application** (server startup), not per-request. The served spec **excludes the spec endpoint itself** (middleware reads the incoming set then appends — by construction the spec describes only the endpoints present before it). `compileWithoutLineNos` variant is available for the persisted/diffed stable form (Phase 4).
4. Response bypasses `ResponseCodec.encodeResponse` correctly: body is `BodyUtil.fromString(specJson, MediaType.application.json)` plus explicit `Header.ContentType(MediaType.application.json)` header.
5. Middleware is wired via `Middlewares` / `CompiledMiddlewares` / `CompiledEndpoints.compile(endpoints, middlewares)` so it composes with other `RequestMiddleware`/`ResponseMiddleware`/`EndpointMiddleware` (`>>>`), and is demonstrated in `example/apps/webServer/WebServerMain` (or equivalent wiring test). A `defaultMiddleware: Middlewares[Any]` convenience exists.
6. At least one integration point is verified: fetching the configured path returns `200` with a JSON body that `JsonCodec[RawCompiledApiSpec].decoder` can round-trip and that `FullCompiledApiSpec.show` renders without error (see `modules/http/it-test/src/test/scala/oxygen/http/CompiledApiSpecSpec.scala` — 5 tests — as the existing precedent).

## Open Questions

1. **Default path — `/docs.json` vs `/oxygen/api-spec`:** Title says `/docs.json`; shipped implementation defaults to `/oxygen/api-spec` (`ApiSpecEndpointMiddleware.Config.default.path = List("oxygen","api-spec")`). Should the default be changed to `List("docs.json")`, should the middleware serve both paths, or should OXY-31 be closed as "done" with the current path? (One-line config decision; affects UI fetch URL and any external tooling assumptions.)
2. **Path configurability scope:** Should the middleware expose a single `path: List[String]` (as today), a `NonEmptyList` variant, or a full `RequestPathsSchema`-style path? Keep it simple (`List[String]`) per "simple" in the title.
3. **Auth / exposure:** Should the JSON spec endpoint be publicly accessible or gated behind auth/middleware? Current implementation is open. No change needed for "simple", but worth confirming for production.
4. **Content negotiation / caching:** Does `GET /docs.json` need `ETag`/`Cache-Control`/`Accept` handling, or is a plain `200` with `Content-Type: application/json` sufficient? Current code does the latter; confirm this meets the "simple" bar.
5. **Self-exclusion guarantee:** Confirm that the spec endpoint itself is intentionally excluded from the served spec (current behavior: middleware reads incoming set then appends). This is desired but should be documented.
6. **Assumption to confirm:** That "endpoint middleware" here means `oxygen.http.server.EndpointMiddleware` (`AppliedEndpoints => URIO[Scope, AppliedEndpoints]`) as opposed to `RequestMiddleware`/`ResponseMiddleware` — i.e. the endpoint-adding variant. Verified by the shipped code and `http-feature-plan.md`, but the title alone could be read either way.

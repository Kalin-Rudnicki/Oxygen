## Expanded Description

**What this bug is:** The bottom-corner toast/page-message overlay (`PageMessagesBottomCorner` — fixed-position stack rendered by `HolyGrail` via `PageMessages.PageLocal` `FiberRef`) does not wrap long text. A message with a long unbroken string or a long sentence (e.g. a server error, validation summary, or `"Info toast, " * 50`) overflows the card horizontally — either painting off-screen, growing `fit-content` forever, or clipping without wrapping — instead of wrapping inside the card's `maxWidth`.

**How it was broken (verified by git history):** The pre-fix implementation (`78b55154` / `369bb2f0~1` — `modules/ui/web/src/main/scala/oxygen/ui/web/component/PageMessagesBottomCorner.scala:89-127` before `369bb2f0`) had:

- Content `div` with `whiteSpace.pre` (CSS `white-space: pre` — preserves whitespace, **never wraps**). This is the root cause; the file's own post-fix comment calls it `white-space:pre was the overflow bomb (no wrap, fit-content grows forever)` (`PageMessagesBottomCorner.scala:71` on current branch).
- Card `div` as `display.inlineBlock`, `width.fitContent`, `minWidth := cfg.minWidth` / `maxWidth := cfg.maxWidth` without `maxWidth: 100%` or `overflow.hidden` or `flexShrink: 0`, so a non-wrapping child forces the card to grow past the viewport.
- Dismiss `button` absolutely positioned (`position.absolute`, `top 0.5rem`, `right 0.5rem`, `zIndex 2`) overlapping the text `div` which carries `marginRight 2.5rem` — truncation/wrap still fails because the text container itself never wraps.
- Outer fixed shell `div` with `right: 20px` + `maxHeight := cfg.maxHeight` but without `maxWidth/min(750px, calc(100vw - 24px))`, `width`, `boxSizing`, `pointerEvents` separation, or `O.Scrollable` on the *list* — so tall stacks clip or squash cards rather than scrolling.

**User-visible symptoms:** On desktop, a long toast extends past the viewport right edge; on mobile/narrow viewports it overflows even sooner. With `fit-content` + `white-space: pre`, the card width is the content's intrinsic width (unbounded), so the fixed bottom-right stack is pushed off-screen. Horizontal scroll may appear. Multi-line messages with `\n` render as single pre-formatted line. The showcase page `example/apps/ui/src/main/scala/oxygen/example/ui/page/showcase/pages/MessagesPage.scala:25-31` explicitly reproduces this: four buttons fire `PageMessage.info/success/warning/error("… " * 50)` — the bug title maps 1:1 to that showcase.

**Why it matters (Priority Higher):** Page messages are the primary transient feedback surface (`PageMessages.add`, `PageMessages.schedule`, `RootErrorHandler`, `docs/docs/ui/agent-guide.md:50`, `docs/docs/ui/builders.md:146` — "Page messages are included by default. HolyGrail mounts PageMessagesBottomCorner"). Every form error, `UIError`, and `PageMessages.add(PageMessage.error(...))` goes through this path. An unwrapped long error (e.g. `400 Bad Request — <long validation message>` or `500 <stack trace>`) is unreadable on both desktop and mobile, blocks the dismiss button, and looks broken. `Higher` (one step below `Highest`) is consistent with a visible UI defect on a default-mounted component that affects all pages using `HolyGrail`.

**Inferred acceptance criteria:**

1. A toast with long natural-language text (spaces between words) wraps onto multiple lines inside the card, which itself is capped at `cfg.maxWidth` (`750px` default) and `min(750px, calc(100vw - 24px))` for narrow viewports. Short toasts still hug `fitContent` width and right-align via `alignItems.flexEnd` on the stack.
2. A toast with a long *unbroken* string (no spaces, e.g. a URL or token `aaaaaaaa…`) also wraps/breaks (`wordWrap: break-word` / `overflow-wrap: anywhere` / `wordBreak: break-word`) rather than overflowing the card.
3. Intentional newlines (`\n` in the message) are preserved (hence `whiteSpace.preWrap`, not `normal`) — `preWrap` preserves `\n` and sequence-whitespace but still wraps long lines.
4. Cards never paint outside the viewport; flex layout ensures the text `div` can shrink below its content intrinsic size (`minWidth: 0`, `flex: 1 1 auto`, `maxWidth: 100%`, `overflow.hidden` on card). The dismiss `×` button is a flex-row sibling (`flex: 0 0 auto`, `28px` square, `inlineFlex centered`) that never overlaps text and never causes horizontal overflow.
5. Stacking N toasts: the fixed shell is only a positioning container (`position.fixed`, `bottom 0`, `right 0`, `pointerEvents.none` except on cards/Close All); the *scrollable list* owns `maxHeight: min(75vh, calc(100dvh - 96px))` + `O.Scrollable` (`overflow-y: auto`, `minHeight: 0`, `flexWrap.nowrap`) so many tall/wrapped toasts scroll rather than painting off-screen or squashing via `flex-shrink`.
6. No visual regression for short messages: right-aligned stack, single-line short toast width ≈ content width, existing colors/shadows/radius preserved, `Close All` button when `size > 1`.
7. Covered on narrow viewports (`100vw - 24px` cap) — verified conceptually by the `stackMaxW` calc; ideally manually checked at 320px width.

## Open Questions

1. **Confirmed already fixed — should OXY-109 be closed?** Current `HEAD`/`origin/main` already contain the full wrapping fix (`369bb2f0`). Checklist still shows `- [ ] OXY-109` (To Do). Action: flip to `- [x]` after verifying `MessagesPage` long toasts wrap, or confirm with assignee whether a follow-up polish (e.g., `hyphens: auto`, `lineClamp`) is still desired.
2. **Unbroken-string policy:** Current fix uses `wordWrap break-word` + `wordBreak break-word` + `overflow-wrap anywhere` — this breaks anywhere (including mid-word) for very long tokens (URLs, hashes). Should extremely long tokens instead use `wordBreak: break-all` or `overflow-wrap: break-word` only? The current `anywhere` is the most aggressive; product may prefer `break-word` alone to avoid breaking short words mid-glyph.
3. **Mobile cap:** `stackMaxW = min(750px, calc(100vw - 24px))` leaves 12px gutters. Is 24px the desired gutter, or should it match the app's `S.spacing` scale (e.g. `S.spacing._4` = 16px → `32px`)? Trivial but worth confirming with design.
4. **Stack height:** `listMaxH = min(75vh, calc(100dvh - 96px))` leaves 96px for `Close All` + padding. If future OXY-110 adds taller featureful messages (open dialog, etc.), should the stack become paginated or virtualized rather than simply scrollable? Out of scope for this bug, but noted for OXY-110.
5. **No other page-message surface affected?** `PageMessage` content is a `Widget` — callers could embed a `pre`/`code` widget with its own `whiteSpace.pre`. Should embedded `pre` blocks inside a toast get `preWrap` forced via a child selector, or is it the caller's responsibility to style embedded widgets? Current fix styles only the immediate text container.

## Expanded Description

**What this likely is:** Add a first-class, ergonomic HTTPS/TLS knob to `oxygen.http.client.Client` so callers can make `https://` requests with minimal configuration — without dropping to raw `zio.http.ZClient` or `javax.net.ssl` details. It is the **client-side counterpart to OXY-79** (easy HTTPS config to server) under Epic **OXY-3 — oxygen-http-client**, and the deferred `ssl` half of the `TODO (KR) : ssl` in `modules/http/zio/src/main/scala/oxygen/http/client/Client.scala:11-12` that was intentionally left for OXY-80 after the broader `OXY-35` client paradigm cleanup.

Current state (verified by reading `modules/http/zio/src/main/scala/oxygen/http/client/Client.scala:10-73`, `RawClient.scala:1-13`, `RawClientPlatformSpecific.scala:1-10`, `RawClientPlatformSpecificImpl.scala:1-15` (JVM), `ZioHttpClient.scala:1-32`, `modules/http/zio/src/test/scala/oxygen/http/client/MultiClientSpec.scala:1-31`, and zio-http 3.7.4 `zio/http/ZClient.scala:Config` + `zio/http/ClientSSLConfig.scala`):

1. **`Client.Config` has no TLS surface.** It is `Config(kind: URL.Location, path: Path, logLevel: LogLevel)` — raw `zio.http.URL` pieces plus log level. No `ssl`, `tls`, `trustStore`, or `verifyPeer` field, no `derives JsonCodec`, no `ssl`-aware factory. Callers construct it via `Config.layer(urlString)` (which does `URL.decode(urlString)` with query/fragment guards) or `Config.relativeUrl`. The URL's `Scheme` already distinguishes `HTTP` vs `HTTPS` (`URL.Location.Absolute(Scheme.HTTPS, "service-a.com", None)` in `MultiClientSpec:30-31`), so `https://` URLs are accepted today, but there is no way to configure client certificates, custom trust, or insecure mode through oxygen's abstraction.

2. **Transport TLS lives one layer below, unused.** `RawClient` wraps `zio.http.Client` and is provided via `RawClient.default = ZLayer.succeed(ZClient.Config.default) >>> requiringConfig` (`RawClient.scala:11-12`) where `requiringConfig` delegates to `zio.http.ZClient.live` with `NettyConfig.defaultWithFastShutdown` + `DnsResolver.default` (JVM). `ZClient.Config` (`zio/http/ZClient.scala:Config`) already contains `ssl: Option[ClientSSLConfig]` with `Config.default.ssl = None`, and `ClientSSLConfig` (`zio/http/ClientSSLConfig.scala`) is a rich ADT: `Default`, `FromCertFile`, `FromCertResource`, `FromTrustStoreFile`, `FromTrustStoreResource`, `FromClientAndServerCert`, `FromJavaxNetSsl` (with `keyManager`/`trustManager` file/resource/password/ keyStoreType fields), plus `ZIO Config` derivation via `ClientSSLConfig.config` and `ZClient.Config.config` nesting `ssl` under `"ssl"`. `ZClient` (the typed client) carries `sslConfig: Option[ClientSSLConfig]` and exposes `def ssl(ssl: ClientSSLConfig): ZClient` and `def request` threads `sslConfig` to the driver. None of this is surfaced through `Client.Config` or `RawClient`; `RawClient.default` always uses `ZClient.Config.default` (no SSL).

3. **The `TODO : ssl` was deferred.** `Client.scala:11-12` reads `// TODO (KR) : accept middlewares when creating a client / : ssl` — the only in-repo hint of intended scope. `OXY-35` (Clean up client configuration paradigm) analysis explicitly lists this TODO as either in-scope for OXY-35 or deferred to `OXY-80`/`OXY-76`, and `OXY-79`/`OXY-80` are paired Lowest-priority tasks under the same "easy HTTPS" theme, confirming OXY-80 is the follow-up that resolves the `ssl` line.

4. **Sibling and priority signal.** Checklist pairs `OXY-79` (server HTTPS, Lowest) with `OXY-80` (client HTTPS, Lowest), alongside `OXY-34`/`OXY-35` (paradigm cleanup, Normal) and `OXY-76`/`OXY-77` (logging/metrics, Low/Lower). Priority Lowest (not Higher/High) indicates a small DX/ergonomics improvement, not a production bug or blocker. The word "easy" (shared with OXY-79) signals the fix should be a thin, typed wrapper — e.g., `Client.Config.withHttps` / `Client.Config.ssl(ClientSSLConfig.Default)` / `OXY-80` adding `ssl: Option[ClientSSLConfig]` or `tls: Boolean` to `Client.Config` — not a full mTLS framework or custom `SSLContext` builder.

**Who it affects:** Consumers of `oxygen.http.client.Client` / `DeriveClient` / `RawClient` that need to call `https://` endpoints (external services, staging with self-signed certs, mTLS services, and tests via `ViaHttpSpec`/`MultiClientSpec`). Today they must either rely on default JVM trust (works for public CAs but not for custom certs) or drop to `RawClient.requiringConfig` with a hand-built `ZClient.Config(...).ssl(...)`, bypassing `Client.Config` entirely — undocumented and inconsistent across services.

**Why it matters (Lowest priority):** As `oxygen-http-client` matures (Epic OXY-3), every service that adds an `https://` downstream will copy-paste `ZClient.Config` assembly. An "easy" config (one field/flag on `Client.Config` that maps to `ZClient.Config.ssl` + wires `RawClient`) centralizes TLS decisions, enables `@envConfig`/`JsonCodec` derivation (so TLS can be configured via env/file like `WebServerMain.Config`), and unblocks consistent docs for `oxygen-http`. Lowest priority suggests it is not blocking OXY-3 release (http calls work today when the URL is `https://` and the trust store is default), but it is polish before `OXY-81` docs and before services need mTLS.

**Inferred acceptance criteria:**

1. `Client.Config` (or `RawClient.Config` via `Client.Config`) exposes an easy HTTPS knob that maps to `ZClient.Config.ssl: Option[ClientSSLConfig]` — at minimum `Client.Config` with `ssl: Option[ClientSSLConfig] = None` defaulting to `ClientSSLConfig.Default` when `https://` is used, or a simpler `useHttps: Boolean` / `insecure: Boolean` alias; ideally the ADT is re-exported or thinly wrapped so callers can write `Client.Config.layer("https://service.com", ssl = ClientSSLConfig.Default)` or `Config.https("service.com")` without importing `zio.http` internals. The `Config.layer(urlString)` parser already validates query/fragment absence — it should also accept `https` scheme and not reject it.
2. `RawClient`/`Client.layer` wiring propagates the SSL config: `RawClient` gains either `def fromZClientConfig(Config)` or `Client.Config >> ZClient.Config` translation, and `Client.layer.default: RLayer[Client.Config, Client]` (currently `RawClient.default >>> live` at `Client.scala:63-64`) internally derives `ZClient.Config` with the `ssl` field rather than always using `ZClient.Config.default`. Existing `Client.layer.live: URLayer[RawClient & Config, Client]` remains as escape hatch for users who already provide `RawClient`.
3. No breaking change to existing call sites beyond additive field: `MultiClientSpec` (with `https://service-a.com` / `https://service-b.com`) and `ViaHttpSpec` / `UIMain` (`relativeUrl` with `http://localhost:$port`) continue to pass; new factories like `Client.Config.https` or `Config.layer(urlString, ssl)` are additive. If `Client.Config` gains `JsonCodec`/`JsonSchema` derivation (as OXY-35 proposes), the `ssl` field also derives cleanly (likely as `String` path or nested `ClientSSLConfig.config` via ZIO Config interop).
4. Docs: brief note in `docs/docs/http/client/index.md` (currently `TODO : Oxygen HTTP Client`) describing how to enable HTTPS (default trust vs custom cert file/resource vs trustStore vs `ClientSSLConfig.Default`), relationship to `OXY-79` server HTTPS and `OXY-35` paradigm, and when to use `RawClient` directly vs `Client`. Placeholder `mcp-feature-plan` etc. unchanged.
5. No behavior change to request encoding / response decoding / `ClientErrorHandler` / logging (OXY-76) / metrics (OXY-77) — purely config/wiring.
6. Tests or a doc example show an `https://` client can be constructed via the new API (ideally an in-memory `ZioHttpClient` unit test or an integration test that provisions `Client.Config` with `ClientSSLConfig.Default` and asserts `client.config` reflects the scheme/SSL — actual TLS handshake not required in CI).

## Open Questions

1. **SSL field shape:** Should `Client.Config` gain `ssl: Option[zio.http.ClientSSLConfig]` (thin re-export, preserves full `ClientSSLConfig` ADT including `FromCertFile`/`FromTrustStoreFile`/`FromJavaxNetSsl`/`FromClientAndServerCert` and `ZIO Config` derivation) or a simplified `SslConfig` wrapper (e.g., `Default | FromCertFile(path) | FromTrustStore(path, password)` mapping to `ClientSSLConfig`), or just `useHttps: Boolean` / `insecure: Boolean`? Should it derive `JsonCodec`/`JsonSchema` for `@envConfig` or rely on `ClientSSLConfig.config` (ZIO Config)? This determines `Config.layer` overloads and backwards-compat.
2. **Re-export vs wrap:** If thin re-export, callers must import `zio.http.ClientSSLConfig` — does oxygen want to hide zio-http types behind `oxygen.http.client.SslConfig` (consistent with OXY-35's goal of not leaking `URL.Location`/`Path`), or is exposing `ClientSSLConfig` acceptable for "easy" scope? Should `ClientSSLConfig` be type-aliased as `oxygen.http.client.ClientSSLConfig`?
3. **Per-client vs shared `RawClient`:** When two clients have different SSL configs (e.g., `service-a` with custom cert, `service-b` with default trust), can they share `RawClient.default` (single `ZClient.Config`) or does each `Client.Config` need its own `RawClient` layer? Current `MultiClientSpec` shares `RawClient.default` across two `https://` clients with `None` SSL — does the new design keep sharing or introduce `Client.layer.default` that builds a private `RawClient` per `Client.Config`?
4. **Scope vs OXY-35:** Does "easy HTTPS config" belong in OXY-35's paradigm cleanup (i.e., should OXY-35 already add `ssl` to the new `Client.Config` shape with `baseUrl: String`), leaving OXY-80 to add only convenience factories (`Config.https`, `Config.insecure`), or is OXY-35 purely `URL.Location`/`Path` → `baseUrl` refactoring and OXY-80 adds the entire `ssl` field? Sequencing matters for whether OXY-80 depends on OXY-35.
5. **mTLS and `ClientSSLCertConfig`:** Should the initial implementation include client-certificate support (`ClientSSLConfig.FromClientAndServerCert` with `ClientSSLCertConfig` for mTLS) or defer to a follow-up? "Easy" suggests one-way TLS first, but confirming avoids scope creep.
6. **Insecure / trust-all mode:** Should there be an explicit `insecure: Boolean` or `trustAll: Boolean` that maps to a `ClientSSLConfig` that trusts all certs (useful for local dev with self-signed certs), or is that out of scope / discouraged? If included, it should be clearly documented as dev-only.
7. **JS target:** `modules/http/zio/.js/src/main/scala/oxygen/http/client/RawClientPlatformSpecificImpl.scala` also implements `rawRequiringConfig` — does the `ssl` config apply on JS (browser `fetch` handles TLS differently), or is the new `ssl` field JVM-only with JS as no-op? This affects whether `@envConfig` derivation includes `ssl` on JS.
8. **Assumption to confirm:** That "client" refers to the `oxygen-http` client (`modules/http/zio/src/main/scala/oxygen/http/client/Client.scala` — Epic OXY-3 In Progress) and not to some other client (e.g., `oxygen-sql` `DbConfig`, `oxygen-pulsar` `PulsarClient.Config` with its own `tls` field, `oxygen-ui` web client). Confirmed by module proximity and sibling OXY-79 server / OXY-35 client paradigm, but worth explicit sign-off.
